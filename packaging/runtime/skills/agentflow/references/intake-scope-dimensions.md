# Intake 范围维度清单（主动穷举，而非被动应答）

> **解决什么**：痛点 7——登录 feature 完全没有提前沟通三方登录（微信 / QQ）、邮箱 / 手机验证、注册、格式支持、防抖等；部分是用户提问后才补齐。根因：intake（开工提问）只问「已明确的不确定项」，不主动枚举「本类功能的常见范围维度」。
>
> **用法**：进入 intake / 需求评审前，按 feature 领域选一张维度表，**逐维主动确认**（一次最多 2 个选择题，遵循 `references/intake.md` 六要素纪律），把用户选择落进 `proposal` 的「范围」节与 `spec/checklist.md`，避免「第一版没沟通、提问才补」。

## 0. 通用维度（所有 feature）

- [ ] 用户角色与权限分层
- [ ] 是否需要审计 / 埋点
- [ ] 是否需要国际化 / 多语言
- [ ] 性能与规模基线（并发 / 数据量）
- [ ] 合规与隐私（PII / 加密 / 留存）

## 1. 认证 / 登录类（重点）

- [ ] **认证方式**：账号密码 / 手机号 / 邮箱 / 三方（微信 / QQ / Google / GitHub）/ SSO
- [ ] **注册**：是否支持注册、自助 / 邀请、邮箱 / 手机验证
- [ ] **找回与重置**：忘记密码流程、验证渠道
- [ ] **验证渠道防抖**：验证码发送冷却、重试限频、暴力破解防护
- [ ] **会话与退出**：记住我时长、退出失败是否清本地态
- [ ] **格式与单位**：账号格式（邮箱 / 手机号正则）、密码强度规则
- [ ] **可访问性**：错误文案、键盘操作、读屏
- [ ] **三方登录 UI 边界**：未配置时的降级（隐藏还是占位）、回跳 / 回调 / 失败回退、与自有账号绑定
- [ ] **登录后落点（信息架构）**：登录成功去哪里——既有视图 / 独立首页 / 回跳来处；「沿用现状」类决策与新增决策同级显式列出，不默认通过
- [ ] **未登录访问受控区**：业务页匿名可达吗——可访问 / 跳登录 / 明显标注演示；不问这一条等于登录不设防

## 2. 数据 / 报表类

- [ ] 实时 vs 离线（T+1）
- [ ] 导出格式（CSV / Excel / API）
- [ ] 口径变更兼容（历史数据如何处理）

## 3. 交易 / 支付类

- [ ] 幂等与防重（见 `standards/server-side.md` §1）
- [ ] 退款 / 对账
- [ ] 失败补偿与人工干预

## 4. 集成 / 接口类

- [ ] 同步 vs 异步
- [ ] 重试与死信
- [ ] 版本与废弃窗口

> 领域表可持续扩充；新增领域维度时登记到本文件并 bump 版本（遵循 Host Init 的漂移规则）。agent 在 intake 时**必须显式逐维确认**，而非等用户想到再补——这是消除「被动应答」的关键。
