# Git 提交与变更记录规范（agentflow 通用底线）

> **定位**：与宿主全局规则 `global-rules.md` 配套的 Git 提交信息与变更粒度规范。agentflow 强调版本可追溯、评审可复现与变更原子性；本册提供**提交信息格式、分类语义、任务关联与破坏性变更标注**的硬判据。
> **来源**：吸收 Conventional Commits 1.0.0 规范与大型工程团队实践，对齐 agentflow 任务计划（Execution Plan）与缺陷（Issue）追踪体系。
> **编号**：`GIT-01…GIT-07`，供 Reviewer 在代码合入评审时核查，或开发者日常提交遵循。

## 0. 适用范围

所有纳入版本控制的代码库提交（Git Commits）、Pull Request / Merge Request 标题与变更日志生成。

## 1. 提交信息结构标准（GIT-01）

**MUST**
每次 Git 提交信息必须遵循标准三段式结构：

```text
<type>(<scope>): <subject>

[optional body: 详细说明改动动机、核心方案与影响面]

[optional footer(s): 关联任务编号、Issue、关闭命令或 BREAKING CHANGE 声明]
```

- **Header 限制**：首行（Header）总长度建议不超过 72 个字符，禁止使用无意义的提交词（如 `fix bug`、`update code`、`test`、`wip`）。
- **Subject 规范**：使用动词祈使句开头，首字母小写（英文）或精准动宾短语（中文），结尾不加句号。

## 2. 变更类型与语义定义（GIT-02）

**MUST**
`<type>` 必须使用以下标准枚举值之一，不得随意自创类型：

| 类型 (Type) | 语义说明 | 是否影响版本号 | 示例 |
|---|---|---|---|
| `feat` | 新增用户可见功能或特性 | MINOR (次版本) | `feat(auth): 新增企业微信扫码登录支持` |
| `fix` | 修复用户可见或内部运行的缺陷 | PATCH (修订号) | `fix(order): 修复快速双击导致重复扣减库存问题` |
| `refactor` | 重构代码（不改变外部行为，非新增功能也非修 bug） | PATCH | `refactor(payment): 抽取支付渠道路由到独立策略类` |
| `perf` | 性能提升与优化改动 | PATCH | `perf(query): 为用户订单列表增加联合索引` |
| `test` | 增加或重构测试用例（单测、集成测试、E2E） | 不变 | `test(auth): 补充登录态过期自动刷新的集成用例` |
| `docs` | 仅文档改动（README、API 规范、架构设计） | 不变 | `docs(api): 补充退款接口错误码对照表` |
| `style` | 代码格式调整（空格、分号、lint 格式，不影响代码逻辑） | 不变 | `style(ui): 统一使用 prettier 格式化样式文件` |
| `ci` | 持续集成与部署脚本配置（Actions, GitLab CI） | 不变 | `ci(github): 新增 PR 提交自动触发安全静态扫描` |
| `build` | 构建系统或外部依赖变更（npm, cargo, poetry 升级） | PATCH / 不变 | `build(deps): 升级 axios 至 1.7.0 修复安全漏洞` |
| `chore` | 日常杂项与非核心维护工作 | 不变 | `chore(release): bump version to 0.44.0` |

## 3. 破坏性变更标注（GIT-03）

**MUST**
- 当变更包含破坏向下兼容性的修改（Breaking Changes，如接口删除、参数类型变更、存储结构不兼容时），必须在 Header 或 Footer 中显式标注：
  - **Header 叹号标注**：在 `<type>(<scope>)` 之后紧跟 `!`，如 `feat(api)!: 废弃 v1 接口并修改返回结构`。
  - **Footer 详细说明**：在提交信息底部增加以 `BREAKING CHANGE:` 开头的段落，清晰说明破坏点及调用方迁移路径：
    ```text
    feat(api)!: 统一使用新版响应信封结构

    BREAKING CHANGE: 移除旧版顶层 `result` 字段，全量切换为 `data` 与 `code` 包装。
    迁移指南：调用方需将 response.result 改为 response.data。
    ```
- 包含 `BREAKING CHANGE` 的提交将触发 MAJOR（主版本号）升级。

## 4. 任务计划与 Issue 强绑定（GIT-04）

**MUST**
- **关联任务**：在承接 agentflow 执行计划（`plan/execution.md`）中的任务时，提交信息 Footer 必须关联具体任务号，如 `Task: T03` 或 `Task: T03, T04`。
- **关联缺陷**：在修复缺陷（Issue）时，提交信息 Footer 必须关联缺陷单编号，如 `Closes: ISS-20261124-001` 或 `Fixes: #128`。
- 严禁提交脱离计划或无缺陷关联的“孤儿生产代码修改”。

## 5. 原子性提交与单一职责（GIT-05）

**MUST**
- **单一职责**：一次提交只完成一个逻辑独立的变更。严禁将功能实现（`feat`）与大规模代码格式化（`style`）或无关的重构（`refactor`）混合在一个提交中。
- **构建可独立通行**：每个提交节点必须能够独立通过编译、静态检查和自动化测试，不得将不可编译的中间状态提交到共享分支。

## 6. 严禁敏感信息与杂质入库（GIT-06）

**MUST**
- **敏感文件拦截**：提交前必须核查 `git status`，绝对禁止将本地密钥（`.env`、`*.pem`、`id_rsa`）、临时调试文件、本地 IDE 专属配置提交入库。
- **完备 `.gitignore`**：项目根目录必须具备完备的 `.gitignore`，覆盖 Node/Python/Go 等运行时产物、构建缓存目录及本地环境变量。

## 7. PR / MR 标题、正文与合并边界（GIT-07）

**MUST**
- 标题沿用 GIT-01 的 `type(scope): subject`，不得用「更新」「修复若干问题」这类无法检索的标题。
- 正文至少四段：改了什么、为什么、影响面与验证证据、风险与回滚；关联 `Task:` / `Closes:`。
- 一个 PR/MR 只做一件逻辑变更；混合改动先拆，不把格式化、重构与功能塞进同一个 PR。
- 合并前确认目标分支、必需检查通过、冲突已解决并重跑受影响检查；冲突解决不等于授权合并。
- **合并与推送是两次独立授权**：解冲突 ≠ 合并，合并 ≠ 推送；未经当次明确授权，不执行 merge / push / 远端数据删除。
- 不写 AI/LLM 署名或 co-author 行，除非用户明确要求。
- 不把密钥、内网地址、用户数据放进 PR/MR 描述、截图或评论。

**拆分计划（有多个合并单元时）**

- 以实际 diff 或拟改路径为范围，查 `CODEOWNERS`、目录维护约定或负责人确认。每片列任务、文件范围、评审方依据、目标分支与可在该片运行的验证。路径归属未知时说明待确认项。
- 同时改动共享契约和消费者时检验中间状态能否构建和运行。兼容过渡可按依赖排序分开，否则把必须原子落地的改动放同一片。各片独立时从各自实际目标分支出发；有真实依赖时写前置、合并顺序和最终集成检查。
- 待拆内容已在工作区时，拟计划先对账已提交、未提交及暂不拆的文件。执行所需分支、提交、推送和开 PR/MR 按当前授权办理，移动改动前按[保全规则](../execution.md#不可逆操作前的保全与清理)保全。
