# 服务端工程内容标准（agentflow 通用底线）

> **定位**：agentflow 的 `document-chain` / `review-checklists` 是**流程门禁**（查「文档齐不齐、门过没过、表达守不守纪」）；本册是**工程内容底线**（查「写出来的服务端代码专不专业」）。两者互补——Reviewer 在给 `approved` 前同时套用。
>
> **来源**：吸收 youc《服务端工程规范》的硬判据（BE-10 幂等、BE-15 稳定性、BE-02 反过度分层）重写为与 agentflow 评审链对齐的通用底线。项目有更强规范时以项目为准；本项目规范缺失时用本册。
>
> **适用**：`design/be`、`spec/be`、任何服务端代码实现、代码评审、服务端 bug 修复。

## 0. 何时必查

Reviewer 对每条服务端改动套用下面的 **MUST** 判据；任一 MUST 不满足即 `changes_requested`，finding 标注 `defect_class: 代码` 或 `规范`（若因本册未引用导致漏写，归 `规范`）。

## 0.1 按规模分级（防止单进程 / 演示批次照字面执行即红）

- **集群级条款只对多实例或对外多租户部署强制**：§5 的限流 / 背压 / 无单点、§6 的链路追踪与指标三件套。单进程 / 本地演示批次在 design/be（§1.3.3 运行边界或 §2 稳定性）**声明「单进程部署，不适用」即放行**——声明是义务，沉默跳过才是缺陷。
- **任何规模都强制**：幂等或显式非幂等声明（§1）、入口校验与不吞异常（§2）、下游超时、资源有界（内存态也要写上限与清扫）、日志不打敏感（§4）。
- 判级依据写一行：部署形态（本地演示 / 单实例生产 / 多实例），落 design/be §1.6 影响等级旁。

## 1. 幂等（Idempotency）— BE-10

**MUST**
- 所有**会改变状态**的接口（写 / 更新 / 删除 / 支付 / 发送 / 触发异步任务）必须幂等，或在 design 显式声明「非幂等 + 理由 + 客户端去重责任」。
- 幂等实现三选一且写进 design/be §1.4.5：① 天然幂等键（订单号 / 业务单据号）；② 客户端幂等键（`Idempotency-Key` 头，服务端 24h 内同键返回首结果）；③ 乐观锁（`version` / `ETag`）。
- 重试安全：网络超时 / 502 重试不得造成重复副作用（重复扣款、重复发信、重复创建）。
- 明确「已处理」判据：返回 200 + 业务结果，还是 409 冲突 / 202 已受理，写进契约。

**SHOULD**：幂等键作用域、保留期、跨实例一致性写进数据模型（见 `data-model.md` DB-45）。

## 2. 鲁棒性（Robustness）

**MUST**
- **边界校验**：所有外部输入（参数 / header / body / 文件 / 上游响应）在**入口**做类型 / 范围 / 长度 / 非空 / 枚举校验，非法即 4xx，不传到业务层。
- **不吞异常**：`catch` 后必须记录结构化错误（含 `requestId`）+ 上抛或转领域错误；禁止 `catch {}` 空块、`except Exception: pass`、`try` 后无日志。
- **超时与熔断**：所有下游调用（DB / HTTP / RPC / 队列）设超时；对不稳定依赖加熔断 / 降级，降级路径可观测。
- **资源有界**：连接池 / 线程池 / 并发数 / 分页大小有明确上限；不无界增长。

**SHOULD**：失败分「可重试 vs 不可重试」；不可重试失败快速失败，不盲目重试放大故障。

## 3. 面向对象与分层（OOP & Layering）— BE-02

**MUST**
- **单一职责**：一个类 / 模块只承担一类职责；不把业务逻辑堆在 controller 或一个巨型 service。
- **依赖注入**：依赖通过接口 / 构造注入，不藏在全局单例里偷偷取；便于测试与替换。
- **领域行为**：领域模型承载行为，不只是 getter/setter（避免贫血模型）——计算 / 规则进领域对象或领域服务。

**SHOULD**：接口隔离，不强迫实现用不到的方法。

**MUST NOT（反过度分层，BE-02）**：不要为「看起来规范」加无业务逻辑的中转层（多余 repository 包装、纯转发 service、空 `Impl`）。层是为边界与可测性存在，不是仪式。

## 4. 可维护性（Maintainability）

**MUST**
- 命名表达意图，无黑话缩写；魔法数字 / 字符串提为具名常量。
- 函数短小、单一出口清晰；一个函数只做一件事。
- 日志带 `requestId` 贯穿；关键分支有日志但不打敏感（密码 / token / 身份证 / 银行卡）。
- 无死代码、无注释掉的旧实现（历史用版本控制，不靠注释保留）。

**SHOULD**：模块间依赖方向稳定、可画出来；公共 API 有契约注释。

## 5. 稳定性（Stability）— BE-15

**进程级（单实例）MUST**
- **优雅关闭**：收到 SIGTERM 先停收新请求、排空在途、释放连接，再退出；不暴力 kill 丢在途。
- **启动自检**：依赖（DB / 配置 / 下游可达）不可用时明确失败并报警，不「起了但半残」。
- **资源限制**：内存 / 文件句柄 / goroutine / 连接数有上限与监控。

**集群级（多实例 / 多租户）MUST**
- **限流**：对单用户 / 单 IP / 单接口有速率上限，超过返回 429 而非压垮。
- **背压**：队列 / 批处理在下游慢时降级或拒绝，不无限堆积。
- **无单点**：关键依赖有降级或冗余；避免「一个慢依赖拖垮全站」。

## 6. 错误处理与可观测性

**MUST**
- 错误分域（用户输入错误 / 依赖错误 / 系统错误），对外只暴露用户可理解的文案 + 内部 `code`；不把堆栈抛给用户。
- 可观测三件套：结构化日志（requestId）、指标（延迟 / 错误率 / QPS）、链路追踪。
- 关键路径埋点「成功 / 失败 / 耗时」，与埋点契约联动。

## 7. Reviewer 自检清单（写进 design/be §3 与代码评审 finding）

- [ ] 每个写接口标注幂等策略（天然键 / 幂等键 / 乐观锁 / 显式非幂等 + 理由）
- [ ] 入口校验完整（类型 / 范围 / 长度 / 非空 / 枚举）
- [ ] 无空 catch、无吞异常
- [ ] 下游调用有超时与失败 / 熔断处理
- [ ] 贫血模型？业务逻辑是否进了领域对象
- [ ] 有无无谓中转层（反过度分层）
- [ ] 优雅关闭 / 限流 / 背压是否覆盖
- [ ] 日志带 requestId、不打敏感
- [ ] 错误对外文案与对内 code 分离

> 任一未勾选即 `changes_requested`，finding 必须带 `path:line` 或可复核 Grep 模式（不得只写文件名）。
