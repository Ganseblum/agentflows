# 文档交付链（链契约）

当用户要求为某 feature **产出**文档集（需求提案 / 规格 / 技术方案 / 实施计划）、某 feature 先有文档尚无代码、**或在目标仓实施一个新 feature（代码工作随行）**时，走这条链：

```
接入（Init）→ 采集访谈 → 提案 → spec → 设计 → 计划 → 实施
```

每阶段有必需骨架（见 [`templates/feature/`](../templates/feature/README.md)），质量以「阶段产出是否齐全、可核验」为准，而不是以某条机器判据为准。

## 档位

- **轻量**：纯后端 / 无 UI 的批次，可只产出 proposal + 关键 spec 节；原型与视觉基线 N/A。
- **完整**：涉及用户可见界面或跨层契约的批次，走全阶段，且原型与视觉基线必产出。

偏离默认档位时，在批次记录写明理由。

## 各阶段必需骨架

| 阶段 | 位置 | 必需骨架 |
| --- | --- | --- |
| 接入 | Init | 目标仓接入节（[templates/hub/repo-rules.md](../templates/hub/repo-rules.md)）：硬判据 + 仓事实槽位 + begin/end 标记 |
| 提案 | `proposal/proposal.md` | 目标承接表、范围（含「不做」）、§1.4 范围穷举与存量面处置 |
| spec | `spec/{be,fe,qa}/*.md` | 后端契约、前端交互、QA 验收点（AC 表） |
| 设计 | `design/{be,fe,qa}/*.md` | 实体字段表（十列）、接口契约、异常矩阵 |
| 计划 | `plan/execution.md` | 任务看板（状态 / 依赖 / 证据回写）、回滚点顺序 |
| 实施 | 代码 + `plan/` 回写 | 已接受任务的状态与证据回写 |

## 三条只有主工作流才管的动作义务

1. 立项当天打 `agentflow 目标承接` 标记就必须同时写目标承接表，缺表即不完整；宣布任何一步「已完成」时，计划证据列必须留下可复核的载体之一（`/tmp` 里的东西不算）。
2. 产品语义的未决分支一律先交用户（一行问题带推荐，提问纪律见[契约](contracts.md)的「先问再假设」节）。
3. 目标仓有自己的模板体系就保留它，在其上施加质量标准：本契约是不存在模板体系或用户要求采用本方法时的下限，绝不替代一套行之有效的约定。

## 原型（涉及用户可见界面时）

可交互原型在 **spec 落盘前**产出并经用户逐项确认，需求评审在原型确认之后。判据见 [`templates/feature/prototype/README.md`](../templates/feature/prototype/README.md)。纯后端 / 无 UI 批次写 `N/A: 无 UI`。

## 埋点三处贯通

走文档交付链且涉及用户行为事件时，埋点在三处连成一线：`proposal` 的埋点决策 → `spec/fe` 的口径 → `design/fe` 的事件契约，验收落在 QA；三处互相矛盾、或任一处缺席，按缺口处理而不是可选装饰。事件手册不与档案链重复：沿链工作的项目，`design/fe` 的契约节就是它的事件手册；目标仓本就既有手册时以后者为准，契约节只登记本期的差异与出处。

## 视觉基线三档

UI 轨启用时，视觉基线分三档——A 复用本仓既有基线（默认）、B 跨项目移植（逐项列差异）、C 冷启动才新建「基线 v1」。形态与判据见 [`templates/feature/prototype/README.md`](../templates/feature/prototype/README.md) 与 [`references/repo-audit.md`](repo-audit.md)。
