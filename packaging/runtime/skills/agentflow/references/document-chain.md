# 文档交付链

功能交付先按风险与材料需要选择轻量或完整档位。行为、验收、证据、独立评审和授权要求对两档都成立；测试方法统一见[执行与验证](execution.md)。目标仓已有模板体系时保留其结构，并满足这里的质量要求；一条事实只维护一个正文真源。

**与目标仓模板体系的关系**：本契约是不存在模板体系、或用户要求采用本方法时的下限，绝不替代一套行之有效的约定。目标模板的结构性要求绝不凌驾于本契约的质量条款之上——当模板要求质量条款所禁止的内容（逐行裁决指针、逐行权威声明之类）时，保留模板骨架，按质量条款收敛冲突，并在文档头以一行「结构性裁剪声明」记录该裁剪。

## 使用时机

用于新增功能的需求、设计和实施材料，以及用户要求的文档交付物。纯问答、只读了解和单篇快速说明不强制建立 feature 目录；它们仍须遵守表达与证据纪律。作为执行证据的记录继续遵守自身契约，不重建文档链。

## 文档档位

用户明确要求整套需求提案、规格、设计和计划，或任务涉及公开/跨层契约、持久化、权限安全、共享流程时序/幂等或不可逆风险时，使用完整链。其余任务仅在下面六条均能给出具体依据时使用轻量档；任一为否、未知或待决即使用完整链，不能用标题上的“轻量”绕过实际风险。

| 轻量判据 | 要证明什么 |
| --- | --- |
| 目标与行为已确认 | 没有影响本次行为的未决产品语义 |
| 无跨层或公开契约变更 | 不改变其他层、仓库或公开调用者依赖的契约 |
| 无持久化或权限变更 | 不改变数据模型、迁移、认证或授权边界 |
| 无共享时序或不可逆变更 | 不改变共享流程、幂等语义或难以撤销的动作 |
| 单一部署单元且回退明确 | 影响可界定，并有具体恢复办法 |
| 验收可执行 | 目标与失败结果可由真实测试或明确人工步骤判断 |

轻量档在既有 feature 目录中只维护一份 `README.md`，精确声明 `文档档位：轻量` 和 `完整文档要求：否`（按用户真实请求判断，是/未知/未填均不得轻量），使用[轻量模板](../templates/feature/lightweight.md)。必需章节是 `## 适用性`（列为判据、结论、依据，六条全部为“是”且有具体依据）、`## 需求与验收`、`## 实施与证据`、`## 风险与恢复`。行为表写预期与验证，任务表列名为任务、代码落点、状态、证据，任务以 `T01` 等稳定ID开头；已完成行按本契约门8的C23证据载体要求留可复核来源，完成结论不能只靠勾选。

轻量减少材料重复，不省略独立评审、有效失败、受影响回归、必需 CI、授权或原始证据。范围扩大或出现上述风险时先升为完整链，再继续依赖实现；保留原先事实与证据，不把事后补文档说成事前已完成设计。

降档判据只有上面的轻量判据表一处（六条全「是」且有具体依据才可轻量，任一否/未知/待决即完整档），不另设速查表。

降档理由逐条写进 feature README 的适用性表；C26 由 linter 机器核验，口头降档无效。

完整档遵循 接入 → 采集访谈 → proposal → spec → design → plan → 实施，后文的阶段骨架、设计形态与阶段门针对完整档。历史批次不回改，新档位不追溯删改已有材料。

## 目录布局（目标仓，无约定时）

两种形态，在 Init 时与 owner 确认；**无既有约定时默认推荐①**。两种之外**不得自创落点**
（例如 `records/plans/`）；落点结论写入目标仓 `AGENTS.md` 的接入约定小节。

- **① 文档枢纽仓（默认推荐）** ——项目内（或独立）的文档/元信息中枢（`<project>-workflow-ai`
  模式；骨架见 [`../templates/hub/`](../templates/hub/README.md)）。各阶段位于枢纽根目录下，
  每个 feature 一个目录，与缺陷流、发布记录并列：

```text
features/feature-<date>-<topic>/
  README.md               single entry: meta + progress board with stage gates
  proposal/proposal.md    why: background, goals, scope (incl. NOT doing), principles, open questions
  spec/{be,fe,qa}/        what it must finally behave like (+ re-audit checklist of the proposal)
  design/{be,fe,qa}/      how: decision table, challenges, architecture, impact assessment, verification
  plan/execution.md       execution contract (single file; follow the target repo's plan convention if any)
issues/                   defects and items (numbered, board README, archive/)
releases/                 release records (todo + pending-test)
index.md                  the single document index
```

可选层（按需启用）：`workflow/` 项目级活规则、`templates/` 复制骨架、
`user/` 产品使用文档、`api/` 接口规范。

- **② 普通业务仓**（无独立枢纽）：文档链留在仓库内部——默认
  `docs/features/feature-<slug>/`，阶段骨架相同。

每个 feature 一个目录。README 是唯一入口，承载带阶段门的进度板与一张**段落映射表**——复选框
只在附有文档链接时才推进，跳过项写 `N/A: reason`，评审门只由独立 reviewer 勾选。

**段落映射豁免。** 段落映射表逐段声明各段落（proposal / spec / design / plan）的落点：
某段落的落点非空且不是「—」时，该段目录可以缺失（内容由落点指向的活文档承载，不重复造册）；
落点为空或是「—」时，该段目录必须存在。这是完整链复用已有活文档的方式——**段落映射表声明
落点的段落可缺失，其余段落齐全**，与单文件轻量档不是同一种结构。落点指向本 feature 目录之外的活文档时，在表里写明对方路径。

文档链内的文件命名：每个角色轨在两个阶段各是一个目录，彼此镜像——`spec/be/backend.md` ↔
`design/be/backend.md`，`spec/fe/frontend.md` ↔ `design/fe/frontend.md`，
`spec/qa/acceptance.md` ↔ `design/qa/testing.md`，`spec/ui/visual.md` ↔
`design/ui/visual.md`（`design/be/` 和 `design/fe/` 作为目录是 linter 的硬性要求；其余与
它们镜像，因此一个角色的读取范围恰为每个阶段一个目录）。单文档阶段保留一个文件：
`proposal/proposal.md`、`plan/execution.md`。`be/be.md` 双写是命名缺陷——在收口通读之前修掉，
不要留到评审里。

文件名口径（2026-10-23 补）：linter 的 C1 只判「该阶段目录里有没有真实文档」，**不判文件名**——`proposal/prd.md` 这类旧命名不会被门抓住，只能靠这里的约定与评审。插件仓批次一律用契约名（`proposal/proposal.md`、`spec/<角色>/<镜像名>.md`、`plan/<plan_id>.md`，其中 plan 的文件名由计划契约机器强制）；目标仓批次使用 `plan/execution.md`（见下文 plan 节），spec 与 proposal 阶段文件名同上；存量批次按「历史不回改」保留原名，接入时先跑基线再决定要不要改名。

## 阶段骨架

带**固定标题字面量**的填写式模板位于
[`../templates/README.md`](../templates/README.md)——骨架按角色目录组织（`spec/be/backend.md`
与 `design/be/backend.md` 等互为镜像；单文档阶段 `proposal/proposal.md`、`plan/execution.md`），
清单列在其 README；枢纽仓骨架见 [`../templates/hub/`](../templates/hub/README.md)。
复制模板，填写占位符，不得重命名或删减章节（记录契约的固定标题做法，应用于文档链）。
允许增加领域专属章节；模板核心不是可选项。文档链若在 README 中用标记行
「本 feature 文档链由 agentflow 文档链方法生成（<日期>）」声明自己，即选择接受 linter 的
结构检查（C11：固定的 design 标题必须齐备）。阶段文档缺少章节即不完整，无内容的章节写
"N/A: reason"。

- **proposal**: 文档信息（原文出处与版本）· 背景与目标（含本期不包含）· 产品定位与核心
  原则 · 用户与场景 · 范围决策表（含"明确不做"）· 待冻结问题台账（每项 owner + 关闭条件）·
  **成功指标与可观测性（含埋点决策：新增 / 复用既有事件 / N/A + 理由，粗粒度事件与要收集的
  信息，不写事件名与参数）**。原始需求文本**逐字保留**并标注版本，改写发生在后续层，
  不在原文上。
- **spec**: §0 反审 checklist（对照 proposal 逐节挑缺口，阻塞项全关才能进 design）· 行为
  条目（陈述 → 验收口径 → 标尺；spec/be 也可以按其模板把验收口径展开为 §5 验收补充的
  「验收点 → 可测细化 → 判定方式」形态，三列语义等价）· 埋点口径（由 proposal 决策收敛的可验收草案：
  业务动作、触发点、触发时机、要收集的信息、复用与不埋声明）。验收口径必须可判定；"标尺"指会失败的
  具体检查（测试、脚本、评审门），写不出标尺的条目诚实标注。
- **spec 的定位（吸收 ai-workflow-meta，2026-10-23）**：spec 是**需求事实唯一权威**——各角色
  轨（`spec/be`、`spec/fe`、`spec/qa`、`spec/ui`）只可引用或展开 proposal 与本文，不得另行新增
  业务事实；发现新业务事实时须经需求方确认并回写 proposal 与 spec。design 只能新增实现决策与代码勘察事实，不得新增业务语义。**所有待确认 / 待冻结问题统一登记到
  `spec/checklist.md`**（编号 `Q-01`、`Q-02`…；存量批次的 `OQ-` 旧编号仍被 linter 接受），不在
  各 spec 文件里另开一套问题表；`spec/checklist.md` 里带「阻塞」且仍「未确认」的行未关闭前，不得生成
  design（对应 C3 反审门）。**拍板口的标记是开关，不是注释**（2026-10-29）：目标仓创建 `docs/PENDING-DECISIONS.md` 时必须把标记行独立成行，逐字写法为 `agentflow 决策记录`（该行整行去掉首尾空白与「> 」前缀后必须恰好等于这个词——[decision-record 模板](../templates/decision/decision-record.md)开头有意**不写**它，写了模板自身会被 C16 当成真记录来判）。摘掉它不会判红，只会让 C16/C17 失去对象。**与拍板口的分工**（2026-10-29）：本文件的问题表是运行时台账，`docs/PENDING-DECISIONS.md` 才是唯一需要用户逐条回复的清单——凡属主为用户且未关闭的行，该行必须写明拍板口的条目编号；打 `agentflow 决策归属` 标记的批次由 C18 家族核验这一点，缺编号即判红。模板见 `skills/agentflow/templates/feature/spec/checklist.md`。
- **design**: 0. 先说结论（问题→结论速览表）· 关键决策速览（编号 D1..Dn：结论 + 一句话
  理由 + 详见交叉引用）· 技术挑战（优先级 + 应对）· 架构图（每张图只回答一个问题）·
  **主链路 S 步骤表**（每步：调用方→承接方 / 动作输入输出 / 状态数据变化 / 失败处理 /
  观测点）· 组件负责/**不负责**表 · 核心算法（判断顺序 + 伪代码 + 代码职责落点 + 不变式）·
  **存储设计：新增表必须给字段级 DDL**（每个字段的类型/空性/默认值/注释/索引，迁移文件
  命名与回滚方式）· 详细接口设计（清单表 + 每接口请求/响应字段与错误 + 运行逻辑 +
  错误幂等状态约束表）· 验证与灰度 · 失败模式与回滚 · **影响面评估**（L0–L3 定级 +
  变更兼容性分类 + 影响面 checklist + 消费方清单与结论）·
  监控告警（编号 + 阈值）与问题定位预案（现象→首查→日志→原因→动作）· 评审前自检
  checklist。推翻既有决策时留翻案记录（改了什么结论、原前提为何不成立、何时定稿）。
- **design（前端）**: 技术挑战表 · 分层职责表（视图/hooks/store 各自边界）·
  **文件落点表**（每个新增/修改文件的精确路径，路径未核实的挂显式核实项）· **S 步骤表**
  （每步：视图层状态 / hooks 编排 / store 读写 / 服务端调用 / 成功异常去向 / 观测点）·
  组件复用边界与 **data-testid 清单**（QA 可测性）· 核心逻辑带语言级伪代码 ·
  **类型/接口契约**（请求响应的 TS/interface 定义）· **字段映射处理表**（服务端字段 →
  前端模型 → UI 展示 → 可空默认 → 非法枚举处理）· 错误重试并发表 · Mock/联调/接口未就绪
  方案 · **埋点事件契约**（事件名/类型/触发点与代码落点/触发时机与去重/逐事件字段级参数表/
  隐私与失败降级/每个事件一条会失败的验证方式）· 评审前自检。
- **design（UI 轨，可选扩展）**: 目标仓有独立设计流（设计稿评审、品牌/多站点规范）时，在
  spec 与 design 各加一份 ui 文档（`spec/ui` + `design/ui`，骨架见模板），与 fe 同构但只装
  视觉/交互/可达性内容——**视觉来源与基线**（三档：A 复用本仓既有基线 / B 跨项目移植 /
  C 冷启动新建基线，附组件库与版本、主题机制与接入点、token 源文件、字体图标资产的
  `path:line` 或链接，以及相对基线的差异项）、布局断点、token 纪律、组件视觉状态表、
  线框真源声明、用户迭代变更记录；proposal 保持单一不分角色，ui 分歧从 spec/ui 开始。
  **主题样式必须来自既有项目**：A 档默认，B 档逐项列差异、不整包搬，C 档只在确无可参照
  项目时使用，且第一份 design/ui 的变更记录就是「建立基线 v1」，之后按 A 复用；凭空写色值、
  截图取色、按感觉选组件库都是缺陷，不是风格差异。linter 对 ui 轨仅做存在性与
  围栏/时效性检查（C1/C3/C10/C12–C14 会扫到 ui 文件），不做形态/密度检查（C4–C8/C11），
  ui 轨的待核实项也不进 C9 闭合——其质量靠 §0 反审 checklist、与 spec/fe 的真源声明
  （引用不复制）和 README 门禁记录兜底；启用与否在 README 元信息里声明一行。
- **图与形态要求的适用条件（C4/C8）**: 某个角色轨的 `spec/<角色>/` 或 `design/<角色>/` 任一
  含 `.md` 文档时，该角色的 `design/<角色>/` 必须满足地图形态要求——`design/be/` 必须满足 C4
  （含失败分支的时序图 + 架构/流程 flowchart + ER 图或状态图 + 字段级 API 契约表），
  `design/fe/` 必须满足 C7/C8（工程线框 + flowchart / sequenceDiagram / stateDiagram + 成功与
  失败双覆盖的异常矩阵）。只声明了目录、里面没有任何文档的轨不触发要求（例如只做后端、前端轨
  不启用的批次），但一旦该轨写了第一份文档，形态要求随之生效。UI 轨是例外，按上一条的宽口径处理。
- **产品原型与线框**: 新增或改动用户可见页面、布局、样式或交互时，在需求访谈中识别受影响页面
  与视觉待决项，并在设计冻结、计划和实现之前准备可供用户确认的预览。形态 A/B 的判据与存放规则、
  入口页写法、依赖闭包、真源声明、可点性与假数据自检、`N/A` 条件的**唯一正文**见
  [原型模板 README](../templates/feature/prototype/README.md)（`prototype/index.html` 是每个
  feature 的统一原型入口，骨架同目录）。此处只留链内的硬口径：
  - 形态选择只有一条规则：**目标仓已维护原型库 → 必须形态 A；确无原型库 → 形态 B**，不设第三种；
    **有 UI 改动的批次不得用 `N/A: 复用 <页面> 既有结构`**（它只适用于完全复用且无界面改动的批次）。
  - `README` 元信息登记原型形态（A 仓库级原型库 / B 批次自建）、统一路径（形态 A 另记正文
    `path@revision`，跨仓写 `<repo>@<revision>:<path>`）与沿用来源；无 UI 的 feature 写 `N/A: 无用户界面`。
  - 用户确认人、结论与确认时的原型修订写入 design 变更记录；尚未确认或用户要求修改时，
    不冻结设计、不进入计划或实现。原型是需求对齐、QA 与后续实现的共同依据；产品结论写回
    提案或 spec，原型按统一路径保留，不在结论落账后删除。
  - **原型要能点**——这条靠人工逐页点击判定，插件没有对应的机器门，脚本扫描只能当线索
    （实测初筛 102 个问题页 / 1403 个死按钮、真实缺口 8 页；单位不同不能直接算误报率），
    不能拿扫描通过代替走查。
- **plan**：目标仓已有计划契约时沿用；没有时，目标仓使用 `plan/execution.md` 模板。本插件仓库的批次记录使用 `plan/<plan_id>.md` 混合形态（信封 + 进度总览 + 带状态/证据回写的任务表 + 接口与共享机制 + 验证命令），计划文件名必须等于 `plan_id`。**计划必须含
  `## 分支策略` 节（H2，固定标题字面量）**：逐仓声明基线、开发分支与分支纪律（开工前查分支、
  改动只落开发分支、合并与推送各自需授权），落地既有代码时附落点校对表（`file:line`）。缺这
  一节的计划不完整，linter 的 C9 判它失败。
- **plan 的出处列与单一权威（吸收 ai-workflow-meta，2026-10-23）**：三件事，都是缺陷而不是风格
  问题——① **每个取值都要写出处**：验证命令与启服清单的「命令依据 / 依据」列只能取四种写法之一
  （`标准`、`<仓内文件>#<键路径>`、`人工确认：<理由>`、`待 Coding：<任务编号>`），裸「待补充」
  不合格；`待 Coding：<任务号>` 引用的任务必须真实存在且落在同一仓，计划评审时可未完成；首次执行对应命令前须完成并回写真实命令与证据。健康检查写成 URL
  路径时该路由必须在仓内真实存在，否则写「端口监听」；前端域名/hosts 只能取自目标仓 README，
  不许自己填 IP 或 `localhost`。② **仓库基线表是唯一权威**：计划的「分支策略」节基线表是全链唯一一份基线表，
  feature README 只作指针，不维护第二份；**基线提交只是起点、不是发布版本**——实施仓发布的是
  任务 ☑ 行证据指向的提交。③ **联调/发布目标表唯一权威**：环境变量、配置文件、会话里的临时地址
  都不能代替它。计划还要有一节**残余风险**（无风险时保留表头写「无」），每条须能写出责任人、
  触发信号与处置办法——写不出即该条不完整。
- **影响面按等级升高的评审门（吸收 ai-workflow-meta，2026-10-23）**：design/be §1.6 定级
  L0–L3 后，放行条件是分级的——L0/L1 方案自洽即可；L2 要求强依赖消费方已确认、缓解可执行；
  L3 须多方 sign-off 且**未通过不得进入 plan**。同时**间接下游**（报表、T+1 统计、离线任务、
  搜索索引、第三方）是强制覆盖类，只写「上下游」一个词视为未完成；接口仍返回 HTTP 200 但字段
  类型/语义/默认行为已变的，按潜在或静默破坏性处理。

## 采集访谈（proposal 阶段）

proposal 分多轮采集，而不是一次问完。把待决事项建模为一棵决策树：每个决策分叉出挂在它
下面的决策。**前沿**是所有前置条件已经确定的决策。一轮问完整个前沿——编号列出，每项带一个
建议答案和推荐它的理由，措辞使回答「是」即接受该建议——然后等待回答齐了再计算下一个前沿。
依赖本轮仍未关闭的决策的问题属于后续轮次，不属于本轮。

事实是作者的职责，绝不是 owner 的：凡是能在仓库、环境或平台文档里查到的，都去查而不是去
问；一次未解决的查询只阻塞它下游的问题——继续问前沿的其余部分。决策属于 owner：每个都交给
他们并等待；绝不自行填入一个并记为已关闭。只有产品 owner 能回答的开放问题，绝不作为假设
混进 spec。视觉基线同属这一类事实：组件库、主题机制、token 源文件、参照页面都在仓库或
既有站点里，作者查出来给 `path:line`；只有「本仓没有、要不要照隔壁项目移植」或「冷启动
选哪套」才是 owner 的决策。

前沿为空时访谈才算完成——每条分支都访问过、没有任何静默假设——并且 owner 确认了共同理解；
只有到这时 proposal 才冻结。没有问题数量上限：边界是前沿，不是一个数字。当前沿连续多轮
仍在扩张时，说明范围太大——拆分 feature，而不是压缩轮次。

**问题格式。** 一行问出问题，然后最多三个选项——通常为现状、最廉价的可行路径与建议项——
每个附一行适用条件与代价，绝不写成利弊论述。标出建议项，并写明它在什么条件下是错误选择；
第四个选项只在确实独立时才出现；当不存在工程偏好时，建议项要明说这一点
（「无工程差异；按产品偏好选择」），而不是消失。详细比较——合规引用、失败模式、被否方案——
属于 design 的决策表；问题指向它，而不是复述它。每个问题都接受自由格式回答，每轮声明一次：
选一个；选一个并修改它；或都不选——那会重开该分支，而不是增加选项。选项字母是轮内局部
标签——台账和每一份下游文档都用白话（代号）写出结论。

**质疑答案。** 当一个答案与已冻结的原文、既有术语表或 spec 术语、或仓库代码的实际行为
相冲突时，把冲突放回同一轮（「文档写 X，你说 Y，哪个为准」）并记录哪一个胜出及为什么。
与已冻结文本相矛盾却未被标记的答案，是缺陷，不是备注。

**谈不出来的问题。** 谈话无法定夺的问题——应该长什么样、应该怎么感觉——不再反复去问：
构建回答它的最廉价一次性产物（上面的线框/原型路径），在那里回答它，并把结论记在问题旁；
产物留在那条路径存放它的地方，作为结论的证据。

**台账回写。** 每个答案都落进 proposal 的 待冻结问题台账，成为一行：关闭条件可判定
（「做了」不是关闭条件）、带日期、注明由谁确认。暂时无法说清的问题进入「未成型」列表并
注明被什么阻塞，随着前沿推进升级为一行或一条 范围决策表 条目——它绝不被丢弃，也绝不靠
猜测变清晰。

## 门

1. **Spec 反审门** ——spec 的 §0 checklist 登记对照 proposal 发现的每个缺口；阻塞项通过
   修正 proposal、被某条 spec 条目吸收、或记入台账来关闭。属于**产品决策**的阻塞项（必须由
   需求 owner 抉择的语义，例如状态冲突或首次触发时机未定义）作为带推荐默认值的明确问题
   交给 owner——spec 作者绝不单方面填入并宣布关闭——按上面的采集访谈提出（每轮问完整个
   前沿、事实去查而非去问、答案冲突在到达的那一轮裁决）。存在未关闭的阻塞项时，不得开始
   design 工作——唯一的过渡形态是「建议值草案」：阻塞项已登记台账并带建议值时，下游的 design / plan 阶段可
   先行起草为草案（状态行标注「草案：随建议值」；登记待答的阻塞行状态字建议用 ◐），但不得标冻结、
   不得过本门、不得开工实施；
   owner 关闭阻塞项后草案转正式。「建议值草案」必须在 proposal 的**待冻结问题台账**里登记一项
   `owner + 关闭条件 + 建议值`（否则下游没有可承接的草案来源）；台账项见 proposal 形态节的
   「待冻结问题台账」必含字段——这是该过渡形态唯一的记录入口，未在台账落项的草案视为越权起草。
2. **需求评审门** ——独立的 reviewer 对冻结的候选运行文档评审模式（需求提案与 spec）。
   阻塞性发现在 design 冻结前关闭。
3. **Design 评审门** ——独立的 reviewer 运行 design 模式。批准后 design 冻结；此后的改动是
   带翻案说明的设计变更记录，而不是静默编辑。
4. **Plan 前置条件** ——plan 引用已冻结的 design 结论；当被引用的决策后来被推翻时，plan 行
   随附说明予以更正。
5. **Design 承载契约** ——design 阶段包含字段级 API 契约（方法、路径、请求/响应字段、
   每次调用的错误语义）以及至少一张覆盖主链路**并含其失败分支**的时序图；把所有契约都
   推迟到"评审后"的 design 不完整。因代码未读而受阻的事实进入一份显式的待核实清单，注明
   每项阻塞什么——它们推迟的是精度，绝不是契约的存在。
6. **链路收口通读（chain-closure pass）** — 本动作的唯一定义处：在文档链最后一份文档落地
   之后、宣布完成之前，由一名**非作者**从头到尾通读整条链并检查（它是链尾门，不属 plan
   阶段；plan 阶段的产出门是第 4 条「Plan 前置条件」）：
   ① 时效性引用 — 某句话声称某目标「待产出 / 尚未产出 / 待补充 / 待生成」，而它指向的目标
   已经存在，即为一条发现；删掉该断言或改指它处；
   ② 流程角色词 — 受会话绑定的流程词（supervisor, 评审人缩写, TD, 本轮, 本次会话 …）绝不出现在
   正式文档中；替换为具体角色名或删除；
   ③ 会话材料落仓 — 正式文档引用的会话材料（决策笔记、勘察报告）在引用之前已归档进 feature
   目录；否则删除引用，使正文自足；
   ④ ①② 中可机器检查的部分连同 代号裸用 形态由
   `tools/lab/doc_chain.py` 承载——运行 `python3 tools/lab/doc_chain.py <feature-dir>`
   （C12 时效性引用, C13 会话角色词, C14 代号裸用）并修复或对每条发现显式放行；独立会话
   交付物经 `python3 tools/lab/doc_chain.py --file <路径>` 走同样的文本形态检查。自 0.16.0
   起该检查器随插件交付、装在插件根 `tools/lab/`；在目标仓工作时从插件根调用并带
   `--root <目标仓根>`，否则落点按插件仓根解析。C13 的
   **作用域是交付物**（链阶段文档与会话交付物）：方法的自述面（`docs/product/**`、
   `skills/**`、`agents/**`）与评审记录（`reviews/**`）里这些词是被定义的术语或被列举的
   例词（reviewer 档案本身就列举了它禁止的词），机器分不清「指称」与「提及」，故整体豁免，
   交给条款文本与评审逐处裁量——同 C15 的取舍。

   门 6 曾是一条只有文本定义、零机器判据的死条款（四批次 / 六计划 / 43 episode 零命中，
   2026-10-26 审计 G06）。为了让"收口"可复核，它有了 opt-in 的机器载体 **C25**：批次 README
   打上 `agentflow 链路收口` 标记，即承诺已完成通读；标记后，链内任一阶段文档不得仍残留
   「待产出 / 尚未产出 / 待补充 / 待生成」且指向已存在目标的时效断言——那是门 6 本要抓的
   腐烂，且正是 C12 在别处查的形态（C25 复用 C12 的同一定义，二者不会各说各话）。未打标文档
   不受 C25 约束（门 6 的文本定义仍管它，但 C25 不打标不触发）；判定与夹具在
   `tools/lab/doc_chain.py`（C25，自测 103–105）。

7. **评审落地与验收用语** ——每一轮评审的结论都以记录文件落在批次的 `reviews/`（或本仓
   评审其它仓库文档时的 `reviews/<project>-<feature-slug>/`）；只存在于 plan 散文里的结论是
   缺陷。发布带一份 待验证清单（pending-test），把"代码已落地"与"已验证"分开；没有验证
   证据就把 已实现 标成 已验证 是缺陷。

8. **目标承接与证据在场** ——批次 README 打上 `agentflow 目标承接` 标记后，必须同时给出目标承接表
   （列：目标 / proposal 出处 / spec 承接 / plan 任务 / 状态）。**打标只对新批次生效**（2026-10-29
   拍板 B）：立项时把「打标并建承接表」写进立项动作清单；存量批次不回改、不补打标，其历史状态按
   「历史不回改」保留。C23 证据在场对全部批次生效，不随本条的适用范围缩小。检查是双向的：提案里声明的每个目标都要
   进表，表里引用的模块号、验收点与任务号都要在 spec 与计划看板里真实存在，计划里已 ☑ 或 ⚠ 的任务行
   必须被某一行承接；表的状态列与看板聚合一致（看板还在 ☐ 而表写已完成，当天即红）。证据义务不属于
   标记范围：计划中每个 ☑ 已完成的行，证据列都要含可复核载体之一——仓内存在的路径、
   `仓库@修订:路径`、git 能解析的提交号，或 `N/A: 理由`；只指向 `/tmp` 的散失证据不合格。
   判据实现与夹具在 `tools/lab/doc_chain.py`（C22、C23），目录模式与 `--repo` 模式共用同一实现。

9. **HISTORY 单账本模式（C24，吸收 ai-workflow-meta，2026-10-23，纯增量）** ——当一个 feature 目录
   **没有 `README.md` 但有 `HISTORY.md`** 时，进入单账本模式：`HISTORY.md` 作为该链的唯一账本，承载
   C2 入口门禁（需求评审 / 技术方案评审）与 C22 目标承接标记 + 承接表（当启用目标承接时，后者改从
   `HISTORY.md` 读取）。**纯增量、不回改存量批次**：只要 `README.md` 存在，就仍是 README 模式，规则
   与改动前完全一致；`HISTORY.md` 与 `README.md` 同时存在时以 README 为准，HISTORY.md 只当作普通阶段
   文档，不接管门禁。这吸收了 ai-workflow-meta「当前节点只看 HISTORY、不另写一套进度」的做法，但保留
   本仓独立的 supervisor/reviewer 评审门（不吸收它「单角色 Maker 跟到底」的设定）。判定与夹具在
   `tools/lab/doc_chain.py`（C24，自测 99–102）。注意：**单账本模式没有豁免入口**——C19 的
   「qa 不适用 / 无 qa 轨」豁免只认 README 里的声明，单账本没有 README 可声明，因此 C19 必红。
   单账本批次若确实无 qa 轨，唯一的出路是改回 README 模式（补一份 README 或放弃 HISTORY 单账本），
   或补一份 `spec/qa/` 验收文档；在 `HISTORY.md` 里写「范围依据」不能豁免 C19。

10. **跨批次决策依赖（decision_deps，D8，2026-10-30，机器强制于 `tools/lab/decisions.py`）**
   ——下游文档若复述或依赖一条跨批次决策，在其 frontmatter 声明 `decision_deps`，不再用散文追述
   「该决策是否还成立」。形态为行内列表，每个条目是一个 token：
   `DEC-YYYY-NNN#rN`（钉定到具体修订）/ `DEC-YYYY-NNN#invariant=<不变式文本>`（只钉不变式，
   正文改具体能力而不改约束时仍为绿）/ 可附 `#stale_reason=<理由>#review_date=<YYYY-MM-DD>`
   （受影响但获准滞后；复核日期须为今日或之后，否则不生效）。机器规则（G7-AC-01..05）：
   钉定被撤回的修订 → 红；钉定标记为 `等价` 的早版 → 绿；钉定不变式且仍出现在正文 → 绿；
   只写豁免不写理由 → 红。反向索引由 `decisions.py check` 算出来，不在任何文档手写。
   2026-10-30 补充的机器规则：终态（`superseded` / `withdrawn` / `deferred`）即使钉当前修订或不变式也红，
   除非同时登记 `stale_reason` + 未来 `review_date`；空 `#invariant=` 红；未知终态词红；台账表头必须含
   `DEC编号 / 修订 / 撤回 / 等价 / 终态` 五列；`docs/decisions/issued.txt` 是已发放编号的只追加见证，
   台账里的每个编号必须出现在其中，issued 里的编号不得从台账消失。
   **立账门槛**：一条决策只有在满足以下任一条件时才立 `DEC-` 账——① 有第二个文档复述它（横向消费者）；
   ② 它可能被推翻（时间风险）。一次性、无下游引用的决定不立账，防止重演记录面膨胀。台账本体在
   `docs/PENDING-DECISIONS.md`，规则为「只追加、永不移出」，未决视图由 `decisions.py view` 生成。

文档链的机器检查口径（结构 C1–C26、运行命令、跨仓运行与既有仓基线）、质量密度下限与逐文档质量标准全部在

## 角色接线

- Supervisor 通过运行采集访谈来采集 proposal（围绕决策前沿推进多轮；事实由作者解决，决策
  交给 owner；答案冲突在到达的那一轮浮出并裁决），并逐字保留原文。
- spec 与 design 可由 Supervisor 起草（单层文档工作），或委派给 `plan-architect`（plan 层
  只写，绝不批准）；跨层 feature 先由 `technical-director` 的接口决策界定边界。
- 独立的 `reviewer` 拥有全部三道评审门，使用本仓的文档评审模式并引用被评审的文本。
- 每轮的证据：目标仓拥有文档时落在目标仓；本仓是第二遍评审者时，经评审桥落入 `reviews/`。
- **简报卫生**：委派简报位于文档措辞的上游，遵循同一表达纪律——不得出现受会话绑定的流程词
  （supervisor / TD / 本轮 / 本次会话 …）；简报引用的任何决策或事实材料，都以已归档在
  feature 目录内的路径给出（先归档，后引用），绝不用临时路径。

## 待拍板提案：默认档改轻（Q-02）

> **状态：提案，未生效。** 本节的任何结论在用户拍板前不得作为降档依据；现行判据仍是上文
> 「文档档位」的六条轻量判据。拍板入口见 `docs/PENDING-DECISIONS.md`，实施另立批次。

**问题。** 现行规则是「默认完整链，六条全是为『是』才可轻量」，实际效果是默认档落在最重的一侧：
本仓 11 个批次里 9 个走完整链，记录面基线 23,030 行。而完整链的多数材料（proposal / spec /
design 各角色分册）在低风险改动上并不产生可判定的验收增益——它们主要增加评审阅读量。

**提案。** 把默认翻转：默认「一页提案 + 验收判据 + 计划看板」，完整链改为**按需启用的加强档**。
现有六条判据不废弃，改作**升级触发条件**——任一命中即必须升到完整链，其余走默认档。

三个选项与各自后果：

| 选项 | 做法 | 做的后果 | 不做的后果 |
| --- | --- | --- | --- |
| A 保持现状 | 默认完整链，六条全「是」才降档 | 材料最全、评审最贵；低风险改动持续付全额成本 | 记录面继续膨胀，评审注意力被稀释 |
| B 翻转默认（推荐） | 默认一页提案 + 验收判据 + 计划看板；六条判据转为升级触发 | 低风险改动成本大幅下降；需同步改 C26 判据（判据方向从「能否降档」改为「是否必须升档」），属门变更 | 不翻转则本项收益为零，记录面行数目标（≤ 2.5 产出比）无法达成 |
| C 只并阶段 | 保留五段骨架，允许 spec 与 design 在低风险时合并成一册 | 改动最小、无需动 C26；但材料总量下降有限 | 省下的主要是分册开销，提案与计划仍各自成册 |

**推荐 B。** 理由：A 的成本已被实测（23,030 行），C 的收益不足以支撑一次契约变更。B 的关键
前置是 C26 判据必须同批改写——只改散文不改判据，等于让门继续按旧口径判新规则，属「声明了
却不被校验」的已知缺陷形态。

**落地前置（拍板后另批执行）。** ① 改本文件「文档档位」节与 C26 判据；② 改
`templates/feature/lightweight.md` 的必需章节；③ 存量批次不回改（沿用历史不回改原则）；
④ 跑一轮 `doc_chain_live` 确认存量文档不因判据方向翻转而新红。
