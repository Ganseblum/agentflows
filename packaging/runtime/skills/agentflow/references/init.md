# 首次接入（Init）执行细则

> **加载者**：`skills/agentflow/SKILL.md` 首次接入节（Init）；执行体是 `scripts/init_workspace.py`（脚本先行），本文件是它之后的人工步骤。接一个新项目时读。

> 本文件是 Init 的**操作细则**单点。SKILL.md 只留三行指针——Init 不属于「每次会话都要在场」的内容，它是「接一个新项目时才读」的一次性流程。
> 判据与规则正文：`templates/hub/repo-rules.md`（目标仓接入节模板）、`templates/engineering/baseline.md`（工程基线模板）、`templates/host/global-rules.md`（宿主级规则正文）。

在一个尚未接入 Agentflow 的项目里第一次工作时（目标仓没有相关约定、记录结构或检查命令），先做一次轻量接入，再走正常流程。

## 0. 脚本先行，AI 只填项目事实

先跑 `python3 <skill>/scripts/init_workspace.py <目标仓根> --dry-run`——它扫描目标仓并打印
`[create]/[refresh]/[append]/[skip]/[conflict]` 计划（AGENTS.md 托管块、`.cursor/rules/agentflow.mdc`、
`CLAUDE.md` 指针、copilot 入口、`.agentflow/standards/` 工程内容底线）。

用户确认计划后去掉 `--dry-run` 实跑；宿主既有文件只追加托管块或跳过，**绝不覆盖**，
冲突项与用户逐条裁决。随后 AI 只做脚本做不了的事：探测项目事实（技术栈 / 目录 / 检查命令——
**探测命令必须带超时**，禁止把可能长跑的命令丢进后台再靠 TaskStop 收尾）并回填工程基线。

只有脚本报冲突或用户明确要求时，才退回「AI 逐文件生成」，并在接入报告里写明退回原因。

收尾校验：`python3 <skill>/scripts/init_workspace.py <目标仓根> --check`（比对 manifest 与托管块区段哈希）。

## 1. 与用户确认六项

有默认值的按默认走、**一次集中确认差异**。六项：

1. **交付语言与读者**——默认中文；面向用户时白话优先。
2. **术语约定**——用户反复纠正过的词、内部自造词的替代说法（例如「台账」→「清单 / 记录」）。
3. **分支与合并纪律**——前缀实例与禁止方向。
4. **仓库自带的检查命令**——构建 / 测试 / lint 的确切命令。
5. **文档与记录落点**——目标仓已有自己的文档体系则用其体系；否则在链契约的两种形态中二选一
   （无既有约定时默认推荐①文档枢纽仓 `<repo>/<name>-workflow-ai/`：`features/` + `issues/` +
   `releases/` + `index.md`，骨架见 [hub 模板](../templates/hub/README.md)）。
   **不得自创第三种落点**（例如 `records/plans/`）。
6. **工程基线**——目标仓已有工程规范时登记其入口路径；没有时与用户确认后用
   [工程基线模板](../templates/engineering/baseline.md) 落一份最小基线（技术栈与运行环境、
   禁止的平行方案、目录与命名、新增模块必做清单、测试栈与运行方式、质量门顺序、配置与边界）。
   工程基线**只收目标仓的实测事实**：查不到写缺口，不按通用默认推断，也不搬运其它项目的
   业务数值与部署流程。

## 2. 写「Agentflow 接入约定」小节

按[目标仓接入节模板](../templates/hub/repo-rules.md)写——模板是**必产出载体**，不是可选参考：
固定块写死硬判据，槽位由第 1 步的六问填充，整节用模板规定的 begin / end 注释标记包住，
重跑只替换标记内内容。

经用户确认后追加进目标仓的 `AGENTS.md`（或用户指定的等效规则文件）；没有该文件时先征得同意再创建；
选枢纽仓形态时，同时建立枢纽骨架（README、index、features、issues、releases）。

**小节必须包含三句可执行的门条款**——只写「走主流程」而不写「跑门」，接入等于没接
（2026-10-21 跨仓复盘实证：接入约定只写了主流程的仓里，三个实际干活的会话门禁调用为零）：

- 新批次建好当天，运行一次文档链检查器（已随插件交付，装在插件根 `tools/lab/` 下；
  引入版本见 `CHANGELOG.md`，不在文档里写版本号）：
  在目标仓根目录运行 `python3 <插件根>/tools/lab/doc_chain.py --root <目标仓根> <feature-dir>`——
  **位置参数相对当前目录解析**（不相对 `--root`），`--root` 只决定落点与路径核验的基准；
  不带 `--root` 时落点按插件仓根解析；
- 宣布任何批次完成前，对该仓全部批次跑一遍 linter 并贴原始输出；
- 输出里出现 finding 不许口头绕过——要么修复，要么显式登记放行。

小节还要写明**工程基线入口**：目标仓已有规范写其路径，本次落下写新文件路径。它是接入要件之一，
不改变上面三道门的口径；工程师在实现前读它，基线与任务冲突或缺失时按「先问再假设」停下，
不按通用默认推进。

写入后按模板末尾的确认单核对：七节都有值或 `N/A: 理由`，三句门齐全，分支前缀与记录编号形态
是本仓实测事实而不是通用默认；**缺项在接入报告里如实列出，不写成已完成**。

## 3. 接入已有批次的目标仓

先做一次基线对齐再立项：

1. 对既有批次全量跑一遍 linter，把「**真缺口**」与「**口径噪声**」分开——常见噪声两类：
   代码落点按批次目录或枢纽仓根书写而解析基准是目标仓根（先在批次 README 元信息声明
   「落点基准」再跑）、裸文件名（无目录前缀）本就无法解析；
2. 与用户拍板口径（改存量文档还是改门），**拍板前不得按噪声立项**；
3. **历史批次不回改**——基线只登记，不触发整改。

同时把两条检索纪律写进小节——正文以 [repo-rules 模板](../templates/hub/repo-rules.md) 第 4 节的
固定块为准（判据出处见[审核契约](repo-audit.md)的铁律清单），此处不复述第二份：
写进目标仓小节的是硬判据，不是建议。

## 4. 此后以该小节为准

约定变化时就地更新它，**不另开平行文件**。

Init 只配置项目侧约定，**不把 Agentflow 的内部机制名词搬进目标仓**——需要说明时用白话。
