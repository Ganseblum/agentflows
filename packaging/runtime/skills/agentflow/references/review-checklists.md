# 评审深度清单（专项模式与文档评审模式）

> 权威载体：本文件是「按 diff 形状加载哪几份清单」的清单正文。选择规则与判定口径留在
> `agents/reviewer.md`，本文件不复述那些规则——一条事实一个权威载体（归属表见
> `skills/agentflow/references/carrier-map.md`）。
> 立档来源：2026-10-29 全面修正与瘦身批 T12——原样从 `agents/reviewer.md` 移出，逐条内容未改写；
> 移出的理由是评审者按 diff 形状只加载需要的那一份，而不是每次把 200 行角色档案全读。

**专项评审模式。** 简报可以把评审范围限定到某一专项；除通用检查外，应用与之匹配的深度清单。

- *Security*：每个新增或变更端点的授权（谁可以调用、可以读写什么）、每个受影响表面的认证态
  矩阵（未登录、令牌过期、租户不符）、配置/日志/URL 中的密钥处理、注入与输入校验面（SQL、
  命令、路径穿越、SSRF）、查询中的租户隔离，以及公开面的限流。每条检查项都引用代码或检查；
  「不适用」要显式声明，绝不沉默。
- *Test depth*：每个新增测试都必须能在它针对的缺陷上失败——推演修复被还原后该测试是否还会
  通过；改动触碰的「表面 × 状态」矩阵格子要么有覆盖测试，要么显式标注「未测试」；契约级
  断言（状态码、错误形状、顺序）优先于内部实现；每个被修复的 Bug 都写明其回归检查。revert
  实验是行为断言，不是散文：你自己不能运行它，所以对每条承重的回归检查写明确切的还原命令
  （例如恢复未修复代码的 `git stash` / worktree 配方）和预期的失败输出，由 Supervisor 执行
  并回传原始结果——与上文相同的检查协议，绝不接受摘要。
- *Flow reasonableness (test evidence)*：当产物中包含测试执行记录（`docs/features/<批次>/testing/`）
  时，把其中的原始证据视为覆盖它指名的用户可见断言，并评审流程本身：spec 未定义的超时、重复
  提交、中断与登录态过期路径；跨表面一致的错误信息语义（同一失败、同一措辞、可操作的下一步）；
  无法到达或无法离开的状态。「该失败而没失败」也是 finding，即便观察到的行为看起来方便。计划
  的 `## 流程疑点` 条目是起始清单——实现只是碰巧回答了的问题也是 finding，不是备注。finding 由
  Supervisor 按标准归因转为 Bug 记录。
- *Documentation accuracy*：文档中的每条行为断言都映射到 `path:line` 或检查输出；API 文档与
  实际路由、参数和错误形状一致；不再能运行的示例是缺陷，不是风格问题。

**文档评审模式（外部文档）。** 当被评审产物是在另一系统的流水线中撰写的文档（二次评审桥）时，
选择与每份文档类型匹配的模式，并在通用检查之外应用其清单。任何模式下，检查项只有引用到原文
句子或 `path:line` 才算通过——无法引用的检查项视为未评审；清单要求的内容「没写」本身就是
finding。

- *需求提案*：范围之内/之外都写清且可核验（无法证伪的「范围之外」主张是缺陷）；
  「怎么知道它生效了」的判据可判定；用户或场景的切分落在具体对象上而不是类别上；刻意不做
  的事有说明；与既有能力/历史的关联是显式的。
- *Spec*：字段语义、边界规则与异常分支已冻结；权威裁决规则有明确说明（哪个结果优先、哪些
  状态变化强制重算、哪些历史事实可以展示但绝不得用于推断当前资格）；默认值与降级规则存在；
  边界场景清单覆盖刚成功 / 刚过期 / 空 / 非法枚举值 / 脏历史；**上游缺口已登记**（需求提案
  不合规项 / OQ 清单存在，阻塞条目在 spec 被视为冻结之前关闭）。
- *Design*：设计完备性产物存在——以步骤表为基准的关键链路时序、异常矩阵（超时 / 重复请求 /
  状态冲突 / 回调失败；重试格子写明责任方、次数、退避、幂等前提；泛泛的「异常兜底」式表述
  按缺陷退回）、与回滚点配对的发布顺序，以及带缓解措施的影响面分级；契约兼容性以及幂等、
  并发与事务边界都有说明；可观测性有具名（失败如何通过日志、指标、trace 定位）；**安全边界
  有专项清单**——授权与认证态矩阵、密钥处理、注入与输入校验面、产物渲染消毒、租户隔离与
  限流逐项有结论（不适用项显式声明并附理由，绝不沉默）；验收标准指向 spec/QA 来源，而不是
  另一套独立发明的标准。启用 UI 轨时另查**视觉来源**：组件库与版本、主题机制接入点、token
  源文件、字体图标资产是否给了 `path:line` 或链接，§1 的 token 值能否追回来源，相对基线的
  差异是否逐条说明；凭空写色值、截图取色、无理由换组件库、冷启动却没声明「基线 v1」都按
  缺陷退回。
- *埋点（事件契约）*：被评审产物含 proposal 的埋点决策或 `design/fe` 的事件契约时启用。逐事件套用
  [`references/telemetry.md`](telemetry.md) 的评审门十条——本模式不复述那份
  清单，按它逐条核对；本来拷贝到三处的清单会漂移，放着一份才是那份契约自己的要求。其中三条属
  **运行时判据**（发送先于结果 / 同一动作不重复计次 / 成功与失败两端都报），只认端到端路径证据或
  网络请求日志，读代码不构成证据——拿不到就记为未验证，不因"看过实现"放行。三处（决策 / 口径 /
  契约）的新增 · 复用 · N/A 互相矛盾按 finding 退回；缺的那一段要写明不适用与理由，表上没有这一行
  不等于声明过。
- *Plan*：所评审仓的计划契约（插件仓见 `docs/features/README.md` 的计划形态节；目标仓有自己计划约定时以它为准，无约定时见链契约的融合形态 `plan/execution.md`）——依赖图无环、固定状态枚举、阻塞
  未决项在批准前关闭；不需要外部模式。

每种模式下还要检查阅读负担与表达纪律。判据的单点定义在
[`references/document-chain.md`](document-chain.md) 的质量标准节
（换 > 释 > 删、代号裸用、模式词分域、流程角色词与时效性引用），本档案不重复列举——重复定义正是
那一节自己判为缺陷的「同一结论双源并存，不声明取舍」。这里只写评审者怎么用它，以及只有这里才有的两条：

- 每一条检查项都要引用到原文句子或 `path:line` 才算通过；无法引用的检查项视为未评审，
  清单要求的内容「没写」本身就是 finding。每一处命中都带引用逐处报告，否则不予报告。
- **不得自造接口编号**：接口以「方法 + 路径」标识，跨文档引用必须用读者不必翻回前文就能解析的名称；
  关于文档自身的元叙述（门、来源、流程话题）不得作为段落出现在内容里。
- 评审对象不限于文档链文档：被指派评审独立会话交付物（分析报告、状态报告）时，复用同一判据，
  包含代号裸用与模式词分域两种形态；不单开评审模式。
