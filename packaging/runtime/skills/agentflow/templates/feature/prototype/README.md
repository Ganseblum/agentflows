# `prototype/` — 可直开的产品原型

> 一句话：先把现有产品页面与设计基线查清，再用这份可编辑预览确认本期界面；后续迭代继续沿用。
> 将 `index.html` 放在 feature 目录的 `prototype/` 下，浏览器双击直开——没有构建链、没有依赖、
> 不发网络请求。截图可以从此页面导出用于评审，但 HTML 是唯一可继续修改的原型主文件。

## 原型形态（在页面标题旁标注当前状态）

| 形态 | 做法 | 什么时候用 | 评审看什么 |
| --- | --- | --- | --- |
| 产品视觉预览 | 沿用项目真实页面骨架、组件、主题与 token；按本期改动补交互 | 默认。涉及页面、布局、样式或交互的变更 | 是否符合现有产品、差异是否准确、状态与操作是否完整 |
| 可点原型 | 在产品视觉预览上接本地假数据，能点通受影响流程 | 主流程步骤多、或需要确认交互手感 | 步骤数、跳转去向、放弃路径、异常反馈 |
| 结构草稿 | 中性线框 + 区块标注 | 仅用于访谈中尚未决定布局或信息顺序的早期讨论 | 结构是否成立、待决项是什么；不得作为计划前最终 UI 预览 |

产品视觉预览是用户确认与后续实现的共同依据，不等于生产代码。视觉结论写在 `design/ui`；未启用 UI
轨时写在 `design/fe §1.1.5`。结构草稿只回答明确标出的待决问题，不能把通用灰色骨架当成目标项目的
视觉方案。

## 命名与落点

```text
<feature 目录>/
  prototype/
    index.html          唯一原型入口（同一 feature 的迭代沿用此文件）
    assets/             可选：随原型离线使用的图片、图标与字体
    states.md           可选：四态与边界态的截图/说明，页面里放不下时用它兜
```

- 文件名固定 `index.html`：README 元信息与 design 文档都指向它，避免每个批次换个名字。
- 一个页面一个 `<section class="screen">`，页签自动生成；新增页面不改脚本。
- 先读取实际产品页面及组件/主题/token 源文件；`design/ui §0.1` 或 `design/fe §1.1.4` 写具体路径与
  revision。截图可帮助比对布局，但不能作为取色依据或替代实现来源。
- 新 feature 改动已存在的页面时，复制最近一次用户确认的原型到本 feature 的 `prototype/index.html`，
  在 README 记下来源 feature、原型路径和 revision；在 design 变更记录写本期差异与用户结论。不要另建
  日期副本目录，已确认的旧版由 Git 历史保留。
- 页面预览区应尽量只呈现目标产品界面；标注、版本和评审说明放在预览区外或可隐藏区域，避免把说明面板
  做成产品功能。
- 页面里出现的可点击元素，在 `design/fe` 的 testid 清单里必须有同名条目——原型与实现用同一套
  testid，测试用例才能直接引用。

## 真源声明（必须写，只写一处）

在 `design/fe` 或 `design/ui` 的线框节头部声明一次，不要两处各画一份：

```text
原型真源：prototype/index.html（页面与交互）+ design/fe §1.1.5 或 design/ui §4 标注表（基线出处、差异与用户结论）
冲突时以 design 中已确认的文字结论为准，并同步修正 HTML；页面截图只是该 HTML 的预览证据。
```

## 结论回写

原型是需求确认与设计评审的入口，不是交付终点：每个标注项都要在提案待冻结问题或 spec 里落成一行
结论（采用什么、为什么），并带上判定口径。页面按上面的统一路径保留，**不要在结论落账后删除**——
它同时是 QA 与后续实现理解页面和迭代差异的依据。

## 什么时候可以 `N/A`

- 本 feature 没有用户可见界面（纯后端、纯脚本、纯文档）：在 `README` 元信息写
  `原型：N/A: 无用户界面`。
- 视觉与结构完全复用既有页面、无新增区块：写 `原型：N/A: 复用 <页面> 既有结构，见 <链接>`，
  并在 `design/fe` 的线框表里逐条写明复用哪一块。
