# issues — 缺陷与事项流

> 规则：编号 `<ISS-<YYYY-MM-DD>-<slug>｜沿用项目既有编号规则>`；开放条目与已验证（`verified`）记录**都平铺**于本目录，只有被拒（`rejected`）条目移入 `归档/<日期>/`。小修在条目内解决；中/大问题经用户确认后升格为 `features/` 批次。

## 开放条目

| ISS-YYYY-MM-DD-<slug> | <一句话现象> | `ISS-YYYY-MM-DD-<slug>.md` | <负责人 / 关联批次> |

> 本表**不写状态结论**：状态权威在每条记录的 frontmatter（`open` / `fixed-pending-review` / `verified` /
> `rejected`）。行内带状态词却无记录链接的行，会被本文件末尾那行标记启用的 C15 判红。列形态与
> `AGENTS.md` 的「台账只做索引」一致。详细规则与记录形态见 `docs/issues/README.md`。
> **标记是 opt-in 开关，且必须独立成行**：只在散文里提这个词（哪怕在行内代码里），门会认为你要启用
> C15 却没有声明行，直接判红；不需要台账判据就把下面那一行删掉。

## 升格通道

- 中/大问题经用户确认后，在 `features/` 下建批次；原记录的状态节写「已升格并入 `<批次目录>`」，批次 README 写「升格来源：ISS-YYYY-MM-DD-slug（原由）」。
- 升格即留痕，不靠记忆。

## 归档（只覆盖被拒态）

- 被拒记录移入 `归档/<YYYY-MM-DD>/`（日期目录 = 该记录 `recorded_at` 的日期），原记录正文注明拒绝理由与出处。
- **已验证记录不移入归档**：记录 id 就是文件名，复发台账与评审记录都按该路径引用，搬走会打断引用链。
  目标仓若确有不同的归档口径，要在本节写明它是什么、由哪条检查强制——不要留着让模板与本仓的门互相打架。
- 归档是记录面的移出面，不是 git 历史的替代；删除类操作仍以 git 历史为回溯依据。
- 本目录的「归档」与 `episodes/归档/`（按月下沉）、评测/评审件的 `archive/`（按期或按轮次封存）不同义：
  那三处与记录状态无关。
