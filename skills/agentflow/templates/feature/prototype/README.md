# `prototype/` — 可直开的产品原型

> 一句话：先把现有产品页面与设计基线查清，再用这份可编辑预览确认本期界面；后续迭代继续沿用。
> 将 `index.html` 放在 feature 目录的 `prototype/` 下，浏览器双击直开——没有构建链、没有依赖、
> 不发网络请求。截图可以从此页面导出用于评审，但 HTML 是唯一可继续修改的原型正文（形态 A 在原型库内，
> 形态 B 在批次目录；批次入口页只做索引，不是第二份正文）。

## 原型形态（在页面标题旁标注当前状态）

| 形态 | 做法 | 什么时候用 | 评审看什么 |
| --- | --- | --- | --- |
| 产品视觉预览 | 沿用项目真实页面骨架、组件、主题与 token；按本期改动补交互 | 默认。涉及页面、布局、样式或交互的变更 | 是否符合现有产品、差异是否准确、状态与操作是否完整 |
| 可点原型 | 在产品视觉预览上接本地假数据，能点通受影响流程 | 主流程步骤多、或需要确认交互手感 | 步骤数、跳转去向、放弃路径、异常反馈 |
| 结构草稿 | 中性线框 + 区块标注 | 仅用于访谈中尚未决定布局或信息顺序的早期讨论 | 结构是否成立、待决项是什么；不得作为计划前最终 UI 预览 |

产品视觉预览是用户确认与后续实现的共同依据，不等于生产代码。视觉结论写在 `design/ui`；未启用 UI
轨时写在 `design/fe §1.1.5`。结构草稿只回答明确标出的待决问题，不能把通用灰色骨架当成目标项目的
视觉方案。

## 存放形态（先判形态，再决定写哪里）

| 形态 | 判据（目标仓事实，不看偏好） | 原型正文写在哪 | 批次 `prototype/index.html` 放什么 |
| --- | --- | --- | --- |
| A 仓库级原型库 | 目标仓已维护原型库（如 `design/html/<产品组>/`，另有库首页） | 库内页面文件，唯一正文 | 入口页：受影响页深链 + 整体预览入口 + 正文基线 `path@revision` |
| B 批次自建 | 目标仓确无原型库 | 批次 `prototype/index.html` 本体 | 就是正文；下面各节按此形态写 |

选择规则只有一条：**目标仓已维护原型库 → 必须形态 A；确无原型库 → 形态 B**。判据是目标仓事实，不看
偏好；没有第三种形态——不在批次里复制库内正文，也不为单个批次在库里建副本目录。

**形态 A 入口页**：只做索引，不放页面正文（骨架 `index.html` 顶部注释给出链接块写法：删掉所有
`<section class="screen">` 与页签脚本，改成一个链接块）；每个本期受影响页一条相对深链指到库内具体页面，
另给库首页作为整体预览入口（如 `design/html/index.html`），并写明正文基线 `path@revision`（git 可解析
的提交号）。入口页零依赖、离线双击可开、不发网络请求；链接目标与它们依赖的 assets、主题层、字体图标
必须可达。跨仓或文档枢纽仓（批次文档在枢纽仓、原型库在实施仓）时，revision 与路径写成仓限定形式
`<repo>@<revision>:<path>`；相对深链跨仓不可达就登记该仓限定路径 + 一个可打开的工作台入口（实施仓内
库首页或本地预览命令），不得用外部 URL 冒充离线原型。**确认结论绑定登记时的 revision**：库内正文此后
改动要在变更记录写出新 revision 并刷新入口页，不把活文件当作已确认结论。历史版本用
`git show <rev>:<path>` 取，不建按日期堆放的副本目录。参考项目或竞品的还原稿只能作对照基线，不得当作
目标仓现状。

**形态 B 复制或搬运既有页面**：必须带上依赖闭包（共享 assets、主题层、字体图标）并重写相对链接，来源
基线 `path@revision` 登记进 README；复制后不得删改主题层或 `data-*` 主题开关。批次内副本是派生快照，
不是第二份正文——改正文回库内（形态 A）或上游源（形态 B）。

## 命名与落点

```text
<feature 目录>/
  prototype/
    index.html          唯一原型入口（同一 feature 的迭代沿用此文件）
    assets/             可选：随原型离线使用的图片、图标与字体
    states.md           可选：四态与边界态的截图/说明，页面里放不下时用它兜
```

- 文件名固定 `index.html`：README 元信息与 design 文档都指向它，避免每个批次换个名字。
- 形态 A 下这个 `index.html` 是入口页而不是正文：正文在原型库内，批次目录不出现库内页面的副本。
- 一个页面一个 `<section class="screen">`，页签自动生成；新增页面不改脚本（形态 A 的入口页不需要这层骨架）。
- 先读取实际产品页面及组件/主题/token 源文件；`design/ui §0.1` 或 `design/fe §1.1.5` 写具体路径与
  revision。截图可帮助比对布局，但不能作为取色依据或替代实现来源。
- 形态 B 下新 feature 改动已存在的页面时，复制最近一次用户确认的原型到本 feature 的
  `prototype/index.html`（并带齐依赖闭包），在 README 记下来源 feature、原型路径和 revision；在 design
  变更记录写本期差异与用户结论。不要另建日期副本目录，已确认的旧版由 Git 历史保留。
- 页面预览区应尽量只呈现目标产品界面；标注、版本和评审说明放在预览区外或可隐藏区域，避免把说明面板
  做成产品功能。
- 页面里出现的可点击元素，在 `design/fe` 的 testid 清单里必须有同名条目——原型与实现用同一套
  testid，测试用例才能直接引用。

## 真源声明（必须写，只写一处）

在 `design/fe` 或 `design/ui` 的线框节头部声明一次，不要两处各画一份：

```text
原型真源（二选一，只写一处）：
  形态 A：<库内页面路径>@<revision>（页面与交互）+ design/fe §1.1.5 或 design/ui §4 标注表（基线出处、差异与用户结论）
  形态 B：prototype/index.html（页面与交互）+ 同一标注表
冲突时以 design 中已确认的文字结论为准，并同步修正原型正文（形态 A 回改库内，形态 B 改批次文件）；
页面截图只是该原型的预览证据。
```

## 交付前自检（人工执行；本插件没有对应的机器门）

以下每条靠人核对，`validate.py` / `doc_chain.py` 通过不等于验过：

- [ ] 形态判定写进 README 元信息：目标仓已维护原型库→A；确无原型库→B。
- [ ] 入口页/原型双击可开，无构建链、无外部 URL、不发网络请求；引用的 assets、主题层、字体图标都在仓内
      可达（逐条点开过，不是只看路径像不像）。
- [ ] 形态 A：入口页不含页面正文（没有页面结构、没有 `<section class="screen">`）；批次目录没有库内页面
      副本；每个深链的目标文件在仓内存在，整体预览入口指向库首页。
- [ ] 形态 A：登记的 `path@revision` 能被 `git show <rev>:<path>` 解析，且 `<path>` 与深链指向同一文件
      （每条链接各核对一次；跨仓写 `<repo>@<revision>:<path>`，深链不可达时同时给可打开的工作台入口）。
- [ ] 形态 A：确认记录里的 revision 与入口页登记一致；正文在确认后又改过的，变更记录里已有新 revision。
- [ ] 形态 B：复制页面时依赖闭包齐全、相对链接已重写，主题层与 `data-*` 主题开关未被删改；来源基线
      `path@revision` 已登记。
- [ ] 参考项目或竞品的还原稿只作对照基线，没有被写成目标仓现状。
- [ ] 真源声明只写一处，指向当前形态的正文（形态 A 指库内路径）。

## 结论回写

原型是需求确认与设计评审的入口，不是交付终点：每个标注项都要在提案待冻结问题或 spec 里落成一行
结论（采用什么、为什么），并带上判定口径。页面按上面的统一路径保留，**不要在结论落账后删除**——
它同时是 QA 与后续实现理解页面和迭代差异的依据。

## 什么时候可以 `N/A`

- 本 feature 没有用户可见界面（纯后端、纯脚本、纯文档）：在 `README` 元信息写
  `原型：N/A: 无用户界面`。
- 视觉与结构完全复用既有页面、无新增区块：写 `原型：N/A: 复用 <页面> 既有结构，见 <链接>`，
  并在 `design/fe` 的线框表里逐条写明复用哪一块。**澄清条款：有 UI 改动的批次不得用这一条**——只要
  本期改动用户可见页面、布局、样式或交互，就必须有 A 或 B 形态的可确认原型。
