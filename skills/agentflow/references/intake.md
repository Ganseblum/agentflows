# 开工前的提问与对齐（Intake）

Supervisor 在 Intake 阶段把用户的需求补成一份可执行的简报。目标不是「问得多」，是「问得准」：用户少想，但关键空白不被假设掉。

## 六要素

| 要素 | 要问清什么 |
| --- | --- |
| 目标 | 要解决什么问题，为什么现在做 |
| 交付物 | 产出什么：格式、结构、文件名、放在哪 |
| 验收 | 怎样算对：要带什么证据、**证据层级**（`api / browser / file / manual`）、不许出现什么、用户会怎么检查 |
| 上下文 | 用户知道、agent 不知道的：哪些决定能动、谁拍板、时间；**哪些不能动（红线）** |
| 分工 | 谁做谁审：哪些能交给子 agent，哪些必须本人做 |
| 节奏 | 先给方案等确认，还是直接做；分几步交；有依赖时按 1、2、3 排 |

**红线单独确认。** 原话里出现「不要动 X」「别改 Y」「不能碰 Z」的，原样写进简报，不缩写、不转述。任务会碰生产环境、删数据、权限、计费这类不可回退面，而原话又没写红线时，问一句「哪些不能动？」，推荐按「只读 / 只动当前工作区 / 不动已部署环境」给。

**验收必须落到可观察。** 页面元素、提示文案、网络请求、文件内容、命令输出；不要写「功能正常」。用户可见入口的证据层级只能是 `browser` 或 `manual`；`api` 200 不能证明页面可用（ISS-2026-050 类事故的根因）。

## 提问预算

- **先查后问**：对话、当前目录、路径、仓库、档案能回答的，自己找；找不到再问。
- **能假设就假设，但要让用户看见**：推断写成「我按这些做」列出；只有猜错代价大的（整份返工、不可回退、动已拍板的事）才问。
- **一次最多问 2 个问题**，每题最多 3 个选项并标推荐；用户回「发」或没理会，按推荐走。
- **小事不打断**：一句话说得清、做错也好改的任务，直接做，不走完整六要素。
- **只有不可回退或大范围改动，才先给方案等确认**；不替用户加确认环节。
- **领域清单一次勾选例外**：进入某类功能（登录 / 支付 / 上传 / 通知等）时，先按[范围维度](intake-scope-dimensions.md)把该领域的惯例维度整理成一张勾选表（每项带推荐默认与「不做的后果」），让用户一次勾完——这张表不计入上面的 2 问预算；其余澄清仍守 2 问纪律。勾选表解决的是「范围想全」，2 问纪律解决的是「不打断」；「不做」的项进 proposal §1.4 留理由，不许静默消失。

## 输出：任务简报

```md
目标：<要解决什么问题，为什么现在做>
交付物：<格式、结构、文件名、放在哪>
验收：<可观察结果；证据层级 api/browser/file/manual；不许出现什么>
上下文：<agent 不知道但影响做法的事；谁拍板；时间>
红线：<不能动的路径/环境/数据/已拍板决定；没有写「无」>
分工：<谁做谁审；哪些能交给子 agent>
节奏：<先方案后做 / 直接做；分几步；依赖顺序>
```

简报是委派输入，不是需求文档：只写这次任务需要的，不复制 proposal/spec 的正文。对象还没定的位置写 `<待定：…>`，不编。

## 路由

- 需求本身说不清（做什么、给谁、什么时候要）→ 用本文件。
- 方案/设计已成形，要压漏洞 → 用[压设计](grilling.md)。
- 两者都有 → 先 Intake 把需求和验收问清，再压设计。

## 与现有契约的关系

- [契约](contracts.md) 的「先问再假设」是总则；本文件是 Intake 阶段的执行细则，不复制总则全文。
- 需要用户拍板且尚未关闭的条目进 `docs/PENDING-DECISIONS.md`，不另起一份待决清单。
- 用户可见任务的验收层级与测试记录的关系见[测试记录](test-records.md)：计划登记 `入口` 与 `证据层级`，执行记录登记实际 `层级`。
