# 开工前的提问与对齐（Intake）

> **加载者**：`skills/agentflow/SKILL.md` 路由「开工提问」行与第 1 步；用户主动入口是 `agentflow-intake`。需求说不清、开工前要对齐时读。

Supervisor 在 Intake 阶段把用户的需求补成一份可执行的简报。目标不是「问得多」，是「问得准」：用户少想，但关键空白不被假设掉。

## 起步先判状态

同一句需求，处置方式不同——先判落在哪一档，再决定要不要走完整六要素。

| 状态 | 判据 | 怎么走 |
| --- | --- | --- |
| **小事** | 一句话说得清、做错也好改（提交、找文件、装个工具） | 一两行说「我按这样做」就开工，不列六要素 |
| **已完整** | 目标、交付物、验收都写清了，剩余空缺猜错也好改 | 一两行确认后开工；用户要拿去别处用时回「可以直接发」 |
| **混沌** | 说不出要什么（「帮我搞一下那个」） | 先猜后问，见下 |
| **其余** | 有目标、缺细节（最常见） | 按「提问预算」补要素 |

**混沌态先猜后问。** 前面有对话时，从**最近 3 轮**的话题出发，给 2～3 个「你是想……」让用户挑，每个一行；用户挑完再补要素，混沌最多走这一轮。前面没有对话时不硬猜，用一个问题问清对象，并附 2～3 个候选（优先与当前分支、最近改动有关的，其次最近修改的）。猜测必须是可验证的具体选项（「A：修 X 那个报错」「B：给 Y 加导出」），不能是「你是想要个方案吗」这类空问——空问等于把判断成本又推回用户。

## 六要素

| 要素 | 要问清什么 |
| --- | --- |
| 目标 | 要解决什么问题，为什么现在做 |
| 交付物 | 产出什么：格式、结构、文件名、放在哪 |
| 验收 | 怎样算对：要带什么证据、**证据层级**（`api / browser / file / manual`）、不许出现什么、用户会怎么检查 |
| 上下文 | 用户知道、agent 不知道的：哪些决定能动、谁拍板、时间；**哪些不能动（红线）** |
| 分工 | 谁做谁审：哪些能交给子 agent，哪些必须本人做 |
| 节奏 | 先给方案等确认，还是直接做；分几步交；有依赖时按 1、2、3 排 |

**红线单独确认。** 原话里出现「不要动 X」「别改 Y」「不能碰 Z」的，原样写进简报，不缩写、不转述。任务会碰生产环境、删数据、权限、计费这类不可回退面，而原话又没写红线时，问一句「哪些不能动？」，推荐按「只读 / 只动当前工作区 / 不动已部署环境」给。

**验收必须落到可观察。** 页面元素、提示文案、网络请求、文件内容、命令输出；不要写「功能正常」。用户可见入口的证据层级只能是 `browser` 或 `manual`；`api` 200 不能证明页面可用（ISS-2026-050 类事故的根因）。

## 提问预算

- **先查后问**：对话、当前目录、路径、仓库、档案能回答的，自己找；找不到再问。
- **能假设就假设，但要让用户看见**：推断写成「我按这些做」列出；只有猜错代价大的（整份返工、不可回退、动已拍板的事）才问。
- **一次最多问 2 个问题**，每题最多 3 个选项并标推荐；用户回「发」或没理会，按推荐走。
- **小事不打断**：一句话说得清、做错也好改的任务，直接做，不走完整六要素。
- **只有不可回退或大范围改动，才先给方案等确认**；不替用户加确认环节。
- **领域清单一次勾选例外**：进入某类功能（登录 / 支付 / 上传 / 通知等）时，先按[范围维度](intake-scope-dimensions.md)把该领域的惯例维度整理成一张勾选表（每项带推荐默认与「不做的后果」），让用户一次勾完——这张表不计入上面的 2 问预算；其余澄清仍守 2 问纪律。勾选表解决的是「范围想全」，2 问纪律解决的是「不打断」；「不做」的项进 proposal §1.4 留理由，不许静默消失。

## 点名对象不在时

需求里点名的路径、文件、报告是**任务的对象**，不能悄悄换成别的。查不到时按对象与辅助材料分开处置：

| 情况 | 处置 |
| --- | --- |
| 找到了明显是它的（同名仓搬了家） | 列出来让用户确认；有多个时推荐在当前工作区里的、或最近改过的那个 |
| 一个都没找到 | 进「要你定」，让用户给路径或贴内容，不拿相似文件顶替 |
| **辅助材料**不在（参考文档、配置样例） | 写成假设「没找到 X，按……处理」让用户看见；不要为它打断 |

当前目录只是环境，不算点名的对象。

## 依据缺失时：先问，不替用户补空白

信息不全时最容易犯的错不是「问得少」，是**用合理猜测把空白填掉**，然后一路做到底。三种缺失分处置：

| 缺失什么 | 错误做法 | 正确做法 |
| --- | --- | --- |
| **任务要求的简报 / `design` 目录 / 字段级契约 / 接口定义**（做这件事的前提材料） | 按「仓库既有页面模式」「按推荐口径」「以代码为准」自行补全后开工 | **停下**，用提问补齐范围、约束与验收；补不齐就返回 `blocked`，不带着假设实现 |
| **`diff` / `HEAD` sha / 测试原始输出**（评审的证据材料） | 用作者摘要代替，或「看起来合理」放行 | 如实记为**未评审 / 未运行**，不假装通过；缺证据时结论上限是 `partial` |
| **代码与文档/规格/用户描述不一致** | 默认「以代码为准」，按实现现状写文档或按文档改实现 | **先摆冲突点**（哪份文档、哪段代码、哪个约束），由用户定以谁为准再继续 |

**「代码为准」只有两种情形可以直接用**：① 用户在本轮已明确授权；② 冲突纯属文档落后于**已验收落地**的实现，且用户已知晓。

这条与上一节同源：**点名的对象不在**不拿相似文件顶替，**做事的依据不在**不拿相似套路顶替。两者都是把判断交还用户，而不是替用户拍板。

## 执行类任务先核状态

提交、部署、跑 SQL、改配置这类任务，动手前先看当前状态（`git status`、当前分支、目标环境），原话里带「如果……就」的条件也先核一遍。状态与原话对不上时，回一句说明再问，不空跑。

## 输出：任务简报

```md
目标：<要解决什么问题，为什么现在做>
交付物：<格式、结构、文件名、放在哪>
验收：<可观察结果；证据层级 api/browser/file/manual；不许出现什么>
上下文：<agent 不知道但影响做法的事；谁拍板；时间>
红线：<不能动的路径/环境/数据/已拍板决定；没有写「无」>
分工：<谁做谁审；哪些能交给子 agent>
节奏：<先方案后做 / 直接做；分几步；依赖顺序>
```

简报是委派输入，不是需求文档：只写这次任务需要的，不复制 proposal/spec 的正文。对象还没定的位置写 `<待定：…>`，不编。

**用户的预判要改成待办，不能写成结论。** 原话里「应该不需要改了」「这个应该没影响」这类判断，写进简报时改成「先验证 X 是否仍需处理」「先确认 Y 有无影响」——预判不是事实，直接照抄会让 worker 拿假设当前提。

**范围外的加料要打标。** 同类任务的公认做法如果明显更好用（比如评审清单按严重度排序），最多加 1 条，在简报里标「（我加的，不要就说）」。除此之外不扩大范围、不加额外产出。

## 路由

- 需求本身说不清（做什么、给谁、什么时候要）→ 用本文件。
- 方案/设计已成形，要压漏洞 → 用[压设计](grilling.md)。
- 两者都有 → 先 Intake 把需求和验收问清，再压设计。

## 与现有契约的关系

- [契约](contracts.md) 的「先问再假设」是总则；本文件是 Intake 阶段的执行细则，不复制总则全文。
- 需要用户拍板且尚未关闭的条目进 `决策记录`，不另起一份待决清单。
- 用户可见任务的验收层级与测试记录的关系见[测试记录](test-records.md)：计划登记 `入口` 与 `证据层级`，执行记录登记实际 `层级`。
