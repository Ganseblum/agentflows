# 仓库整体审核

对**一个仓库**（本仓或已接入的目标仓）做一次可复用的整体审核：角色分工、文档链、独立评审、
确定性校验是否真的成立，规则之间有没有互相打架，模板与实施状态是否对得上。产出缺口清单与
拍板项，不产出分数以外的裁决。

> 本文是**审核任务书的契约**，与「外部文档二次评审」是两件事：那条评审的对象是**另一套系统
> 规则下产出的文档**（业务仓自己模板里的提案/spec/设计/计划），证据落在本仓 `reviews/`；
> 本文的对象是**仓库自身的全部表面**，产出是缺口清单。两条都由主审发起、都可点名
> 独立 Reviewer，但输入形态与落点不同，别混。
>
> 与**改进环**的关系：审核发现的问题按修复批次落到 `docs/issues/` 与 `docs/features/`，
> 不在此立项。改进环的输入是明确反馈与真实任务结果；本审核是它的语料来源之一，
> 不是它的替代品。审核产出的缺口**不得**表述为 `evaluation_result: better`——那会把
> 「无人评审的推断」记成「已验证的改进」（2026-10-12 起方法级改动一律
> `measurement: none`，见 `docs/design-decisions.md`）。

## 什么时候走

| 情形 | 档位 |
| --- | --- |
| 版本发布前、大改后的全面体检 | 全量档 |
| 规则之间反复冲突、或某类返工第三次出现 | 全量档 |
| 只想知道「全绿」声称的真伪 | 门禁实证档 |
| 门工具改动前后的代码级复查 | 门禁实证档 + 代码审查档 |
| 某维修复后复查 | 定向档（指定维度） |
| 对外叙事 / 存在意义复盘 | 定位档 |
| 一次轻量现状摸底（无 diff、时间盒内） | 轻量档 |

**轻量档是 2026-10-23 审核实证过的形态**：一份主审加两到三名独立子审，主审核对决定性原文。
它比全量档便宜一个量级，但覆盖声明相同——凡是没读的文件、没跑的命令，一律进「未读 / 未验证」
清单，不许用经验补全。

## 开工三件事（主审先做，贴进附录）

1. **基线固定**：`date` 现取当前时间；`git -C <repo> status --short`；
   `git -C <repo> log --oneline -5`。证明整个审核基于哪个 revision。
2. **确认产物落点不与既有文件冲突**：先 `ls` 目标目录，定下本轮文件名与 `NNN`。目标已存在即
   换号，不覆盖（见 *产物落点*）。
3. **分发角色**：宿主支持并行子代理就并行（每角色独立上下文、只发该角色的任务书）；不支持则
   顺序执行，并在报告首页声明「独立并行不可用，角色分离仅为流程性」——这句话本身就是治理维
   的评分输入。

**全局排除项**：`.git/`、所有 `__pycache__/`、所有 `*.pyc`、生成树（可由
`packaging/build_runtime.py` 重新产出，除非审核打包正确性，读其生成器而非产物）。读了什么 /
跳过什么都须记入覆盖清单。

## 铁律（违反任一条，报告作废重写）

1. **证据优先**：一切结论必须带 `文件路径:行号` + 逐字引用，或「命令 + 退出码 + 逐字输出」。
   没有证据的主张单独进「无证据推测」清单，不得混进结论。
2. **实跑优先**：凡涉及门 / 工具 / 测试 / 脚本的主张，必须实际运行并贴输出。无法复现的检查
   记为「未运行」，**绝不计为通过**。
3. **只读铁律**：不得修改被审核仓库的任何文件。故障注入与变异测试只允许在 `/tmp` 的 `cp -r`
   副本上进行。不得使用 `git checkout` / `git restore` / `git stash` / `git clean` 撤销真实树
   上的任何东西。
4. **不屏蔽输出**：禁止 `2>/dev/null` 及同类写法掩盖错误。
5. **先懂再判**：评判任何文件之前，先从它自身的内容归纳三行「意图卡片」——它要干嘛（职责）、
   它声称守什么（自述契约）、它的消费者是谁。先有卡片，后有评判。卡片与观察不一致的，这个
   不一致本身就是一条发现。
6. **结论里禁止出现**「应该是 / 大概率 / 通常是 / 想必 / 一般来说」类猜测句式。没读到的就是
   没读到。
7. **不凭记忆**：对文件的主张以本轮实际读到的内容为准。引用历史结论（CHANGELOG、旧评审
   报告、README 声明）时必须重新验证其当前真伪——**过期引用是发现，不是依据**。
8. **声明与强制分开计分**：提示词级约束与机器级强制分别评价。不得把「文档声称会拦」记成
   「已强制拦截」。
9. **时间写实**：所有时间戳用 `date` 现取，不手算；校验器拒绝未来时间。
10. **检查 / 验收脚本必须先打印命中原文再判 PASS/FAIL**；否定式表述与验收条目自身的引用式
    命中要排除——关键词命中不等于缺陷。存在性结论不得用裸 `grep` 下结论（BSD grep 对中文
    关键词与部分 `--include` 组合会静默漏报），用可计数、可打印命中文件与计数的脚本检索。
11. **诚实勘误**：发现自身前期结论错误，集中在报告「勘误节」披露，不静默修改原结论。
12. **派发前先核实任务书里的引用**：写进角色任务书的每个路径、行号、命令、「某文件自承某事」，
    必须先对照仓库核实。任务文本是数据，不是既成事实；未核实的引用标注为待验证，让角色把它
    当假设而不是依据。2026-10-26 本仓自审实证：主审在任务书里写「README 自承宿主不对 Write
    强制路径约束」，实际该自承在 `docs/host-platform-facts.md` C7 行，是子代理逐行检索才纠正的。
12. **阶段分与最终分分开**：审核没跑完就出分，必须标为「阶段分」并附实际覆盖比例，不得表述为
    最终全仓评分。文件清点、测试运行、门禁 PASS 都不等于语义审查已覆盖。
13. **整改建议必须可执行**：每个问题都要带触发条件、影响、代码位置、修复方向与关闭验收条件。
    只描述现象的条目不合格。
14. **产物只增不覆**：审核产物一律写新文件，绝不覆盖同名文件；每轮带 `recorded_at`（现取）、
    `source_revision`（被审对象 revision）与 `model`（观察到的模型标识 + 宿主）。细则见
    *产物落点*。

## 评分口径

每维出分：**0–10 + 锚点说明 + 至少一条硬证据**。锚点说明必须指名通用锚点的具体档位，
不得另造刻度。各维可细化，但不得更松。

**通用锚点**：

- **9–10**：该维的设计声明全部有结构或机器支撑，无未立案的矛盾。
- **7–8**：主体扎实；存在已定位的硬伤，但每条都有明确解锁路径。
- **5–6**：声明与实现存在系统性差距，核心承诺部分落空。
- **3–4**：大面积声明无证据支撑，或门存在 fail-open 面。
- **0–2**：名存实亡。

**综合分**：十三维算术平均，D2 计两遍（门禁是本仓自声名的地基）。认为权重应改的，给出理由
与备选权重下的分数，两版都列。

### 评分卡（子项制）

维度分容易掩盖「同一维里三条过硬、七条没查」。因此每一维拆成**可复核子项**（建议每维 5 项），
逐项给「已核实 / 未验证 / 未读」三态之一，再由子项聚合出维度分。子项是打分的唯一依据——
**不允许凭维度整体印象直接出分**。

评分卡是一份独立产物，不进报告正文，也不与覆盖清单合并：

| 列 | 含义 |
| --- | --- |
| 子项 | 该维要证明的一件具体的事 |
| 状态 | 已核实（有证据）/ 未验证（查了但缺运行证据）/ 未读 |
| 证据 | `文件:行号` 或「命令 + 退出码 + 逐字输出」 |
| 扣分 | 该子项失分多少，与锚点档位对应 |

**打高分必须有运行证据**：7 分以上要求该维关键成功与失败路径有当前 revision 的运行证据
（实跑输出、走查截图、测试结果）；只有代码阅读支撑的子项记为「未验证」，不得计入高分。
**关 issue、补文档或单测变绿，都不能单独保证升分。**

### 阶段分与最终分

| | 阶段分 | 最终分 |
| --- | --- | --- |
| 覆盖 | 部分文件 / 部分链路 | 声明的范围内全部覆盖 |
| 标注 | 必须写明实际覆盖比例（如「216/843 生产源码 = 25.6%」） | 覆盖清单与评分卡子项一一对齐 |
| 用途 | 决定下一步查什么 | 可作为对外结论 |

阶段分**不得**用来回答「这个仓库好不好」——它只回答「目前已查的部分怎么样」。审查未完成时，
报告首页必须同时写覆盖比例与「这不是最终全仓评分」。

### 达到 8 分需要什么

低分要能翻盘。每一维写出「达到 8 分必须证明的事」，且必须同时满足三条：

1. 该维无未处理的 P0 / P1 问题；
2. 关键成功与失败路径有当前 revision 的运行证据；
3. 子项状态全部为「已核实」，没有「未验证」充数。

关 Issue、补文档、单测变绿都是过程动作，不是升分条件本身。

## 维度清单

全量档跑全部维度；定向档跑指定维度；轻量档至少覆盖 D1、D2、D8、D11 四维。

### 通用七维（任何项目原样跑）

这七维的判据不依赖「项目有 agent / 有 skill / 有门禁工具」，换任何仓都成立：

| # | 维度 | 要回答 |
| --- | --- | --- |
| D1 | 架构与设计一致性 | 声称的分层与实际的依赖是否一致；关键声明与代码行为是否一致 |
| D3 | 代码质量与安全 | 真实 bug、异常逃逸、fail-open 面、破坏性默认值、注入、非 ASCII 路径处理；测试覆盖真相 |
| D4 | 代码工艺与可读性 | 整洁、注释、命名、一致性；死代码与过期注释 |
| D6 | 结构合理性 | 同类相聚、边界清晰、命名一致；依赖方向；可发现性实测 |
| D7 | 逻辑链路 | 主流程是否闭环；状态机有无死路；文本定义的路径 vs 记录里真实走过的路径 |
| D8 | 文档与记录活性 | 索引是否同步、链接是否可解析、文档有无矛盾、记录是活的还是仪式的 |
| D11 | 实现的效果 | 用仓库自己的历史证据回答「实际跑出了什么」；统计加抽查验证 |

### D2 改为「阻断机制审」（不问有没有门禁工具）

**不要问「项目有没有 `validate.py`」，要问「这个项目用什么机制阻止坏东西进去，那个机制真的
会拦吗」**。按实际形态选审法：

| 项目的形态 | 审什么 | 关键判据 |
| --- | --- | --- |
| 有 CI | 步骤是否真的会失败 | `continue-on-error`、`\|\| true`、缺依赖时是红还是静默放行 |
| 有 lint / 类型检查 | 同上 | 没装工具时退出码是什么；有没有 `--no-verify` 类绕过且绕过无痕 |
| 有 code review 流程 | 提示词级还是机械级 | GitHub required check 是机械级；「请大家 review」是提示词级 |
| 有 pre-commit / pre-push hook | 可否绕过、绕过是否留痕 | hook 是否随 clone 丢失；绕过有没有被记录 |
| 只有测试 | 测试是不是真跑了 | `t.Skip` / `@pytest.mark.skip` / 被注释的断言 / `if False` |
| **什么都没有** | — | **打低分，但原因写「无机制」而非「机制失效」**——两者整改路径完全不同 |

**先区分真缺口与口径噪声**：一个长期项目里通常混着已豁免项、历史格式、模板解析问题。第一步
是把「finding 数」拆成「真缺口 / 口径噪声 / 已豁免」三类，再评分。把噪声数当缺陷数是最常见的
误判来源。

### D5 / D9 / D10 按项目形态换对象

| 维度 | 有对应面时审什么 | 没有时审什么 |
|---|---|---|
| D5 契约质量 | 角色 frontmatter 与正文互证、判断词可判定、模板无断号、契约文件无矛盾 | **项目对自己约定的自洽性**：它自己的 AGENTS.md 说的检查命令是否存在、模板是否互相矛盾、README 声称的结构是否与目录一致 |
| D9 治理与发布闭环 | 角色分离多少是机器强制、`measurement` 口径诚信、发布 = 人工批准 | **发布与回滚**：有没有版本号、发布是不是人工批准、回滚是切版本还是现场热修、发布后有没有验证 |
| D10 安全与权限边界 | 写范围谁强制、候选隔离、凭据纪律、fail-open 面全集 | **业务安全**：鉴权与越权、凭据是否落盘/落日志、SQL 注入、路径穿越、敏感数据暴露。两边内容完全不同，同一维度名 |

### 业务仓追加维度（按项目有无对应面决定是否启用）

| 维度 | 启用条件 | 要回答 |
| --- | --- | --- |
| 幂等与一致性 | 有写操作 / 有外部调用 | 重复请求只执行一次；同键异内容是否冲突；迟到结果是否覆盖新状态 |
| 故障恢复 | 有异步任务 / 有外部依赖 | 断连、失败、重启后任务能否继续、补偿或进入明确的人工队列 |
| 计费与权益 | 有支付 / 会员 / 积分 | 单位一致、快照固化、账实相符、有无重复扣发 |
| 可用性 | 有用户界面 | 用户能否完成主任务；失败后有没有可理解的恢复入口 |
| 数据与隐私 | 有用户数据 | 跨账号隔离、敏感数据不落日志、外部接口不泄露内部快照 |

### 评分隔离规则

**不适用的维度不计入综合分分母，而不是打 0 分。** 否则「没有 agent 的项目」会在契约质量上白丢
10 分，把缺席当成缺陷。报告须写明「本仓适用 N 维，M 维不适用及原因」，分母用 N。

### 不适用维度：存在意义

「为什么值得存在」只对**工具/框架/插件**有意义，业务仓不需要论证自己该存在。审业务仓时删除
该维，不要为了凑数而审。

### 定位组（只对工具/框架类项目）

| # | 维度 | 要回答 |
| --- | --- | --- |
| D13 | 竞品比对 | 真实空白创新点、重复造轮子的部分、对外叙事该押注什么。结论必须回到本项目实证，不用宣传语 |

### D2 的方法（必须两步）

先实跑贴输出；再在 `/tmp` 副本上做**至少 5 个变异实验**证明门真的会红。**不会让门变红的变异，
本身就是发现**（记入缺口清单）。

建议变异方向：往某 schema 加一个未实现关键字；把一条真实记录改成非法状态；改坏一个 manifest
的版本；在受保护路径制造一处改动；往文档面引入一条断链。

## 角色分工

角色是能力清单，不是必走流程——只上那些能降低风险或形成有效并行的。

| 角色 | 覆盖维度 | 必读范围 |
| --- | --- | --- |
| 架构评测员 | D1 + D6 + D7 | 入口文档、manifest、目录实况 |
| 门禁实证员 | D2 | 全部门工具源码 + 受保护清单 + 测试文件 |
| 代码审计员 | D3 + D4 + D10 | 全部工具源码 + 测试 + 写范围审计脚本 |
| 契约审计员 | D5 | 全部角色文件 + 两个 SKILL + references + templates + schemas |
| 记录与效果审计员 | D8 + D11 | 文档面全量 + 记录根全量 |
| 治理评测员 | D9 | 改进环 SKILL 与 references + 发布目录 + CHANGELOG |
| 对标与定位分析师 | D12 + D13 | 公开资料检索（唯一被授权用网络的角色） |
| 元评审员 | 不产分 | 随机抽 30% 证据引用逐条核对；标记「验证缺席」型结论 |

**审计员通读原则**：D3/D4/D10 读的是同一批文件，一次通读、三类发现分别出分，避免多角色重复
读同样文件。发现须按维度归类，不得把可读性问题记成 bug、把 bug 记成风格问题。

**记录与效果审计员的内部分工**：D8 答「记录是否在更新」（活性），D11 答「更新是否产生了
可验证的结果」（疗效）。两维分别出分，不得互相借用证据充数。

## 角色交付契约

每个角色交付一份分维度报告，六部分齐全，缺一即退回：

1. **意图卡片**——它要干嘛、它声称守什么、它的消费者是谁（铁律 5）
2. **分数 + 锚点说明**（指名通用锚点档位）
3. **亮点清单**（每条带证据）
4. **硬伤清单**（每条带证据，含触发条件）
5. **无证据推测清单**（单独一节，绝不与结论混排）
6. **未读清单**（含原因）

动笔前先确认自己的必读清单已穷尽。必读清单是**穷尽**要求，不是抽样要求；抽样只允许用于
明确标注的统计目的，且必须写明样本量与总体。

## 无 diff 的现状审核（轻量档的输入形态）

当审核对象是**仓库现状**而不是某次改动时，没有 `reviewed_revision` 可绑。此时输入是一张
**固定文件清单 + 版本号**，由 主审显式列出，而不是让角色自行探索：

- 活文档（入口、契约、当前批次）全文阅读；
- 历史记录按状态与引用抽查，抽查比例写进报告；
- 机器校验全量跑（`validate.py all` 及各单项），原始输出贴进附录；
- 主审核对其它审核者的决定性原文——**引用同一行原文的两位审核者得出相反结论时，
  主审必须亲自读那一行再裁决**。

无 diff 不等于可以放宽铁律：凡是没读的文件、没跑的命令，照样进「未读 / 未验证」清单。
**不得声称走查过未观察到的宿主行为**——那类主张应连同证据、范围与再验证方法记进
`docs/host-platform-facts.md`。

## 输出契约（单文件骨架，缺节即退回重写）

审核产物**一个文件承载全部内容**，不拆成多份。评审报告、评分卡、覆盖清单各有独立消费对象
的直觉是错的——三者都在同一批读者手里，拆开只会制造双源漂移（2026-10-26 本仓自审实证：
三份产物合并前，附录 B 的抽核数字与勘误节的抽核数字已经不一致）。

```
〇、总览：维度分数表（分数权威只此一处）+ 综合分 + 一句话裁决 + 对审核问题的直接回答
一、发现总表：按 P0–P3 排序，编号唯一家族，是编号与严重度的唯一权威
二~N、逐维明细（意图卡片 / 亮点 / 硬伤 / 分数锚点，全部带证据）
N+1、无证据推测清单（单独成节）
N+2、整改路径：分批推进表（每批做什么 + 完成标准）
N+3、勘误节：本审核自身错误的集中披露（不写流程自证）
N+4、最终裁决 + 拍板项清单
附录 A：实跑命令与逐字输出
附录 B：元评审结论（证据链审计）
附录 C：覆盖与证据（仓库规模 / 按面覆盖 / 运行证据清单 / 按角色覆盖 / 未读清单 / 排除项）
附录 D：评分卡（每维 5 子项 × 状态 × 证据 × 扣分 + 每维「达到 8 分必须证明的事」）
```

**发现总表必须带整改状态列（2026-10-28 增补，源自评测发现 B1）。** 没有状态列的审计报告只描述
过去，不承担后续可追踪性：一周之后「谁修了、谁没修、谁待拍板」只能靠人读提交历史，实测已导致
把**已修复**项误判为漏网。因此发现总表的列集合固定为
`# / 严重度 / 发现 / 位置 / 解锁条件 / 整改状态 / fix_revision`，其中：

- `整改状态` 只取五个词，禁止自由文本：`已修` / `部分修` / `未修` / `已声明设计` / `已登记待拍板`。
- `fix_revision` 必须指向能复核的载体（提交号、`0.x.y` 版本、记录路径），`未修` 时写 `—`。
- **状态只在发现总表维护**：各维度节正文不改写状态，避免同一事实两处漂移。
- 后续修复批次不改写审计正文，只回写这两列；某批关掉了哪几项，由 diff 自行说明。

**不写进报告的**：铁律执行自证、跑过哪些命令的流水账、流程合规声明——这些是过程记录，
不是审核结论。唯一不可替代的过程信息是「哪些检查记为未运行及原因」，并入附录 C 的
运行证据清单末尾。

**分数单源**：维度分只出现在总览表与正文章节标题两处，附录 D 不重复维度分，只记子项证据与
扣分。两处合起来才能复算一个维度分；只读附录 D 得不到分数，只读正文得不到扣分依据。

**编号单家族**：全文档只用一套发现编号（推荐 `G<NN>`）。不同章节出现第二套编号（如子代理
报告带来的 `H<NN>`）即缺陷——读者无法把两套编号对应起来。

**产物自身要过目标仓的门**。审核产物写在哪个仓，就要过那个仓的确定性检查——本仓即
`python3 tools/lab/doc_chain.py --file <产物>` 加 `python3 tools/lab/validate.py all`。
2026-10-26 实证：契约文件写进 `skills/agentflow/references/` 后被 C13「会话角色词」拦下 4 处
（`Supervisor`、`本次会话`）——**审别人的东西时，自己的产物也在被审范围内**。写成白话
（「主审」「本轮」）而不是加豁免。

**缺口清单每行都必须有解锁条件**；「已登记为拍板项」不是解锁条件，拍板项的关闭条件才是。

**严重度按实际后果定义，不按发现数量堆**：

| 级 | 含义 |
| --- | --- |
| P0 | 阻断主流程，或让错误结论通过门 |
| P1 | 可能导致错误判断，或主流程某步无法执行 |
| P2 | 影响一致性、可维护性或结论可信度 |

严重度本身也要有证据——没有证据支持的 P0 不得出现。**不要把验收问题一律标成 P0。**

### 产物落点：只增不覆

审核产物**一律写新文件，绝不覆盖同名文件**。同一对象反复审核时，每轮是一个新文件，历史轮次
原样保留——这是审计链的前提：覆盖会让「上一轮结论是什么」永远无法回答。

- 目录锚在被审对象而不是日期：`reviews/<project>-<feature-slug>/`，同一条线的多轮累积在一处。
- 轮次文件命名 `review-<YYYY-MM-DD>-<NNN>.md`（`NNN` 当天递增；`NNN` 冲突即说明已有同轮文件，
  换号而不是覆盖）。
- 每轮把被审对象的**逐字副本**归档到 `archive/<YYYY-MM-DD>-<NNN>/`，并记下当时的 revision——
  此后被审对象的编辑不得追溯改变被评审的对象。
- 本仓自身的整体审核（对象是整个仓库而不是某个 feature）落在
  `docs/evaluations/AGENTFLOW-<类型>-<YYYY-MM-DD>[-NNN].md`；同一天同类型的第二次审核加 `-NNN`，
  不覆盖、不改名复用。
- 写入前先 `ls` / 读目标路径：**目标已存在即停**，报告冲突而不是静默改写。

**frontmatter 必须带三样**（缺一即退回）：

| 字段 | 要求 |
| --- | --- |
| `recorded_at` | ISO 8601 带时区；本仓用北京时间 `+08:00`（`date "+%Y-%m-%dT%H:%M:%S+08:00"` 现取），不手算；校验器拒绝未来时间 |
| `source_revision` | 被审对象的 revision，形如 `<repo>@<commit>` 或 `<repo>@<commit> + 工作树说明` |
| `model` | 产出本轮主要结论的模型标识 + 宿主，见下 |

**模型字段怎么写**：记**观察到的上下文**，不是宣称的配置。经自定义网关时模型标签不可信——
同一次运行里 assistant 事件报的模型名与 CLI 记账的模型可以完全不同（本仓已记录该事实，
`docs/host-platform-facts.md` C6）。因此：

- 写实际观察到的形态，如 `zcode / new-provider:cn:step-5-preview` 或
  `claude CLI 2.1.268 / api.360.cn 网关 / 观察标签 gpt-5.6-luna`；
- 观察不到可靠标签时写 `unknown（网关未暴露）` 并附观察方式，**不得填一个看起来精确的模型名**；
- 多个子代理用同一模型时可合并一行；不同模型必须分别列出，因为结论差异可能来自模型差异。

**多角色审核额外记**：每个角色的产出各自标注 model 与 `reviewer`，让元评审员能核对「证据链
归属」而不是只核对「证据存在」。

### 整改路径

报告末尾给分批推进表，每批写「做什么 + 完成标准」，顺序按后果严重度排（数据丢失与隐私 →
资金 → 状态与恢复 → 可用性 → 文档与配置）。每批修完独立复审后再评下一批。**关 Issue、补文档
或单测变绿，都不能单独保证升分。**

## 已知环境坑

- macOS / BSD `grep` 不支持 BRE 交替（`a\|b`），用 `grep -E 'a|b'` 或宿主搜索工具。
- YAML frontmatter 的列表不支持注释行（`  # ...` 会报 nested mapping）——别被这个假象误导。
- 非 ASCII 路径 + git 的 C-quote 输出曾导致写范围审计脚本误 FAIL——审这类脚本时专门测一条
  中文路径。
- `record_store.py` 需先 `index` 再 `query`；它是词法索引，不是向量库，也不替代记录文件本身。
- 做静态统计时不得向被审核环境安装任何包；宿主没有 ruff / pyflakes 时，用标准库 `ast`
  自写只读统计即可。
- **门红不一定是要修的缺陷**：`validate.py all` 的 `lint` 子项在缺 dev 依赖的环境必红
  （ruff / mypy 未安装）。遇到时先在干净环境复跑，再决定记「未运行」还是「真失败」，
  并在报告里写清是哪一种。
