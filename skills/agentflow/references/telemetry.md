# 埋点契约

前端埋点与服务端事件采集的评审面。它不是"怎么加一个埋点"的实现指南，而是**判断一次埋点改动能否被接受**的检查清单。

适用时机：改动新增、修改或删除用户行为事件，或改动事件采集端点、事件表结构、看板聚合口径时。纯粹调整既有事件的展示文案不算。

具体事件名、字段枚举与逐事件规格由**项目侧事件手册**定义，本文件不复制。项目没有事件手册时，先建立它——没有真源的埋点改动直接退回，不是"先上线再说"。

**走 Agentflow 文档链的项目不必另建手册**：`design/fe` 的「埋点事件契约」节（前序为 proposal 的埋点决策与 `spec/fe` 的埋点口径）就是该项目的事件手册，本文的「阶段矩阵」「事件集合」一律指它——再手工誊一份同样的表等于制造第二个真源。这类项目的第 1 条检查因此落在三处是否贯通、新增 / 复用 / N/A 的结论是否一致上；第 10 条的「事件集合一致」就在该契约节的事件表与代码里的事件常量之间做，同样要留下可复现的校验命令与原始输出。

**目标仓已有事件手册时，以既有手册为准**：events 字典、数据字典或埋点平台上的既有定义优先，`design/fe`
的契约节只登记本期新增与变更的事件，并给出既有手册的 `path:line`（无链接可给时写出处名与负责方）。
两者冲突时回去改既有手册，不在契约节旁边另写一份——第二种真源一旦长出来，本篇第 10 条的 diff 就永远不为零。

## 四阶段闭环

任何触达后端的动作，必须能回答四段：**展示 → 点击 → 发送 → 结果**。

| 阶段 | 含义 | 上报时机 |
| --- | --- | --- |
| 展示 | 入口在屏幕上可见 | 可见面积达到阈值且停留达到阈值后 |
| 点击 | 用户点了 | 点击事件回调 |
| 发送 | 请求**已经发出** | 请求发出前一刻，`await` 之前 |
| 结果 | 后端或网络返回 | 响应或异常回调 |

- **缺段必须声明**：不是所有能力都有四段（页面浏览没有"发送"）。缺的那一段要在项目侧事件手册的阶段矩阵里显式标注不适用并写明理由；没声明的能力不得上线。
- **两段不算闭环**：只有点击和结果时，「点了但没发出去」（交互未完成）与「发出去了失败」（技术失败）会合并成同一个数字，无法归因。
- **三段流失率分别命名，禁止相乘**：曝光点击率、交互完成率（发送÷点击）、技术成功率（成功÷发送）。合成单一"总转化率"即失去归因方向。

## 字段与命名

- 展示、点击、发送、结果由同一条字段（通常是 `type`）表达阶段；**事件名不得再编码阶段**（不得出现 `_view`、`_click`、`_request`、`_result`、`_submit` 之类的阶段词）。两处都编码阶段，必然漂移。
- 身份与时间由服务端派生，不接受客户端提交：登录用户标识、会员或权限段位、统计日、接收时间。客户端提交的身份字段一律不采信。
- 会员/用户段位这类会随时间变化的状态，**写入时落快照**，不在查询时关联当前值。否则用户今天升级，去年的历史事件会整体漂移。
- 属性字段只接受有限枚举与布尔，不接受自由字符串。`section`、`element` 这类位置标识来自项目侧 taxonomy 常量，不硬编码字符串。
- 结果二态必须两头都报：只报成功的事件没有分母，成功率无法计算。失败原因用有限枚举归类，原始错误正文进日志、不进事件表。
- 单批条数、单条属性体积、保留期、抽样或去重口径以项目侧已批准的边界值为准，改动边界值是产品决策，不是实现细节。

## 红线

任何事件、任何字段位都不允许出现：

- query string、hash、完整 URL、来源 referrer
- 用户自由文本：搜索词、消息正文、提示词、文件名
- 个人身份信息：邮箱、手机号、真实姓名
- 凭据：令牌、授权码、一次性 state、会话 cookie
- 存储对象键、存储路径、会话标题
- 浏览器指纹组合

带凭据的路由（重置密码、邮箱验证、授权回调、单点登录回调）不上报任何事件。页面路径只接受规范化 pathname 或路由模板，动态标识必须模板化。

## 新增或修改的顺序

**先改手册，再改代码**，顺序不能反：

1. 在项目侧事件手册里加行：声明阶段集与缺段理由、触发时机、属性键与枚举。
2. 同步服务端：事件常量、事件与阶段的组合校验、属性闭集校验。
3. 前端只传手册定义的字段，不在组件里拼临时字段或自由字符串。
4. 跑本文末尾的检查清单，全部通过才算完成。

**禁止绕过**：不得为"先上再说"在代码里放宽白名单、加未登记字段，或用注释和约定代替枚举。确实需要新维度时走上面四步。

## 评审门检查清单

| # | 检查项 | 判为不通过 |
| --- | --- | --- |
| 1 | 能力在阶段矩阵有行，缺段写了不适用与理由 | 缺行 |
| 2 | 事件名不含阶段词 | 命中任一 |
| 3 | 发送在请求发出前报、结果在回调报 | 顺序颠倒或缺失 |
| 4 | 结果两个分支都上报 | 只报成功 |
| 5 | 同一用户动作没有被重复计一次（例如既报通用元素点击又报能力点击） | 重复 |
| 6 | 属性键都在白名单、枚举值在集内 | 出现自由字符串 |
| 7 | 页面路径无 query、hash、协议头，动态标识已模板化 | 命中 |
| 8 | 凭据路由无任何事件 | 有 |
| 9 | 位置标识来自 taxonomy 常量，跨产品同名保持一致 | 硬编码 |
| 10 | 手册、代码常量、taxonomy 三处的事件集合 diff 为空 | 有差异 |

第 3、4、5 条只能在运行时验证：要求端到端路径证据或网络请求日志，读代码不构成证据。第 10 条要求可复现的校验命令与原始输出；项目没有校验脚本时，把"建立校验"作为该次改动的交付物之一，而不是豁免该项。

## 与确定性检查的关系

埋点改动同样受仓库的确定性检查纪律约束：手写"我核对过"不算通过，要给出命令与原始输出。校验脚本自身不得由被检查的改动顺手放宽——放宽白名单等于编辑自己的门。
