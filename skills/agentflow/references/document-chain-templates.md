# Document chain templates (fill-in skeletons)

用法定纪律：进入文档阶段时**复制本模板并填充占位符**，不重命名章节、不删除节；章节标题是
字面量（与 records 契约的固定标题同思路），linter 对声明使用本模板的链做结构检查。目标仓
已有模板体系时用目标仓的；本模板是下限。占位符形如 `<填：…>`；不适用的节写 `N/A: 原因`，
不留空。域可增章节，模板核心节不可删。

README 需声明一行（供 linter 识别并启用结构检查）：
`本 feature 文档链由 agentflow 文档链方法生成（<日期>）`

## proposal/proposal.md

```markdown
# <feature 名> — 需求提案
## 文档信息
- 需求原文出处：<链接/文件，版本>；状态：<原文已完成/评审中>
> 原文保留方式：<逐字复制 / 引用同目录原文文件（避免双源）>
## 一、背景与目标
### 1.1 背景 <填：现状与问题，引用事实>
### 1.2 目标 <填：可判定目标>
### 1.3 本期范围 <填：包含清单；**不包含清单（每条带一句理由）**>
## 二、产品定位与核心原则 <填：定位一句话 + 原则 3–6 条>
## 三、用户与场景 <填：用户×场景×承诺表；OQ 缺口登记并挂台账>
## 四、范围决策表 <填：做/不做，引用出处>
## 五、待冻结问题台账 <填：#|问题|阻塞性|关闭条件|owner>
```

## 可选层（语料中出现的扩展，按需启用）

- `api/`：接口文档（研发提交 QA 用；§0 文档粒度约定 + §7 提交前自检清单）。
- `复盘.md`：feature 收口后的复盘（喂改进环的证据来源）。
- `code-gap-matrix`：文档 vs 代码现状完成度矩阵（在既有代码上落地的 feature 强烈建议）。
- 超大 feature 的模块化拆分：一模块一套 proposal/spec/design/plan 四件套 + 总控 spec。
