## 1. 背景与目标

### 1.1 现状：门是绿的，但四条自家规则执行不了

全量门 11 项全绿、单测 178 全过，说明**已有判据**没有问题。真正的问题在「规则存在但不在场」这一类，
本仓自己给它起过名字（`docs/issues/ISS-2026-10-23-新判据声明了却不被校验的六处.md`）：

1. **拍板口不再是唯一入口**。`AGENTS.md` 与 `docs/PENDING-DECISIONS.md` 都写明「这里是唯一需要用户
   逐条回复的清单」，实际却有 8 条待决项写在提案 §六、计划末节与批次 README 里。后果可直接观察：
   用户在同一天里第三次问「有什么要拍板 / 能删什么」——答案不在他该看的那张表里。
2. **链内台账与拍板口是两个「单一入口」**。`skills/agentflow/references/document-chain.md` 的 spec
   节写明「所有待确认 / 待冻结问题统一登记到 `spec/checklist.md`」，`AGENTS.md` 写明「等用户拍板的
   事项统一登记到 `docs/PENDING-DECISIONS.md`」。同一件事两处都自称单点，批次文档按前者落项，
   后者就永远看不见它——F1 不是执行疏忽，是条款本身互相覆盖。
3. **删档条款与证据在场条款互斥**。F3 的零执行不是没人想删，而是删不动：删一个批次目录会打断
   外部引用（L3 批 36 行、质量提升批 33 行），其中 `index.md` 与 `docs/features/README.md` 的相对链接
   由 `validate.py docs` 判红、其它批次计划证据列引用的路径由 C23 判红；而 episode 的 `evidence_ref`
   （L3 批 10 处指向该批 184 件原始证据）**不受任何存在性校验**——删了不红，但静默留下悬空指针。
   更尖锐的一处：`docs/features/feature-2026-10-28-评审欠账清偿/plan/PLAN-DEBT-001.md` T02 的落点在
   `docs/features/feature-2026-10-28-评测整改批/reviews/`，即一个未开工任务正等着往议程要删的目录里写东西。
4. **可复核性只做了一半**（F4）。计划证据列的四种载体（仓内存在的路径 / `仓库@修订:路径` / 提交号 /
   `N/A: 理由`）由 C23 机器核验；episode 是同一条链上的档案载体，路径字段只过 JSON schema 的
   「非空字符串」，指向已退役路径与已清理 `/tmp` 现场的内容照录不误。
5. **评审档位无执法**。`skills/agentflow/references/contracts.md` 成文写明「`review_tier: L0` 而
   `dispatch_errors` 为空是伪降级，同样无效」，实测 `schemas/review.schema.json` 无该字段、
   `tools/lab/` 无判据（该缺口已登记 `docs/PENDING-DECISIONS.md` 第 17 条）。

### 1.3 关键约束

**约束一：门变更与删除各自独立成档。** `schemas/`、`tools/lab/`、`tests/` 逐文件、
`skills/agentflow/references/contracts.md`、`packaging/build_runtime.py` 在
`protected-paths.txt` 内；改动属门变更，需显式人工评审（本批已获授权，逐项清单见
`design/be/backend.md` §6）。删除类动作不可逆度高于文档改写，两者不得混在同一条任务里执行。

**约束二：改门的判据不能新增判据号。** 2026-10-28 评测报告 §三 明写「不加新门项（11 项 + 24 条
C 判据已到边际收益递减区，补『该在场的在场』比加新判据重要）」。因此 G2/G3 的实现方式是
**扩既有判据的射程**（C18 归属家族、记录校验器的引用校验），不是开出 C27 或第 12 个门项。

**约束三：删除必须同批改写引用，且不留「口头已改写」。** `validate.py docs` 断言全仓 Markdown
相对链接可解析，`doc_chain` 的 C23 断言计划证据列的路径在盘。本批采用可机器核验的顺序：
先改写引用 → 跑门确认绿 → 再删对象 → 再跑门确认仍绿。任何一次「先删后补」都会把悬空指针
留在中间态，而中间态正是 F4 描述的那种静默腐烂。

**约束四：存量历史证据不回改。** `AGENTS.md` 与链契约都规定历史批次不回改、`CHANGELOG.md`
历史条目按原样保留。本批只动**现行导航面**（`index.md`、`docs/features/README.md`、
`docs/releases/*`、`docs/PENDING-DECISIONS.md`）与**仍开放的记录**；已闭合记录里的
「当时如此」计数与退役路径属于引文，不改写、不冒充现行事实。

**约束五：episode 改写要区分「标注」与「篡改」。** 给已消失对象补 `N/A: 理由` 是如实标注，
不改写当年结论；把 `evidence_ref` 指向的内容说成仍在盘上是篡改。G3 的判据只承认前者，
因此字段口径必须能把「当时指向 /tmp 一次性现场」这类事实表达出来。

### 1.5 产品定位与原则

- **一条事实一个权威载体**：本批所有收敛动作的判据是「删副本、留指针」，不是「删文本」。
- **判据强度不超过对象范围**：新增判据只作用于打标或现行对象，绝不追溯打红历史引文。
- **诚实优先于绿色**：删完仍红的门要如实报告；无法闭环的宿主侧验收继续留在
  `docs/releases/pending-test.md`，不因本批「改了很多」而转绿。

## 3. 成功指标与可观测性

- 指标口径：本批是方法级改动，`measurement: none`（依据 `docs/design-decisions.md` §3 的现行口径），
  证据为实跑命令输出与触发它的实测事实，不表述为已验证提效。
- 埋点决策：**N/A**。理由：本批只改规则文本、门判据、记录与导航面，不新增用户可见行为或事件；
  `references/telemetry.md` 的三处贯通（proposal 决策 → spec/fe 口径 → design/fe 契约）因此整链不适用。
- 可观测性：每条目标配一条会失败的检查（见 `spec/qa/acceptance.md`），其命令在计划
  `## 验证命令` 一节逐字列出，完成后把原始输出回写进计划证据列。
