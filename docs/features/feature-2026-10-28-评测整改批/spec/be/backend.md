# 规格：评测整改批

## 0. Proposal 反审 checklist

| 不合规项 | 结论 | 处置 |
| --- | --- | --- |
| 目标是否都可判定完成 | 合规 | 五目标各有明确成功标志，见 §1 验收点 |
| 是否混入了未授权范围 | 合规 | 不做事项表（proposal §1.3）逐条给出理由 |
| 是否与既有拍板冲突 | 合规 | FE/BE 合并保持 `roles.md` 2026-10-19 拍板 D 案；本批只补裁决规则 |
| 是否存在需要用户拍板才能推进的分支 | 合规 | 无——用户已一次性批准五批方案 |
| 是否声称了未验证的疗效 | 合规 | 全批 `measurement: none` |

## 1. 模块与验收点

### M01 整改追踪载体（G1）

**契约**：审计/评测报告类产物（`docs/evaluations/*-AUDIT-*.md`、`*-EVAL-*.md`）若含「发现总表」，
该表的列集合必须包含 `整改状态` 与 `fix_revision`。

| 字段 | 取值域 | 说明 |
| --- | --- | --- |
| `整改状态` | `已修` / `部分修` / `未修` / `已声明设计` / `已登记待拍板` | 只允许这五个词，禁止自由文本 |
| `fix_revision` | 提交号 / `0.x.y` / 记录路径 / `—` | 指向能复核的载体；`—` 仅用于「未修」 |

验收点见 `spec/qa/acceptance.md` §4 的 G1-AC-01、G1-AC-02。

### M02 评审能力分级（G2）

**契约**：委派能力分三档，超时/额度不可用不得静默降级。

| 档位 | 触发条件 | 独立评审形态 | 记录要求 |
| --- | --- | --- | --- |
| L2 | 委派可用且已派独立角色 | 独立子代理评审（现状默认） | 评审记录 + `review_tier: L2` |
| L1 | 只能派 1 个只读角色 | 独立 reviewer 必到；其余角色按需 | 同上，`review_tier: L1` |
| L0 | 委派整体不可用（额度/加载失败） | 主审自审 + 全套确定性门 | `review_tier: L0` + 失败派发的原始错误 + 恢复后补门承诺 |

约束：L0/L1 不适用于用户可见行为改动的**最终放行**——能力恢复后必须补一次独立评审门。

验收点：G2-AC-01 至 G2-AC-03。

### M03 表达面收敛（G3）

- `SKILL.md` 中对 `execution-coordinator` 不存在性的声明合并为一处，其余处改为指针。
- `document-chain.md` 增加「轻量档判据速查」一行式指向块（不删原有详细节）。
- `roles.md` 给出 FE/BE 是否合并的**裁决规则**（不是结论）。

验收点：G3-AC-01、G3-AC-02。

### M04 本地门基线（G4）

**契约**：`validate.py lint` 与 `pre-push.sh` 在 `AGENTFLOW_LINT_PYTHON` 未设时，若仓根存在
`.venv/bin/python`，自动用它跑 lint；不存在时行为不变（fail-closed，不新增放行路径）。

验收点：G4-AC-01、G4-AC-02。

### M05 改进环首次真实闭环（G5）

产出一份 `candidate` 记录与一份 `release-record` 记录，均通过 schema 编译，且 `measurement: none`
+ `decision: promote` 时 `basis` 明确写人工评审并附评审引用（或如实写 L0 自审 + 待补评审）。

验收点：G5-AC-01、G5-AC-02。

## 2. 设计决定（不留悬空）

1. **G4 不改 fail-closed 语义**：只在 `AGENTFLOW_LINT_PYTHON` 未设时新增 `.venv` 探测，不引入
   「缺依赖即 SKIP」这类放行分支——G01 的结论是门侧保持 fail-closed、脚本侧保持「未运行≠失败」，
   两个口径各自诚实。
2. **G1 只给审计/评测类产物加列**，不给全部记录加列——ISS/计划已有自己的状态机，再加一层是双源。
3. **G2 用档位词不用百分比**：可判定、可复核，避免「80% 评审覆盖」这种无意义指标。
4. **状态只在发现总表维护**：各维度节正文不改写状态，避免同一事实两处漂移。
