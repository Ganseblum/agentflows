## 0. 文档信息

- 来源：2026-10-28 会话。用户先要求「全面评测这个 Agentflow，包括逻辑、结构、架构、处理问题的方式、
  角色深度与能力范围，先讲好在哪、再讲差在哪、最后讲怎么改与改后对比」，读到评测报告后回复
  **「可以，全部处理吧」**——即批准报告中提出的五批整改方案全部落地。
- 评测报告落点：`docs/evaluations/AGENTFLOW-EVAL-2026-10-28.md`。

  `AGENTS.md`。

## 1. 背景

2026-10-28 的全面评测（`measurement: none` 口径，方法级判断，不表述为已验证提效）给出七条发现，
其中四条是本批要处理的结构性问题：

1. **整改追踪没有载体**：10-26 审计的 35 项发现（审计第01项–审计第35项）散落在后续多个修复提交里，谁修了、
   谁没修、谁待拍板没有单一真源。评测自身也踩到这一点——它把已修复的 审计第14项 误判为「漏网」。
2. **改进环空转且评审能力无分级**：四治理角色自 2026-10-12 装置裁撤后零真实候选；且本次评测
   实测宿主子代理并发不可用时，整套「独立评审门」无降级定义，只能靠 主审 临场声明。
3. **表达面重复**：同一规则在用户级全局块、`SKILL.md`、`contracts.md`、宿主模板四处维护；
   `SKILL.md` 对不存在的 `execution-coordinator` 声明两处；`document-chain.md` 481 行里判据与
   流程混排；FE/BE 是否合并的裁决规则一直空悬。
4. **本地门基线不可达**：本机 `validate.py all` 长期 10/11（缺 ruff/mypy 且 PEP 668 阻止 pip），
   lint 红灯常态化稀释了门的报警价值。

## 1.3 范围与非目标

**做**：上述五项；顺带刷新 `docs/trend.jsonl`、补 审计第34项 成本对照的登记、把「审计产物必须带整改状态列」
写进审核契约。

**不做**（本批显式不处理，理由随行）：

| 不做的事 | 理由 |
| --- | --- |
| 合并 frontend / backend engineer 角色文件 | 需 28 例边界测试的通过率数据；本批只写出裁决规则并保持现状（角色文件合并属产品决策，见 `roles.md` 2026-10-19 拍板） |
| 补齐 审计第19项（凭据形状扫描）、审计第20项（C17 变异项） | 均已在 `docs/PENDING-DECISIONS.md` 第 12、13 条登记，属受保护面门变更，待用户逐项拍板 |
| 真实成本对照实验（审计第34项） | 需跑「同题不用 agentflow」的对照组，超出本批可执行范围；本批只补登记与协议 |
| 拆 `document-chain.md` 全文 | 481 行的完整拆分牵动 C 检查与多处引用；本批只加判据速查表并把执行细节留在原节，拆分另立批 |
| 恢复评测装置 / canary | 评测装置已于 2026-10-12 裁撤（ISS-2026-052）；恢复条件见 `docs/design-decisions.md` §3 |
| 发布与推送 | 按仓库纪律：本批只在 `feature-2026-10-28-评测整改批` 分支提交，不合并、不推送、不重装 |

无。用户已一次性批准全部五批；本批范围内的取舍（如 G4 用 `.venv` 探测而不改 fail-closed 语义）

## 2. 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 改动落在受保护面（`contracts.md`、`validate.py`、`pre-push.sh`、`tools/lab/`） | 属门变更，按仓库纪律须人审 | 用户本次明确授权；每处改动附 `validate.py all` 原始输出；缺独立复核如实登记为 L0 |
| 分级协议被误用为「可以跳过评审」 | 削弱核心边界 | 协议要求降级必须留痕（`review_tier` + 失败派发的原始错误）且在能力恢复后补门；L0 不适用于用户可见行为改动的最终放行 |
| 审计表加列后与正文节不一致 | 再次出现双源 | 状态只在发现总表维护，各维度节正文不改写状态；回写时只改表格 |
