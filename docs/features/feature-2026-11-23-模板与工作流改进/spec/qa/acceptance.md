# 验收规格

以[提案](../../proposal/proposal.md)的目标为来源。先核对输出与真实历史输入的绑定，再验证成功与失败分别走到预期结果。工具检查通过、业务覆盖和宿主加载分别确认。

| 验收点 | 场景 | 操作 | 可观察结果 | 最低证据 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| G1-AC-01 | 目录误选或包失败 | 在副本选择已有非生成目录，再分别构造坏链接和错版本 | 退出 1，列出失效路径，已有目录与有效生成包逐字不变 | file | P1 |
| G1-AC-02 | 暂存区有范围外改动 | 暂存文件后仅将工作副本改回基线 | 脚本与新封存的验证都报实际文件名；状态核对能区分暂存与工作区 | file | P1 |
| G2-AC-01 | 阶段稿与增量实现分别评审 | 审未有实施计划的设计稿；再以跨仓快照或缺基线的 delta 运行实现评审 | 设计稿生成可读简报，缺关键输入或来源错绑非零迭代；拒绝改写源稿 | file | P1 |
| G2-AC-02 | 一次立案重试、一次缓存报告 | 输入评审原样记录，再以同轮数据重试；核对 Go 原生缓存报告 | 缺陷不重复立案；缓存不能计为本轮新执行的通过 | file | P1 |
| G3-AC-01 | 新项目生成材料 | 用临时文档根生成 light、后端、UI、UI 带离线原型 | light 恰有一个 README，其余按选轨生成，全部本地链接可解析，不使用示例日期与计划号当事实 | file | P1 |
| G3-AC-02 | 完整文档逐阶段移交 | 按提案、规格、设计、计划分别核对目标、行为、失败与恢复、执行和证据 | 同一需求、状态和断言只在其所属文件维护，各角色可以按实际材料位置工作 | manual | P1 |
| G4-AC-01 | 发布预检和本地安装 | 用带脏文件的副本运行发布预检；重新构建并读回本机缓存 | 范围不清的发布在落盘前停止；已安装宿主逐文件核验，加载状态分别报告 | file | P1 |
| G4-AC-02 | 历史浏览器重放 | 新建夹具、空间和原始证据目录重放核心及扩展流程 | 浏览器实际报告失败恢复、合法提交与重复操作结果；旧结果未被覆盖 | browser | P2 |

本批无业务 API 或数据库契约。新增公开接口是工具的输入、输出与错误状态，详见[技术设计](../../design/be/backend.md)。
