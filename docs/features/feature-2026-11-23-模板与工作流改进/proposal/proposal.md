# 提案：让模板生成、评审和发布可复核

上一轮审核发现，误填打包输出目录可能替换项目内容，写范围和评审工具也会放过不符合契约的结果。用源模板生成项目文档后，作者还需要手工找缺失的链接及审批规则。这些问题会影响正常开发、验收和维护。

| 目标 | 可观察结果 | 承接 |
| --- | --- | --- |
| G1 保全项目及上一份产物 | 错版本、断链、越界或误指目录时，工具给出非零结果并保全原内容 | [验收规格](../spec/qa/acceptance.md) |
| G2 让独立评审绑定实际对象 | 评审区分阶段文档与实现，范围内状态和证据真实可查 | [验收规格](../spec/qa/acceptance.md) |
| G3 让项目能直接使用生成材料 | 低风险用一个 README，完整材料按轨道覆盖假设、失败、验收和回退 | [验收规格](../spec/qa/acceptance.md) |
| G4 精简角色和发布的共同说明 | 角色按风险调用，发布和宿主说明与实际能力相符 | [验收规格](../spec/qa/acceptance.md) |

范围覆盖本仓已识别的 28 项发现。沿用四个 Skill 和十个角色，保留已有项目文档体系的映射能力。现有缓存可走宿主支持的本地安装路径；远端发布和宿主全局规则保持各自的授权流程。方法效果仍需真实项目对照，本批只验具体行为。
