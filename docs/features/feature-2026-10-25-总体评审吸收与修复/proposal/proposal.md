# 总体评审吸收与修复批 — 需求提案

## 文档信息

- 需求名称：把 2026-10-25 会话总体评审的全部结论收口为一个批次的修复契约
- 所属阶段：`proposal`
- 目标阶段：`proposal → plan → 实施`（spec 与 design 由批次 README 段落映射豁免承载）
- 需求原文出处：2026-10-25 用户原话，逐字保留：
  > 提一个 feature，把你说的这些东西全都写进去，包括：
  > 1. 这些问题点；
  > 2. 打分点为什么打分；
  > 3. 将会怎么做、怎么优化。
  > 这些内容全都写在一个 feature 里面。
- 评审方法与边界：主对话全仓阅读（角色、skill、契约、工具、记录、模板）+ 三路独立深审（角色面 /
  文档面 / 门工具逻辑）+ `/tmp` 一次性副本上的破坏性探针 + 命令实测（门套件 11 项、linter 正反例、
  `validate.py installed`、安装快照清单、`grep` 与 `git log -S` 检索）。所有判据逐条给出出处或复现
  方式；深审结论中三处经主对话复核否决，未计入问题清单，单列于 §2.5。
- 状态：已成文，待独立评审与用户拍板（Q-01 至 Q-05）

## 一、背景与目标

### 1.1 背景

本仓当前版本（0.15.0，基线 `a2725a5`）提供 14 个角色档案、两个 skill、六份记录 schema 与 11 项
确定性门；门套件在干净解释器下 10 项 PASS（`lint` 因缺 ruff/mypy 记为失败），文档链自测 110 例、
回归测试 92 例全绿。2026-10-25 的总体评审在这个「全绿」的现状上给出四维结论：

1. **工程工艺与产品适配是两个分**。门与自测的判别力、fail-closed 取舍、受保护路径的威胁模型属于
   上游水平；但装完插件后主用户旅程断在第一步（门工具不随插件交付），端到端从未验证，方法有效性
   无度量。按内部工程产物口径约 8.5 分，按可交付产品口径约 4.5 分。
2. **生产「声明」的能力强于执行「声明」的能力**。三路深审从角色契约、测试契约、证据契约、门自身
   四个方向撞到同一堵墙：文档与发布说明声称被机器强制的检查，一部分没有任何代码执行，且回归测试
   的夹具站在弱契约一边（详见 §2.2 与 §2.4）。
3. **记录面已按实验室节奏增长，而消费者停了**。运行面 5,599 行，记录面 23,030 行（约 1:4）；
   改进环自评测装置 2026-10-12 裁撤后零候选、零发布记录，语料库仍在按天变大。
4. **仓内自评存在通胀先例**。同一棵树（`20724c0`）同一天的两份评测：独立十三维 6.43，主对话自跑
   九维 7.7——后者把维度从 13 缩到 9（删去「存在意义 / 竞品比对」）、架构分 6 提到 8，且引用了被
   前者实测证伪的「51/51 全杀」。本批把外部评审的 6.2 与该 6.43 并列留档，作为评分口径的对照锚。

### 1.2 目标（可判定）

- **G1 安装面闭合**：装完插件的宿主里，skill 要求执行的命令与链接要么真实可用，要么从安装面文本
  撤回——「18 处命令引用 + 6 条断链」的断裂面二选一收口，并有机器断言防回退。
- **G2 门逻辑补洞**：四组已复现的门绕过（未决项审批门、测试运行记录免检、表格解析盲区、schema
  类型 fail-open）全部关闭，每处配「破坏例转红」夹具；顺手修复三个已知工具缺陷。
- **G3 声明与执行对齐**：0.15.0 声称的测试契约与角色契约，要么被机器执行、要么声明撤回——消灭
  「文档说检查了、代码没检查」这一类债；角色文件按字面执行不再产出被自己门拒的产物。
- **G4 勘误可追平**：幽灵测试类（从未进入 git 历史的 `MutationKillCorpusTests` 与
  `SchemaSubsetFailClosedTests`）在全仓九处引用全部带勘误标注；新增「更正必须追平」与
  「证据断言可解析」两道检查，使追加式更正不再只落在作者顺手想起的位置。
- **G5 记录面回到产出比**：按既有删档规则补执行一轮——过程残渣（约一半记录面行数）在授权范围内
  清理，每刀都有规则出处，git 历史可回溯。
- **G6 表达与结构减负**：术语表落地入口文档、最小必读面压缩、文档链默认档与改进环处置按拍板
  结果落进对应载体。
- **G7 决策跨批次统一**：一个决策被推翻时，所有引用它的批次文档必须被点名——不需要任何人记得
  那个批次存在。决策获得活过批次的稳定身份（`DEC-` 编号）、修订链（r1…rN）、显式终态
  （取代 / 撤回 / 延后），下游文档以 frontmatter 声明所钉版本，反向索引由门计算而非人工维护；
  撤回允许声明「等价于旧版」，避免回到初始状态时制造整批假红。

### 4.2 决策跨批次统一（D8 的修法）

**先厘清一件事**：「以最新决策为准」这条规则本身正确且必须保留，但它只解决「两个说法都自称当前」。
它解决不了下面这种形状——某个批次写下「登录用手机号验证码」，二十天后这条能力被撤回，而那句话
毫无变化，它不知道曾经有过那次撤回。**「最新为准」需要一个前提：所有相关文档都能看到最新决策。
散文做不到，因为它没有指针。**

修法分四层，按性价比排序，只有第一层/第四层不动门：

| 层 | 内容 | 任务 | 是否门变更 |
| --- | --- | --- | --- |
| Tier 0 | `docs/PENDING-DECISIONS.md` 改为**只追加、永不移出**；决策编号加 `DEC-<YYYY>-<NNN>` 前缀；「未决视图」由脚本过滤生成，不再手工搬行。现状第 7 行「拍板后移出本表」正是销毁决策身份的源头 | T27 | 否 |
| Tier 1 | 决策记录带**修订链** r1…rN，终态三分：`superseded`（被新版涵盖）/ `withdrawn`（能力下线，须写代码与数据影响）/ `deferred`（决定不做）。允许 `equivalent_to: rK` 表达「回到旧状态」 | T27 | schema（受保护） |
| Tier 2 | 下游文档在 **frontmatter** 声明依赖（不放文档底部——门要读它）：`decision_deps: [{id, rev}]`，或只钉不变式 `{id, invariant: 登录须二次验证}` 使无关文档不随修订失效 | T28 | 是 |
| Tier 3 | 门自动计算**反向索引**并点名受影响文档：`decisions.py check` 只报真正受影响的（钉 r2 的报红，钉 r1 且 r4 等价 r1 的保持绿）；每条只能二选一——改文本并升版本，或显式登记 `stale_reason` + 复核日期 | T29 | 是 |
| Tier 4 | 决策索引由脚本 `--write` 生成，禁止手改 | T30 | 否 |

**两条必须坚持的设计约束**：

1. **反向索引算出来，不写出来**。手写反向表与「九项/十项检查」「95/78 测试数」是同一类东西，
   会自己腐烂。
2. **假红比假绿更伤门**。若只允许钉死版本，一次撤回会牵动几十个文档、逼出大量豁免，机制随即
   退化；因此必须同时支持「钉不变式」与 `equivalent_to`——`ISS-2026-060` 学到的是「0 findings
   是哪一种 0」，这里是它的镜像：「N findings 里有几条是真的」。

**立账门槛**（防止重演记录面膨胀）：一条决策只有满足以下任一条件才登记——① 有第二个文档复述
它（横向消费者）；② 它可能被推翻（时间风险）。一次性的、无下游引用的决定不立账。

### 4.3 目录去留执行口径

按 §2.6 判决表执行；每一刀的规则出处：外部记录迁出（6.43 评测建议二）、完成批次删档
（`docs/features/README.md` 纪律节）、快照去重与归档（记录冻结契约 L3 即删除）、CHANGELOG 压缩
（新增条目形态变更）。**全程不加新规则，只补执行既有规则。**

### 4.4 一条流程建议（不立任务，写进收口复盘）

冻结方法两周，在一个真实业务仓用三个 feature 走完整链，然后按「哪条规则真的拦住过一次错误」
删掉其余。支撑数据：61 条缺陷记录中 30 条归因工作流条款本身（`attribution: workflow_policy`）、
45 条来源为方法自身（`provenance: agentflow`）——四分之三的缺陷是方法在跟自己打架，
过程熵增已现。
