# Q-02 角色取向分析：14 角色重型治理 vs ~6 角色轻量工具

> 状态：待用户拍板。本文档是决策依据，不是决定。
> 关联：`docs/PENDING-DECISIONS.md` 第 8 条①；`proposal/prd.md` Q-02；`spec/be/backend.md` §3。

## 一、现状

### 1.1 角色清单（14 个）

| 角色 | 职责 | 典型触发场景 |
| --- | --- | --- |
| supervisor | 接案、分解、权限、集成、最终验证与决策 | 所有任务（宿主默认） |
| backend-engineer | 服务端 API、持久化、授权、校验、迁移 | 有界后端实现 |
| frontend-engineer | 客户端 UI、状态、可访问性、样式、前端测试 | 有界前端实现 |
| technical-director | 跨层架构决策、冲突方案、安全边界 | 跨层功能、契约变更、迁移 |
| reviewer | 独立评审实现（验收、正确性、回归、安全） | 编码后、文档评审 |
| plan-architect | 把设计结论转为版本化执行计划 | 纯规划请求 |
| test-planner | 设计测试计划与用例库 | 用户可见功能的自动化测试 |
| test-executor | 执行测试计划，写运行记录 | 测试计划已就绪 |
| bug-investigator | 检测、定位、归因 bug（只读） | 重要/不确定/跨层 bug |
| bug-fixer | 实现一个已诊断的 bug 修复 | 诊断已确认 |
| bug-recorder | 记录已接受的诊断与已验证的解决 | bug 修复已验证 |
| feedback-analyst | 分析用户反馈与任务结果，聚类归因 | 插件/角色指令改进 |
| candidate-engineer | 实现一个有界改进候选 | 证据/假设/判据已声明 |
| evaluator | 独立评审候选的基线/候选结果记录 | 候选已实现 |
| release-governor | 只读发布/拒绝/回滚决策 | 候选通过评测 |

### 1.2 实际使用模式

路由表（`skills/agentflow/references/roles.md`）显示，大多数任务只用 1-2 个角色：

| 任务形态 | 启用角色数 |
| --- | --- |
| 单层小修、复现明确 | 0（Supervisor 自己做） |
| 有界前端/后端实现 | 1-2（一名工程师 + 重要时 Reviewer） |
| 跨层功能、契约变更 | 3-4（TD → 双工程师 → Reviewer） |
| 纯规划请求 | 1-2（专家并行 → Plan Architect） |
| 用户可见功能测试 | 2-3（Test Planner → Test Executor → Reviewer） |
| 重要 bug | 3-4（Investigator → Fixer → Reviewer → Recorder） |
| 插件/角色改进 | 4（Feedback Analyst → Candidate Engineer → Evaluator → Release Governor） |

**关键事实**：14 个角色中，只有 supervisor 和 reviewer 出现在大多数任务中。其余 12 个角色只在特定场景触发。

### 1.3 显式过渡态

`roles.md` 的「收敛注记」明确声明：

> bug investigator、feedback-analyst、technical-director 与 evaluator 与 reviewer 画像同构
> （只读、证据进、结构化结论出），且**有意不**收敛进它：四者的输入契约与产出不同……
> 它们保持独立角色文件，是一个显式的过渡态；合并或重塑它们会改动公开角色面，属产品决策。

### 1.4 G5 测试现状

- 测试计划已起草：28 个用例（14 角色 × 2 场景），全部 P0 边界测试。
- 状态：**未执行**。没有通过率数据。
- 每个场景测试「角色在越权指示下是否拒绝」。

### 1.5 维护成本

每个角色有独立的 `agents/*.md` 文件，包含：
- frontmatter（name、description、tools、disallowedTools、maxTurns）
- 职责描述
- 边界规则
- 与其他角色的关系

14 个角色 = 14 份提示词 + 14 组边界规则 + 路由表维护 + G5 测试覆盖。

## 二、问题

> 2026-10-19 核查更正：本节原第 1 条「14 个角色全部在提示词中枚举」已不成立——`skills/agentflow/SKILL.md:15` 写的是「默认不加载完整角色列表」，T08 已完成（`PLAN-PRODUCT-001:102`）。真正的缺口不是提示词体积，而是入口仍分散在 14 个条目里：每次都要靠自由判断拼一条流程，哪一步可省、哪一步不可省只靠判断词定义，没有成链的默认序列。

1. **入口分散**：大多数任务只用 1-2 个角色，但每次都要从 14 个条目里现拼一条流程；提示词负担已经降下来了（按需加载），省下来的是"该用哪几个"这一步的决策成本。
2. **角色边界模糊**：bug-investigator / feedback-analyst / technical-director / evaluator 与 reviewer 画像同构（只读、证据进、结构化结论出），区别只在输入契约。实际使用中容易混淆。
3. **维护成本高**：14 个角色的提示词、边界、路由表、G5 测试都需要持续维护。角色越多，边界越容易漂移。
4. **G5 测试未执行**：没有通过率数据，无法判断哪些角色边界清晰、哪些重叠。

## 三、为什么改

### 3.1 产品定位选择

agentflow 的核心主张是「门禁是确定性程序，而非文字约定」。但角色面是文字约定最重的部分——14 个角色的边界只靠提示词约束。角色越多，文字约定的负担越重，与核心主张的张力越大。

两个方向：
- **重型治理框架**：保留 14 个角色，适合需要严格分工的场景。文字约定重，但粒度细。
- **轻量工具**：合并到 ~6 个角色，默认路径短，文字约定轻。14 个角色留作可选能力（进阶文档）。

### 3.2 架构结论已暗示方向

PLAN-PRODUCT-001 架构结论：
> 14 个角色是能力不是默认流水线。默认路径短；完整角色表进阶文档。

T08 已完成：
> 默认路径缩短：Skill 强调只启用有工作的角色；14 角色留作可选能力。

T14（本期不做）：
> 合并 Investigator/Analyst/TD 为 Reviewer。

**结论**：架构已经朝「轻量默认 + 可选能力」方向走了。Q-02 是把这个方向显式化——是否进一步合并角色面本身。

## 四、怎么改

### 4.1 方案 A：保留 14 个角色（不改）

- 默认路径已经缩短（T08 已完成）
- 14 个角色留作可选能力
- G5 测试执行后根据通过率数据再决定是否合并

**适合**：需要严格分工、角色边界清晰的场景。

### 4.2 方案 B：合并到 ~6 个角色

基于路由表实际使用模式和 T14 提案，一个可能的分组：

| 合并后角色 | 吸收的原角色 | 理由 |
| --- | --- | --- |
| Engineer | backend-engineer + frontend-engineer | 都是「有界实现」，区别只在服务端/客户端 |
| Reviewer | bug-investigator + feedback-analyst + technical-director + reviewer | 画像同构（只读、证据进、结构化结论出），T14 已提议 |
| Test Engineer | test-planner + test-executor | 都是「测试设计与执行」，一个角色覆盖全链路 |
| Improvement Engineer | candidate-engineer + evaluator + release-governor | 都是「改进候选的实现-评测-发布」，一个角色覆盖全链路 |
| Plan Architect | plan-architect | 保持独立 |
| Bug Fixer | bug-fixer + bug-recorder | 都是「bug 修复与记录」，一个角色覆盖全链路 |

加上 supervisor（宿主默认）共 7 个角色（6 个合并组 + supervisor；原文把总数写作「~6」，按本节分组实为 7）。

**注意**：这是一个示例分组，不是最终方案。具体合并哪些、保留哪些，需要根据 G5 通过率数据和用户偏好决定。

### 4.3 方案 C：渐进式（先执行 G5，再决定）

1. 先执行 G5 测试（28 个用例），获取通过率数据
2. 根据通过率数据判断哪些角色边界清晰、哪些重叠
3. 再决定是否合并、合并哪些

**适合**：希望用数据驱动决策，不急于改角色面。

### 4.4 方案 D（推荐）：保留角色文件，收敛「入口」

先看三个约束，它们决定了 14→6 不能靠"合并文件"实现：

1. **默认路径问题已经解过**（`SKILL.md:15`，T08 已完成）。剩下的不是"数量"，是"入口"——14 个条目没有成链的默认序列。
2. **规模很小，合并收益有限**：14 份 `agents/*.md` 共 599 行，最短的四个同构角色各 20–22 行，`roles.md` 全表 125 行。合并到 6 大约省 250 行提示词，但买入的是永久性的契约信息损失 + 一次门变更 + 28 例 G5 重写。
3. **两个硬约束挡住 14→6**：
   - `protected-paths.txt:42-43` 把 `agents/evaluator.md`、`agents/release-governor.md` 列为受保护路径——动它们是门变更，需人工授权 + 独立评审；方案 B 恰好把这两个并进 Improvement Engineer。
   - 独立性是这几对角色存在的理由：实现者不给自己评分（candidate-engineer ⊥ evaluator）、不给自己放行（candidate-engineer ⊥ release-governor）、改的人不写验收记录（bug-fixer ⊥ bug-recorder）、设计与执行分离（test-planner ⊥ test-executor）。`roles.md:56` 的收敛注记也已声明四个同构角色"有意不收敛"，理由是**输入契约不同**，不是画像不同。

所以可行的收敛维度是「入口」（6 条工作链），不是「文件」（6 个角色）。

- **D-1 路由表升级为 6 条工作链**：`roles.md` 已有「阶段 × 角色速查」与「路由表」，补的是每条链的默认序列 + 哪一步可省 / 哪一步不可省（硬边界）。Supervisor 只需认链 + 判 material，不再从 14 个条目里现拼：
  实现链（frontend/backend engineer → reviewer）、缺陷链（investigator → fixer → reviewer → recorder）、测试链（planner → executor）、规划链（TD → plan-architect）、改进链（feedback-analyst → candidate-engineer → evaluator → release-governor）、独立评审（reviewer 单点）。
- **D-2 先跑 G5**（28 例，已起草、`status: draft`、零门变更、零预算）。产出两个数：每个角色的拒绝通过率，以及**同一场景下两个角色的判定是否可区分**。判据先写死：只有"同一场景判定完全一致且输入契约同构"的一对，才进入合并候选。
- **D-3 允许的合并范围**：按现有约束，能动的只有不承担制衡关系的同层角色——实际只剩 backend-engineer + frontend-engineer 这一对（14→13）。其余任何合并都意味着放弃一项制衡，属产品定位变更：须先改 `roles.md` 的收敛注记与 prd 相关条款，再走 T14 决策，不在本批。
- **若目标是"新人只看到 6 个角色"**：正确的工具是打包分层（默认发行只带子集，其余作可选包），成本在五份 manifest 一致性守卫与 marketplace，建议单独立项，不要用合并角色文件来凑。

**收益**：零门变更、零受保护文件编辑、28 例 G5 不用重写、制衡关系保留、默认路径的目标（决策负担）确实下降。
**风险**：文件数不减（观感上"没变化"）；要编辑 `roles.md`（非受保护，但角色面从安装快照加载，改完需重装并复跑 `validate.py installed`）；入口收敛不做数据也能做，但仍建议先跑 G5，否则无法回答"哪一对真的可以并"。

## 五、收益

### 方案 B（合并到 ~6 个）的收益

1. **默认路径短**：Supervisor 只需读 6 个角色的提示词，而不是 14 个。决策负担降低。
2. **维护成本低**：6 份提示词 + 6 组边界规则，而不是 14 份。角色越少，边界越不容易漂移。
3. **与核心主张一致**：角色面文字约定越轻，「门禁是确定性程序」的主张越可信。
4. **G5 测试更简单**：6 个角色 × 2 场景 = 12 个用例，而不是 28 个。
5. **新用户友好**：6 个角色比 14 个更容易理解和上手。

### 方案 A（保留 14 个）的收益

1. **粒度细**：每个角色职责明确，适合需要严格分工的场景。
2. **无需改动**：不需要重新定义角色边界、更新路由表、重写 G5 测试。
3. **灵活性高**：用户可以根据任务需要选择任意角色组合。

### 方案 C（渐进式）的收益

1. **数据驱动**：用 G5 通过率数据支撑决策，而不是凭感觉。
2. **风险最低**：先测试再改动，不会盲目合并。
3. **可逆**：如果 G5 数据显示角色边界清晰，可以不合并。

### 方案 D（入口收敛）的收益

见 §4.4 末的收益/风险两行：核心是拿到方案 B 想要的"决策路径短"，但不付 B 的代价（门变更、28 例重写、独立性丢失）。

## 六、风险

### 方案 B 的风险

1. **边界模糊**：合并后的角色可能边界不清，反而增加混淆。
2. **信息丢失**：合并可能丢失某些角色的特定约束（如 evaluator 的「只读」约束）。
3. **G5 测试需重写**：28 个用例需要按新角色重新设计。
4. **用户习惯**：已经习惯 14 个角色的用户需要适应新角色面。

### 方案 A 的风险

1. **维护成本持续**：14 个角色的维护负担不会减轻。
2. **与核心主张的张力**：角色面文字约定重，与「门禁是确定性程序」的主张不一致。

### 方案 C 的风险

1. **延迟决策**：需要先执行 G5 测试，决策时间延后。
2. **G5 测试可能失败**：如果 G5 测试发现角色边界问题，可能需要先修复再决定。

### 方案 D 的风险

1. **文件数不减**：观感上"没变化"，需要向使用者解释"入口收敛"与"角色合并"的区别。
2. **编辑 `roles.md` 需重装生效**：角色面从安装快照加载，改完要复跑 `validate.py installed`，否则宿主跑的还是旧路由表。
3. **G5 仍要跑**：D 不取消 G5，只是把"决定是否合并"的前置条件从"凭感觉"换成"凭 28 例数据"。

## 七、决策点

| 决策点 | 选项 | 影响 |
| --- | --- | --- |
| 产品形态 | 重型治理（14 角色）/ 轻量工具（~6 角色） | 角色面、默认路径、维护成本 |
| 是否先执行 G5 | 先执行 G5 再决定 / 直接决定 | 决策时间、数据支撑 |
| 合并方案 | 方案 B 的示例分组 / 自定义分组 | 角色边界、G5 测试设计 |
| 收敛维度 | 入口（6 条链，方案 D）/ 文件（6 个角色，方案 B）/ 打包分层 | 门变更量、制衡是否保留、G5 是否重写 |

## 八、建议

1. **推荐方案 D**：先收敛入口（6 条工作链写进路由表），文件数不动。它拿到方案 B 想要的收益（默认决策路径短），不付 B 的代价（门变更、独立性丢失、28 例重写）。
2. **并行跑 G5**（方案 C 的第一步）：28 例、零预算，产出"哪一对角色真的不可区分"的数据。没有这个数，任何合并都是猜。
3. **数据出来后再谈合并**：若 G5 显示 backend/frontend engineer 在同一越权场景判定完全一致，可合并这一对（14→13）；其余对若也要并，先改 `roles.md:56` 的收敛注记与 prd 对应条款，走 T14 决策，另批次处理。
4. **方案 B 只在产品定位改为"轻量工具、放弃独立评审制衡"时才成立**，那不是本批的优化项，而是一次定位变更。
5. **若目标是观感上的"6 个角色"**，走打包分层（D-3 末条），单独立项。
