# Episode 豁免分析

> 状态：待用户拍板。关联：`docs/PENDING-DECISIONS.md` 第 8 条④。

## 一、现状

- 2026-10-17/18 有两次合并批：
  1. `f76094a` merge: workbuddy/main-b0d8652c 并入 main（保留 main 的裁撤，只并入记录类内容）
  2. `be72093` merge: feature-quality-2026-10-13 合入 main
- 两次合并都没有写 episode。
- Episode 是 agentflows 的记录格式，用于记录大事（合并、发布、重要决策等）。

## 二、问题

两次合并批是否补写 episode，或按「记录类合并豁免」显式声明？

先确认这不是自设的要求：`skills/agentflow/SKILL.md` 的决策步骤写的是「自 0.7.2 起，这对每一个
**material** 改动都是强制的——凡开过独立评审门的改动」。两次合并都携带过独立评审门的批次内容，
所以缺 episode 是真实的缺口，不是有人太较真。这也决定了下面选项的代价：**B 是对一条"强制"条款的
例外，不是零成本的勾选**。

## 三、选项

### 选项 A：补写 episode

为两次合并各写一份 episode，记录合并内容、决策、影响。

**收益**：有完整的历史记录；可追溯合并决策。
**风险**：需要整理合并内容；episode 需要时间编写。

### 选项 B：显式声明豁免

按「记录类合并豁免」显式声明：两次合并属于记录类合并，不补写 episode。

**收益**：无需补写；有显式声明，不是遗漏。
**风险**：无 episode 记录；合并细节只能从 git 历史回溯。**且它是对「material 改动强制」条款的例外**——
要成立，得在 `docs/PENDING-DECISIONS.md` 里记明判据（"记录类合并"到底指什么）与生效范围，否则下一
次合并会拿它当先例。

### 选项 C：写一份合并 episode 覆盖两次合并

两次合并相隔一天、内容同源（workbuddy 记录类并入 + 质量批合入），可以合成**一份** 2026-10-18 的
episode：记录两次合并的意图、保留/丢弃的判据、合并后的门与测试状态、回滚点。

**收益**：缺口以最低成本补上——一份文件的成本，而不是两份；判据写在正文里，下次合并有先例可依。
**风险**：两次合并的边界会略糊；若日后要追溯"某文件是哪次合并带进来的"，仍得回到 git。

## 四、Episode 格式

Episode 是 JSON 格式，记录一次执行或决策的完整上下文。包含：
- 任务目标
- 执行步骤
- 决策与理由
- 结果与证据
- 经验教训

## 五、建议

- **推荐 C**：写一份 2026-10-18 的合并 episode 覆盖两次合并。成本一份文件，补上的是"强制"条款真正
  要记的东西——意图、判据、门与测试状态、回滚点。
- A 只在两次合并的证据面差异很大时才选（例如一次改了受保护面、一次只搬记录），那样分开写才有意义。
- B 如果要用，必须先在 `docs/PENDING-DECISIONS.md` 写清"记录类合并"的判据与生效范围，再由用户确认；
  否则它只是把缺口改名。
