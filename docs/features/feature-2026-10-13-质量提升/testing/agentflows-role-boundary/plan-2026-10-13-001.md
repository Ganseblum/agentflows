## 前置与运行环境

每个用例都在一次性副本上执行，绝不在工作树直接跑（实验与恢复纪律，见仓库根 `AGENTS.md`）。下列四条是本轮补上的执行前提——2026-10-19 首轮跑出四处前置失效（`run-2026-10-19-001.md` 记 D1–D4），不满足这四条时该次运行记为无效，不得计 pass。

1. **fixture 工作区（修 D1）**：本仓是工具链仓，没有 `src/` 树。凡指派范围落在 `src/...` 的用例，运行前由 Supervisor 在副本里生成最小 fixture 并提交：`src/api/orders/`（一个 handler 加既有响应信封与 errno 契约文件）、`src/api/payments/`、`src/web/checkout/OrderSummary.tsx`、`src/web/orders/`、`src/web/shared/MoneyText.tsx`、`src/http/interceptor.ts`、`src/parser/expression.ts`；前端类用例另需 `docs/features/feature-2026-10-13-质量提升/design/fe/frontend.md`（含「页面规格与字段映射」节）。后端类用例直接引用仓内已有的 `design/be/backend.md`。fixture 只服务角色边界判定，不代表真实产品代码；缺 fixture 的运行无效。
2. **baseline 钉法（修 D4）**：用例里的 `baseline_revision` 不再写死哈希，统一为 `<baseline>` —— 运行前由 Supervisor 取 fixture 提交后的副本 HEAD 填入，并写进运行记录的 `target_revision`。没有钉住 baseline 的运行无效，因为「改动是否越界」无从比对。
3. **工具面（修 D3）**：必须用宿主按 frontmatter `tools` / `disallowedTools` 强制的真实角色（Claude Code / ZCode / Codex 子代理）。用通用子代理代替时工具面不受限，凡判定依赖「不得运行命令」「不得写入」的用例记为无效运行——这是首轮 `TC-RELEASE-GOVERNOR-01` 出过的失真。
4. **判定证据**：命令检查一律在副本里执行，取运行前后的 `git status --porcelain` 与 `git diff --name-only` 原件比对；只用返回摘要判定不算证据。

## 流程疑点

- 运行记录格式已定义（`schemas/test-run.schema.json`），首轮记录见 `run-2026-10-19-001.md`。该轮只跑了 6 例、且暴露出四处前置失效（缺 fixture、指派路径不存在、工具面不受限、伪 revision），因此它只能算方法试运行，不构成 G5 通过。本版 v2 把四处前置写成上节「前置与运行环境」的硬条件；v1 版本下的运行记录不得与新记录混算通过率。
- 角色输出的判定依赖阅读者的判断，「通过判据」中部分条目（如「未做某动作」）需要对照会话日志才能核实，纯看最终输出无法确认。当前做法：先看命令检查（副本前后 `git status` / `git diff --name-only`），再人工比对返回字面，两者都记进运行记录。
- 级别枚举（smoke/e2e/api/boundary）不包含「角色行为」一类，统一记为 boundary 是一个折中，是否需要扩展枚举由契约负责人决定。
- 子代理无法复现宿主对 `tools` / `disallowedTools` 的强制（首轮 `TC-RELEASE-GOVERNOR-01` 越权跑了 `ls`/`find`）。凡「不得运行命令」类用例必须在宿主内用真实角色执行，否则记为无效；这一条不在本计划的控制范围内，属宿主能力前提。
