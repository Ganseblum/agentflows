# 追溯闭环与证据在场批 — 验证方案（design/qa）

> 前置输入：`spec/qa/acceptance.md` §2 边界覆盖与 §4 验收点。本文件给出用例库与执行安排；
> 用例编号形态 `TC-<域>-<NN>`，与本批 `spec/qa/acceptance.md` §5 的映射一一对应。

## 0. 先说结论

| 问题 | 结论 |
| --- | --- |
| 怎么证明新门真的会红 | 每条判据都有负例：linter 侧进 `--self-test` 夹具（内存文件系统，不污染仓库），门侧进 `tests/test_lab_contracts.py` 回归测试 |
| 怎么证明不误伤 | 正例 + 「未打标批次不产出 finding」的专门夹具各一条（G1-AC-04） |
| 谁执行 | 检查器由本批实施时在真实仓库跑并留原始输出；独立评审者只读，命令由评审者拟定 |
| 失败怎么办 | 判据过宽收窄实现并补夹具；不允许给批次摘标记、不允许改判据文字来放行 |

## 1. 分层与顺序

| 层 | 目的 | 命令形态 | 顺序 |
| --- | --- | --- | --- |
| 判别自测 | 钉住检查器自身 | `python3 tools/lab/doc_chain.py --self-test` | 最先，红则不进入后续 |
| 回归测试 | 钉住契约与实现（schema、门禁行为） | `python3 -m unittest discover -s tests` | 其次 |
| 活体检查 | 在真实批次目录与仓扫上跑 | `doc_chain.py docs/features/feature-2026-10-22-追溯闭环与证据在场`；`doc_chain.py --repo .` | 第三 |
| 全套编译 | 门禁整体 | `python3 tools/lab/validate.py all`（项数以 `--list` 自报） | 最后，且发版前复跑 |
| 变异测试 | 证明新门能被破坏 | `python3 tools/lab/mutate.py`（在 `/tmp` 副本内运行），报告落本批 `testing/agentflows-gate-evidence/` | 全套绿之后 |

## 4. 流程疑点（交独立评审者裁决，不作决定）

| 编号 | 疑点 | 为什么会发生 | 建议处置 |
| --- | --- | --- | --- |
| V-01 | 一处事实有三个载体：承接表、计划看板、README 的模块进度总览。C22 只校前两者的聚合一致，第三处（模块总览）无人对照——「表绿看板红」与「总览落后于看板」都是同一形态 | 回写只允许动计划两列，承接表由人工同步 | 由 C22 状态聚合检查在每次目录模式运行时抓取；模块进度总览这一处仍靠人工回写，登记为未收口的残余（不做成第四处自动判据，因为它的列形态比承接表更自由，硬判会误伤） |
| V-02 | 同一批次被目录模式与仓扫模式各跑一次，是否可能给出不同结论 | 两个入口若分别实现必然漂移 | 设计上强制共用实现（GAP 与 §1.4.4）；TC-TRACE-05 实测一致性 |
| V-03 | `disposition` 只服务 C18，读者可能误以为是状态机的新取值 | 字段名与 `status` 形似 | 在记录根 README 与 schema description 双向写明「不参与状态机」；本批一并补 |
| V-04 | C23 只判载体存在，不判内容质量，是否会被「写了个无关路径」绕过 | 载体识别必然是形式判定 | 如实登记为残余风险：内容质量由独立评审与 `artifacts` 的交叉引用负责，本批不假装能机器判优 |
| V-05 | 一条新判据报 0 findings，读者无法区分「真没问题」与「根本没看到对象」 | 本批实现期内三次踩到（plan 扫描非递归、任务号常量遮蔽、反引号 ID 方言不认），前两次夹具与统一口径才暴露 | 新增判据时必须同时给「正例 + 破坏例 + 未打标不误伤」三类夹具，并要求 0 findings 的结论附上扫描到的对象计数；本批的 C22/C23 已按此配齐（用例 86–106） |

## 5. 执行与记录安排

- 本批的用例执行结果记在计划看板（`plan/PLAN-TRACE-001.md`）各任务的证据列，不另开运行记录文件；
  门基线与变异报告这两份原始产物落 `testing/agentflows-gate-evidence/`，由证据列引用。
- 独立评审由只读评审者执行：命令与预期由评审者拟定，实施方不得替换；原始输出逐字回传。
- 任何检查无法复现时记为「未运行」并写进计划风险列，绝不记为通过。
