## 一、背景与目标

### 1.1 背景

本仓把「文档链是编译产物」做成了确定性门：`tools/lab/doc_chain.py` 按判据清单逐条检查（清单以该文件头注释为唯一真源），
`tools/lab/validate.py` 的门禁项以 `--list` 自报，记录根有 schema 契约。2026-10-22 的走查给出三类反证：

1. **声明与实现之间的环没有门。** 一条提案目标可以在下游彻底消失。实证：
   `docs/features/feature-2026-10-13-质量提升/proposal/prd.md:24` 的 G2 把「CI 在真实 runner 上
   连续两次通过」列为目标，同文件 §四 把它决策为「做」；而 `spec/be/backend.md` §5 的六个模块、
   `spec/qa/acceptance.md` §4 的验收点、`plan/PLAN-QUALITY-001.md` 的十个任务行里，CI 出现 0 次。
   下游只在 `design/be/backend.md` 的外部依赖表（`强依赖（G2）`）与影响面 checklist（`CI 结果 | 首次实跑，结果未知`）两处把它登记成一条待确认依赖。没有任何检查会因此变红。
2. **「已完成」的证据可以在盘上不存在。** 同一份计划的 T01 行证据是
   `/tmp/quality-baseline/validate-all.txt`，T05 行是 `/tmp/mutation-report-v2/results.json`，
   两处都在计划文本里自述「已随 /tmp 清理散失，不可复核」，任务状态仍是 ☑ 已完成。
   本仓自己的规则写着「无法复现的检查记为未运行，绝不计为通过」，但门只看状态字形是否合法。
3. **新造的门可以零采用。** 0.12.0 发布的决策可追溯检查（C15 至 C18）是标记启用式的：
   三个标记在本仓只出现在规则载体（`AGENTS.md`）、发布说明（`CHANGELOG.md`）与正反例夹具
   （`examples/decisions/`）里。`docs/PENDING-DECISIONS.md:27` 这个唯一的拍板口用的是五列
   （`来源 | 待决问题 | 推荐 | 状态`），而 `AGENTS.md`「决策记录与台账」节（该节现位于 `AGENTS.md:110`，行号会随文档改动漂移，故按节名引用） 规定拍板口条目用八列。
   `validate.py decision_gate` 因此绿在夹具上，活文件一条都没进检查。
   顺带暴露一个契约缺口：`AGENTS.md` 与 `tools/lab/doc_chain.py` 的 C18 都把
   `disposition: deferred/not-doing` 当作开放记录的合法豁免通道，但
   `schemas/bug-record.schema.json` 的 `properties` 里没有这个字段且 `additionalProperties: false`
   ——照条款写就编译失败，豁免通道在 schema 层根本不存在。

另有八处文本与双源缺陷（编号重复与编号顺序、过时决策标注、退役路径措辞、同一结论两处并存、手写门项计数、文件名口径、编号歧义、验收点回写口径），
走查时逐条定位到行，见缺口台账。

### 1.2 目标（可判定）

- **G1 目标承接可机判**：批次 README 的目标承接表成为机器检查对象——提案里声明的每个目标必须同时
  在 spec 模块表、验收点和计划任务行有落点，缺任一环当天即红；表里引用的任务号与验收点必须存在。
- **G2 任务证据可在盘**：计划看板上标 ☑ 已完成的行，其证据列必须含可复核载体（仓内存在的路径、
  `仓库@修订:路径`、可在 git 历史解析的提交号，或显式 `N/A: 理由`）；只指向 `/tmp` 的证据不通过。
- **G3 决策门照到活文件**：C15 至 C18 的检查对象不再只有夹具——拍板口补齐八列并打标，
  开放记录的显式豁免通道补进记录契约并逐条登记，使 `validate.py decision_gate` 的绿来自真文件。
- **G4 规范文本自洽**：走查发现的文本缺陷（编号重复、过时决策、退役路径措辞、双源条款、
  手写门项计数）全部修复，并把「同一结论单点成文」的既有纪律应用到本批触及的规范文件。
- **G5 发布可核**：门变更经独立评审并留下评审记录，五份 manifest 同步版本、CHANGELOG 有条目、
  生成树重建并与源面一致，episode 落盘含**每一轮**评审（含 `changes_requested` 的分歧与收场）。
  安装面按本批范围（不重装）如实登记为「差异已声明、未验证」，不冒充通过——把「宿主装到了」
  写成本批达成的目标，会在批次自己划的范围外留一条永远过不了的验收点。

## 二、产品定位与核心原则

本批不改变产品定位：Agentflow 仍是宿主原生的多角色开发方法插件，`tools/lab/` 仍是它自己的
确定性控制面。本批加强的是三条既有原则在执法面上的兑现：

| 原则 | 本批如何兑现 |
| --- | --- |
| 证据编译：声称做过的必须能在盘上复现 | C23 把「证据列可解析」从散文纪律变成检查 |
| 治理优先：门必须照到真文件，不能只照夹具 | C22 与 G3 把两项检查的采用面从 0 推到活批次与拍板口 |
| 诚实声明：做不到的如实登记 | 16 条外部记录显式 `deferred`，不再靠「没打标所以不红」 |

## 六、成功指标与可观测性

本批不产出用户可见行为，**埋点决策：N/A**（无事件新增、无复用、无口径变更；理由：改动面是仓库内的
检查工具与文档，不触达任何采集端点或事件表）。可观测性落在门自身信号：

| 维度 | 指标 | 口径 |
| --- | --- | --- |
| 目标承接 | 缺承接的目标数 | `doc_chain.py <批次目录>` 的 C22 findings 计数，目标 0；接入面为打标批次 |
| 证据在场 | ☑ 行证据不可解析的任务行数 | 同上的 C23 findings 计数，目标 0 |
| 决策门采用面 | 带 C15/C16/C18 标记的活文件数（不含夹具与规则载体） | `python3 tools/lab/doc_chain.py --repo .` 前扫一遍仓的标记计数；本批目标 ≥2（拍板口 + 本批 README） |
| 门可信 | 整门变异杀死数 / 总数、存活数、无效数 | `tools/lab/mutate.py` 在 `/tmp` 副本内跑，报告落 `testing/agentflows-gate-evidence/`，逐项目可复核 |
| 编译状态 | `validate.py all` 红项数 | 全套检查退出码与逐字输出，目标 0（环境依赖缺失记为未运行，不计通过） |
