## 2. 核心语义

1. **承接是双向闭合的**：目标必须在下游有落点（缺承接即红），下游引用的编号必须在上游存在
   （幻影引用同样红）。单向检查会鼓励「随便写一行承接」，所以两条同批实现。
2. **状态一致性优先于状态丰富度**：承接表的状态列只与计划看板比对，不引入新的状态词汇。
3. **证据在场只判「能不能复核」**，不判「内容好不好」。一条写了 `N/A: 纯文本改动，门输出即证据`
   的行通过；一条只有 `/tmp/...` 的行不通过。
4. **C22 沿用标记启用式**，与本仓 C11、C15 至 C21 的取舍一致：未打标的历史批次不被强制改写；
   差别在于本批把标记真正打到了活文件上，采用面从 0 变为非 0。**C23 不启用标记**：证据列本就在计划契约里，
   把它变成 opt-in 等于让最容易造出假「已完成」的那一环继续无人看管。

## 6. 字段口径

### 6.1 目标承接表（C22 的载体）

必需列：`目标`、`proposal 出处`、`spec 承接`、`plan 任务`、`状态`。列顺序不限，表题须含「目标承接」。

| 列 | 合法形态 | 机器判据 |
| --- | --- | --- |
| 目标 | `G1`…`G9` | 与 `proposal/` 文本里出现的 `G\d+` 集合双向相等（缺项红、幻影红） |
| proposal 出处 | 反引号路径（可含 `§` 或行号） | 路径须在本仓可解析（相对批次目录或仓根） |
| spec 承接 | 至少一个模块号 `M-[A-F]` 或 `Gn-AC-*`，可附反引号路径 | 模块号须存在于 `spec/` 文本；AC 编号须存在于 `spec/` 文本；反引号路径须可解析 |
| plan 任务 | 一个或多个任务号，方言与 C9 同一条（`T`/`FT` 前缀、1–2 位数字，反引号包裹也认） | 每个任务号须存在于本批次 `plan/` 任务表；且计划中状态为已完成或阻塞的行必须被至少一行引用（孤儿任务红） |
| 状态 | 已完成 / 进行中 / 未开始 / 阻塞 / 本期不做（字形取值以 `docs/features/README.md` 计划形态节的固定枚举为准，本表不重复列举字形） | 与所引任务行的聚合一致：全部为已完成行时才允许写已完成；出现进行中、未开始或阻塞即要求降级为对应值 |

### 6.2 证据载体（C23 的判据对象）

`☑ 已完成` 行的证据列须含以下至少一类，缺一即 finding：

| 载体 | 识别形态 | 判定方式 |
| --- | --- | --- |
| 仓内路径 | 反引号内或裸写的相对路径 | 首段是本仓真实条目且路径存在（复用既有 `_ref_is_in_repo` 语义，外部仓引用不误判） |
| 仓限定引用 | `<repo>@<rev>:<path>` | 形态匹配即通过（跨仓事实按本仓不可达处理，与记录契约一致） |
| 提交号 | 7–40 位十六进制，或 `agentflows@<sha>` | `git cat-file -e <sha>^{commit}` 成功；git 不可用或对象缺失时不算可复核 |
| 显式不适用 | `N/A: 理由` | 冒号后必须有非空理由 |

`/tmp`、`~/`、绝对路径不计入可复核载体；若整行只有这类引用，判 finding 并给出替换建议。

### 6.3 `disposition` 字段

可选字段，仅与 C18 归属检查相关：`deferred`（本期延后，归属他处）或 `not-doing`（决定不做）。
`status: open` 且既不在打标批次承接表、又无 `disposition` 的记录才红。字段不改变状态机取值。
