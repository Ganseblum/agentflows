# L3 工作流增强提案

## 需求原文

> 全部补息以及增强。如果有需要冗余的地方，就把它全部干掉。包括整体的结构目录，甚至你都可以大幅改造，只要保证可用性，或者说合理性就行。

“补息”按前文上下文理解为“补齐”。用户要求实施此前确认的十四项吸收建议，并允许为去重和可用性改造结构。该请求包括为这些目标必需的执行契约、受保护脚本、检查及回归测试改动；最终结果仍需独立评审。不包含提交、推送、发布、宿主重装、全局文件写入和平台部署。

## 1. 目标与范围

### 1.1 要解决的问题

已有方法对角色、文档、来源和独立评审约束较完整，但行为变更的测试前置、执行输入绑定、原生测试报告核对、遗留补测和托管写入缺少统一可执行路径。相同规则重复出现在入口、角色和指南，使用者需要反复拼接流程。

### 1.2 目标

- G1 把测试前置、有效失败、小步实现、环境准备、证据复用、覆盖复核、简短入口和已答复复用接入同一执行协议。
- G2 用一个可移植证据工具实现计划指纹、报告映射、补测盘点、依赖分流和托管预览保护；继续以既有计划及测试记录为状态权威。
- G3 以可判定的风险边界裁剪简单任务文档，合并同义规则与重复入口，保留复杂任务设计与独立评审。
- G4 保证回归、文档链、源面与生成树一致性，并留下可复跑的真实命令证据。

## 2. 用户与场景

使用者在宿主中提出行为修改、缺陷修复或遗留补测。任务负责人确定范围和真实验收，执行者在已授权范围内持续推进；证据工具绑定输入与实际输出，独立评审检查断言与覆盖。

## 3. 范围决策

| 范围 | 决定 | 理由 |
| --- | --- | --- |
| 八项规则与模板增强 | 本批实施 | 用户已要求全部补齐 |
| 六项执行或流程改造 | 本批实施 | 用共享机制替代平行方案 |
| 新角色、第二套模型循环、任务数据库 | 不新增 | 现有宿主与角色已经承载执行 |
| 公司平台整套接入、自动升级、对话收集密钥、遥测 | 不引入 | 不属于通用方法增强 |
| 历史记录 | 不改写 | 保留来源与已发生证据 |
| 宿主安装、推送和发布 | 不执行 | 用户当前要求本地实现与验证 |

## 4. 约束与决定

现有测试记录和计划继续作为事实来源。执行计划JSON与结果JSON只作证据，不另建任务状态系统。重复原则集中到执行协议，角色只保留分工和引用。简单任务的轻量条件必须可判定，涉及公开契约、持久化、权限、跨模块时序或不可回退动作的任务仍走完整设计。

无需要再次收集的产品选择；用户已授权全部实施及合理结构调整。实现不降低原始证据、独立评审、两次同因失败停止和受保护门要求。

## 5. 验收与非目标

验收见 `spec/qa/acceptance.md`。不宣称文本改造已提升模型成功率；方法疗效沿用 `measurement: none`，只报告实际验证的工具与文件行为。
