# 规格：工程基线吸收批

## 0. 需求提案反审 checklist

| 不合规项 | 结论 | 处置 |
| --- | --- | --- |
| 目标是否都可判定完成 | 合规 | 四目标各对应验收点，见 `spec/qa/acceptance.md` §3 |
| 是否混入了未授权范围 | 合规 | 不做事项表（proposal §1.3）逐条给出理由；P2 可选项未纳入 |
| 是否与既有拍板冲突 | 合规 | 只扩展模板与 Init 文字，不改 `contracts.md`、`schemas/`、`tools/lab/`；不触碰受保护面 |
| 是否存在需要用户拍板才能推进的分支 | 合规 | 范围与档位已在 2026-10-28 的问答中拍定 |
| 是否声称了未验证的疗效 | 合规 | 全批 `measurement: none`；只报告文件与门的行为 |
| 是否把项目事实写成通用默认 | 合规 | 模板一律留 `<填>` 占位，并在开头声明「形态不是默认值」 |

## 1. 模块与验收点

### M01 目标仓工程基线（G1）

**契约**：新增 `skills/agentflow/templates/engineering/baseline.md`，作为「目标仓工程基线」的可复制骨架。
模板必须包含下列十个固定小节（0–9），缺任一即不合格：

| 小节 | 必填内容 | 不适用时 |
| --- | --- | --- |
| 0 适用范围与优先级 | 本仓规则与通用基线的优先级；冲突裁决入口 | 不适用须写理由 |
| 1 技术栈与运行环境 | 语言/框架/版本/包管理器/运行时；多应用或多站点清单（应用名、目录、技术栈、构建命令、部署形态） | 单应用写「单应用」 |
| 2 目录与文件职责 | 允许目录、禁止的平行目录、每类文件职责与落点 | — |
| 3 命名与类型 | 目录/文件/组件/Props/Hook/Store/接口/DTO 命名；ID/金额/时间/枚举字段口径 | — |
| 4 禁止的平行方案 | 不得引入的框架、库、目录、命名，及替代方案指向 | 写「无额外禁令」 |
| 5 新增模块必做清单 | 入口、路由、视图、状态、接口、类型、构建注册、导出、测试、文档 | — |
| 6 测试栈与运行方式 | runner、配置、命令、环境预检、允许补齐的边界、Mock 边界、禁止引入的平行体系 | — |
| 7 质量门与顺序 | typecheck → lint → test → build 的实际命令；pre-commit / CI 归属；失败不得绕过 | 无钩子写「无钩子」 |
| 8 配置与边界 | 配置归属与读取入口、覆盖顺序、生效方式；限制项的对象/单位/上下界/超限结果/权威来源 | — |
| 9 规范入口与规则写法 | 规范分册索引 + 任务类型→读取清单；一条规则的稳定编号/适用/级别/要求/例外/执行/演进 | 单文件规范写「单文件」 |

**Init 契约**：`SKILL.md` 的「首次接入（Init）」第 1 步由「与用户确认五项」改为六项，新增
「工程基线」；第 2 步要求接入小节写明「工程基线入口」——目标仓已有规范时登记入口路径，
没有时用模板与用户确认后落一份最小基线。工程基线缺失的事实按缺口上报，不按通用默认推断。

验收点：G1-AC-01 至 G1-AC-03。

### M02 后端数据与配置设计核对（G2）

**契约**：`templates/feature/design/be/backend.md` 必须提供两张可填写的核对表：

1. **字段与数据设计核对**（新增小节）：至少覆盖下列核对项，每项要求写「已覆盖 / 缺口 / 不适用+理由」
   与载体（DDL / 接口契约 / 测试）：
   - 字段类型、空值、默认、单位、范围、精度与敏感性；
   - 字符长度与字节长度不混用；
   - 时间点与自然日期区分，枚举与 JSON 的职责；
   - 索引与查询组合匹配，分页稳定；
   - 列表查询无 `N+1` 或无界扫描，批查有规模与部分失败语义；
   - 并发更新有事务、锁或 CAS 方案，幂等回放有处理；
   - 迁移有命名、回填与回滚，并在真实库上验收。
2. **配置项与运行边界**（替换原三列「配置键」表）：配置项至少含键/代码字段、业务作用、类型与单位、
   默认与来源、必填条件、合法取值、可见性、覆盖顺序、生效与生命周期、失败行为、部署映射、验证；
   运行边界至少含限制项、适用对象、单位、上下界、特殊值、超限结果、权威来源。

`agents/backend-engineer.md` 必须写明：新增或修改持久化字段、迁移、配置项与运行上限时，按简报引用的
核对表逐项给出结论；缺口以「requires design」上报，不自行编值；不手写通用解析，前端提示不替代服务端校验。

验收点：G2-AC-01、G2-AC-02。

### M03 原型可点性与 Mock 约定（G3）

**契约**：`templates/feature/prototype/README.md` 的「交付前自检」必须新增下列人工核对项：

| # | 核对项 | 判定 |
| --- | --- | --- |
| P1 | 每个可见控件有真实反馈，或明确 `disabled` | 浏览器逐页点击 |
| P2 | 隐藏态（hover 工具条、折叠区、内嵌面板）能通过交互显现并可操作 | 浏览器走查 |
| P3 | 列表页有工具栏与行内动作；详情或编辑至少能打开 Modal / Drawer | 逐页目检 |
| P4 | 假数据形态与真实接口一致（字段名、枚举值、ID 形态、分页结构），数值随筛选或时间范围变化 | 对照接口契约 |
| P5 | 无法演示的能力标注「演示 / 规划稿」，不用 toast 冒充已实现；原型不发网络请求、不引外部资源 | 目检 + 网络面板 |

同一判据在 `references/document-chain.md` 的产品原型节写一句指针；两处都注明「人工执行，插件没有
对应的机器门」。脚本扫描只能作线索：实测初筛报「问题页 102 页 / 死按钮 1403」，逐页核对后真实缺口 8 页；单位不同不能直接算误报率。

验收点：G3-AC-01、G3-AC-02。

### M04 测试设计的三类易漏维度（G4）

**契约**：`templates/testing/plan.md` 的「覆盖方向自检」必须新增三行：

| 方向 | 判定问题 |
| --- | --- |
| 并发与竞态 | 连点、重复提交、旧请求晚返回覆盖新状态、重试导致重复副作用，是否有用例或范围外声明 |
| 生命周期与清理 | 卸载后回调、路由切换残留、轮询/监听/Observer/对象 URL 是否释放 |
| 契约与兼容 | 字段省略、空串、`null`、零值、未知枚举、旧数据与老配置是否被正确处理 |

并在表下写明「按功能形态取最小必测集」：表单提交、异步列表、上传、登录/会话、配置开关各自至少覆盖
主路径、最关键失败、状态切换与重复提交；未覆盖的形态显式声明。`agents/test-planner.md` 指明这三类
维度与最小必测集的取舍要写进计划，不得静默省略。

验收点：G4-AC-01、G4-AC-02。

### M05 前端实现纪律与设计核对（G5）

**契约**：下列五个落点必须同时具备。

1. `agents/frontend-engineer.md` 必须含五组实现纪律：
   - **请求、缓存与生命周期**：取消或请求身份校验、晚到响应不覆盖新状态、监听/定时器/订阅/Observer/对象 URL 的释放方、缓存键与写后失效、登出/切账号隔离、401 单一入口、服务端数据与客户端状态不双源、派生值不用 Effect 复制；
   - **契约字段与类型边界**：省略/`null`/空串/零值/空数组的区分、金额与点数精度、时间/枚举/ID 口径、必需动作使用必需回调、外部输入从 `unknown` 收敛、`import type`、共享契约归低层、纯计算/service/store 的依赖方向、别名与桶导出；
   - **性能、可访问性、媒体与配置**：先测量再优化、稳定 key、重模块延迟加载、加载/空/失败/权限/取消状态保留、可访问名称/label/焦点/键盘/颜色不作唯一提示、长文本/溢出/窄窗、构建资源与 public 分置、私有媒体与凭据不进公开目录、Blob/签名 URL、只用公开配置、前端校验非权威、边界值来自 `design/fe`；
   - **注释与拆分**：注释只写非显然的原因/约束/单位/失败/生命周期、TODO 关联承接事项、按职责/复用/可测性拆分、行数是审查信号不是硬门、孤儿代码删除、不批量改写存量。
2. `templates/feature/design/fe/frontend.md`：§1.3 增缓存键与失效、身份与生命周期两行；§1.4.3 增「省略/null/空串/零值/空数组」「金额/点数/大整数」两行；§1.4.5 增取消与资源释放、登录态与权限变化、写后缓存失效三行；§4 自检增四条。
3. `templates/feature/spec/fe/frontend.md` 增 §2.1 前端行为口径表：数据刷新与去重、并发与晚到响应、身份与权限、字段空值语义、键盘与可访问性、媒体与下载。
4. `templates/engineering/baseline.md` 增请求层与客户端边界段，以及 UI、文案与可访问性基线（多站点、i18n 成对落键、可访问性、格式与命名）。
5. 项目特定 FE 约定不进入方法仓：`IProps`/`I` 前缀、Tailwind 规范类、断点数值、站点白名单、SVG 引入方式、行数阈值只在工程基线登记。

验收点：G5-AC-01 至 G5-AC-04。

## 2. 设计决定（不留悬空）

1. **只吸收形态，不吸收数值与业务事实。** 模板中的目录、命令、上限一律是 `<填>`；示例只演示写法。
2. **工程基线落点由接入方拍定。** 目标仓已有文档体系时用其位置；没有时由用户确认后写进 `AGENTS.md`
   的「工程基线」节或独立文件，不自动创建新的顶层目录。
3. **不新增机器门。** 四项都是模板与角色文字；`doc_chain.py` 与 `validate.py` 的判据不动。
   原型可点性与配置核对属于语义判断，机器只能查「表是否存在」，不能查「填得对不对」，不制造假绿。
4. **`design/be` 的既有小节编号保持稳定。** 新增核对小节排在现有 `1.3.1–1.3.4` 之后，不改旧编号，
   避免历史设计文档的引用失效。
5. **`templates/engineering/` 是新子目录，不是新顶层目录。** 归在现有 `templates/` 之下，随
   `packaging/runtime` 一起分发；模板索引与 `index.md` 的抄模板入口各加一行指针。
6. **FE 纪律落在实现角色与两层模板，不新建 reference。** 请求/缓存/生命周期是执行动作，放 `frontend-engineer`；可核对的场景与数值放 `design/fe`；用户可观察行为放 `spec/fe`；项目事实放工程基线。四层各管一段，不互相复制。
