**盘点确认的四处缺口**（本批要补）：

1. **目标仓工程基线没有载体。** Init 只与用户确认语言、术语、分支纪律、检查命令、文档落点五项；
   没有任何一处承载「技术栈与版本、禁止的平行方案、目录与命名、新增模块必做清单、测试栈与运行方式、
   质量门顺序」。角色文件只说「遵循本地约定」，但没人保证约定存在、能被找到、或是最新的。
   语料 A 的 `agents/spec/17–24` 与语料 B 的 `工程代码规范.md` + `通用工程规范.md` §11
   （采纳/覆盖、一条规则的完整定义、迁入检查）正是这一层的成熟形态。
2. **后端数据与配置设计不可核对。** `templates/feature/design/be/backend.md` 只有一行
   「`DDL` 字段级 SQL」与三列的「配置键」表；没有字段的类型/空值/默认/单位/范围/精度、字符与字节长度、
   索引与查询匹配、`N+1`、事务与幂等、迁移与真库验收，也没有配置项的可见性、覆盖顺序、生效方式与
   失败行为。语料 B 的 `数据库设计与SQL规范.md` §5–§16 与 `配置与边界规范.md` §2/§5 给出了可直接裁剪的
   核对项。
3. **原型只管形态不管可点性。** `templates/feature/prototype/README.md` 的自检覆盖形态、依赖闭包、
   `revision`、真源声明，但不检查「按钮点了有没有反应、隐藏态能否显现、假数据像不像真数据」。
   语料 B 的 `原型交互完备性约定.md` §1/§2 给出了硬性基线与 Mock 约定；同一文件的 §四还记录了一个
   重要反例：脚本初筛报「问题页 102 页 / 死按钮 1403」，逐页核对后真实缺口是 8 个页面；两种计数的单位不同，不能直接换算误报率，但误报量足以说明脚本只能当线索，因此这条只能是人工/浏览器自检，不能做成机器门。
4. **测试设计的易漏维度没有落点。** 计划模板的「覆盖方向自检」改造前共八个方向，不含并发与竞态、
   生命周期与清理、契约字段兼容；语料 A 的 `frontend-test-design/references/test-dimensions.md`
   用 15 个维度覆盖了这三类，适合压缩成三行进入现有表。

## 2. 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 模板被当成「通用默认」照抄 | 把示例数值、技术栈当成生产事实，重演语料 A 明令禁止的「凭通用默认推断」 | 模板每条留 `<填>` 占位并写明「没有的事实写缺口」；模板开头声明「这是形态，不是默认值」 |
| Init 从五项变六项提高接入成本 | 小项目接入变重 | 已有工程规范时只登记入口路径；没有规范时才落最小基线，且最小基线允许「不适用 + 理由」 |
| 配置/数据核对表被填成空表 | 形式合规、内容为空 | 在计划模板与 `backend-engineer` 中要求逐项写结论（已覆盖 / 缺口 / 不适用+理由）；人工评审门抽查 |
| 原型自检条目被当作机器门 | 误以为 `doc_chain.py` 会检查控件反馈 | 在模板与链契约都写明「人工执行；插件没有对应的机器门」 |
| 副本漂移 | 模板改了但 `packaging/runtime` 没重建 | 全量门含生成树逐字节新鲜度；T07 重建并实跑 |
| FE 纪律与 `design/fe` 重复 | 两处各说一套，读者不知道以谁为准 | 角色只写实现动作，数值与场景由 `design/fe` 的表承载；角色用「按 design/fe」指向 |
| 把项目 FE 习惯当通用规则 | 换一个仓就不成立，重演 IProps/Tailwind 之争 | 项目专属项一律写进工程基线；方法仓只留可跨仓的判据 |
