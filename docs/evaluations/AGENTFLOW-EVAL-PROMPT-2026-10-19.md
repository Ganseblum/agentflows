## 一、评测铁律（违反任一条，报告作废重写）

1. **证据优先**：一切结论必须带 `文件路径:行号` + 逐字引用，或「命令 + 退出码 + 逐字输出」。
   没有证据的主张，单独进「无证据推测」清单，不得混进结论。
2. **实跑优先**：凡涉及门 / 工具 / 测试 / 脚本的主张，必须实际运行并贴输出。无法复现的检查
   记为「未运行」，**绝不计为通过**。
3. **只读铁律**：不得修改被评测仓库的任何文件。故障注入与变异测试只允许在 `/tmp` 的 `cp -r`
   副本上进行。不得使用 `git checkout` / `git restore` / `git stash` / `git clean` 撤销真实树上
   的任何东西。
4. **不屏蔽输出**：禁止 `2>/dev/null` 及同类写法掩盖错误；工具行为的主张要退出码与逐字输出，
   不要推理。
5. **先懂再判，不猜不想**：
   - 评判任何文件 / 组件之前，先从**它自身的内容**（不是从别的文档转述）归纳出三行「意图
     卡片」：**它要干嘛**（职责）、**它声称守什么**（自述契约）、**它的消费者是谁**（谁依赖
     它的产出）。先有卡片，后有评判。
   - 意图卡片与阅读 / 实跑观察不一致的，这个不一致本身就是一条发现（记入对应维度）。
   - 结论里禁止出现「应该是 / 大概率 / 通常是 / 想必 / 一般来说」类猜测句式；没读到的就是
     没读到，进「未读 / 未验证」清单，不得用经验补全。
   - 阅读覆盖必须穷尽（各角色的必读清单见第四节）；抽样只允许用于明确标注的统计目的
     （如 D4 的命名表意性抽样），且抽样结论必须写明样本量与总体。
6. **不凭记忆与摘要**：对文件的主张以本次会话实际读到的内容为准。引用历史结论
   （CHANGELOG、旧评审报告、README 声明）时，必须重新验证其当前真伪——过期引用是发现，
   不是依据。
7. **声明与强制分开计分**：提示词级约束（写在自己文本里的规矩）与机器级强制（宿主 / 脚本 /
   schema 真能拦截的）分别评价。不得把「文档声称会拦」记成「已强制拦截」。
8. **时间写实**：所有时间戳用 `date` 现取，不手算；校验器拒绝未来时间。
9. **诚实勘误**：发现自身前期结论错误，集中在报告「勘误节」披露，不静默修改原结论。
   评审自身也要防「验证缺席」——这个项目最反对的恰是这件事。

### D4 代码工艺与可读性

- **要回答**（本维答「好不好读、好不好改」；正确性与安全性归 D3）：
  - **整洁**：函数 / 方法长度与单一职责；圈复杂度异常点；重复代码——同一条规则被复制到多处
    （本仓有过先例：两个 agent 文件里的 partial 规则复制粘贴）；死代码——评测装置裁撤后的
    残留引用、不可达分支、无人调用的函数；文件长度异常。
  - **注释**：注释解释「为什么」还是复述「是什么」；关键取舍（为什么选这个算法、为什么这里
    fail-closed）有无注释；有无**过期注释**（与代码行为矛盾——比没注释更坏）；TODO / FIXME
    的数量与真伪。
  - **命名**：标识符是否表意（`_validate`、`check_diff` 这类名字是否名副其实）；命名风格
    一致性（snake_case / camelCase 混用、公有常量与局部变量的区分）；布尔命名（`is_` / `has_`
    前缀）、缩写惯例（`src` / `dst` / `cfg`）是否成文且被遵守；命令行参数与子命令命名风格。
  - **一致性**：错误处理模式（抛异常 vs 返回码）、返回结构、CLI 参数风格是否全域统一。
- **方法**：读 `tools/lab/` 全部源码 + `tests/`——整洁 / 注释 / 死代码三项**全量**，命名
  表意性允许抽样（每文件 5 个，须记录样本量与判断依据）；用**只读**静态手段辅助——若宿主有
  pyflakes / ruff 的 check 模式可直接用，没有则用 `python3 -c` + `ast` 自写统计（函数行数、
  圈复杂度近似、标识符频率），**不得向被评测环境 pip install 任何东西**。
- **锚点细化**：9–10 = 全域风格统一、命名自解释、无死代码、注释解释为什么；7–8 = 主体清晰，
  个别函数过长或命名含糊；5–6 = 复制的规则 / 常量已现多处漂移风险，或过期注释存在；
  ≤4 = 大段不可读或死代码成群。
- **与 D5 的分工**：D4 只管 `tools/lab/` 与 `tests/` 的**代码**；指令面 / 文档面的同类问题

  （13 步）——之间的**切换点**是否定义（什么条件下从主工作流进入改进环、退出到哪里）；状态机
  完备性：每个状态的入口 / 出口是否成对，有没有死路（如 open 之后无路可走）或只进不出的
  吸收态；文本定义的路径 vs 记录里真实发生过的路径——找出**死条款**（文本存在、记录中从未
  发生）与**隐性惯例**（记录中发生、文本未定义）；并行分支的汇合点是否定义。
- **方法**：把正文里所有规定「下一步」的句子抽出来画成状态图；再用记录面（issue 状态流、
  episode、plan 看板）核对每条边是否真实走过；两向差集即发现。
- **锚点细化**：9–10 = 状态图完备、无死路、文本与记录双向对齐；7–8 = 主链路闭环、
  个别切换点靠口头约定；5–6 = 存在断环或死条款成群；≤4 = 链路文本互相矛盾或大面积空转。

### D8 文档与记录活性

- **要回答**：`index.md` 与实际结构是否同步；全仓相对链接是否可解析、有无退役路径散文与内联
  死引用；文档之间有无自相矛盾（同一事实两种说法）与冗余重述；记录面是活的还是仪式的——
  统计 issue 状态流（多少 open 后停滞、多少走完 verified、归档规则是否空转）、episode 的
  `evidence_ref` 密度与 `review_roundtrips` 实质率、plan 看板与任务表算术是否自洽、`reviews/`
  有无实质轮次；`docs/PENDING-DECISIONS.md` 是否被真实维护。
- **证据来源**：链接检查（可复用 `validate.py docs` 的扫描逻辑，只读运行）、`docs/` 全量、
  记录根统计（`validate.py report` / `validate.py recurrence` 可用）。

### D9 治理与发布闭环

- **要回答**：improve 环的角色分离，多少是机器强制、多少是提示词自觉（`skills/improve/SKILL.md`
  自承「角色分离只是流程性的」那句是否仍成立）；`measurement: none` 口径是否被诚信执行（有没有
  记录同时声称 `none` 与 `better`）；晋升规则（`basis` = 人工评审 + 评审引用）与
  `release-record.schema.json` / `evidence-and-release.md` 是否一致；五份 manifest 名字版本是否
  一致（实跑 `validate.py manifests`）；「发布 = 人工批准」边界是否被遵守；评测装置裁撤后有
  无死代码 / 死引用 / 死文档残留；CHANGELOG 与 manifest 版本是否对得上。
- **证据来源**：`skills/improve/**`、`docs/releases/`、`CHANGELOG.md`、实跑。

### D10 安全与权限边界

- **要回答**：worker 的 `write_scope` 是提示词级还是机械级（`skills/agentflow/scripts/` 下的
  `check-write-scope.sh` 与 `tools/lab/gate/` 的真实覆盖面、退出码是否 fail-closed、对非 ASCII
  路径是否正确）；「宿主不对 Write 工具强制路径约束」（README 自承）带来什么残余风险、有无
  缓释；候选隔离的调用方式是否要求受信检查器根；凭据纪律（会话注入、不落记录 / 脚本 / 日志）
  在文档与工具里是否一致；fail-open 面全集。
- **证据来源**：`check-write-scope.sh`、`isolation.py`、`tools/lab/gate/`、README 自承处、
  `references/contracts.md` 硬边界 14 条逐条对账。

### D11 实现的效果（不看设计看疗效）

- **要回答**：用仓库自己的历史证据回答「这套方法实际跑出了什么」——走完全流程的 issue 数与
  占比；有实质内容（非空 `review_roundtrips`、带 `evidence_ref`）的 episode 数与占比；独立评审
  的真实轮次与 `changes_requested` 发生率；计划的实际完成率与看板回写纪律；再犯类台账的档位
  分布（`single` / `recurred` / `escalated`）；门禁实际拦截过什么的证据（有没有门红后被修
  的记录）；改进环真实产出过几个候选、晋升 / 拒绝分布；用户反馈是否形成闭环（反馈 → 记录 →
  改动 → 验证）。
- **方法**：记录面统计 + **抽查验证**（每条统计至少抽 1 条原文核对，防「数字对、事实错」）；
  与 D8 的分工：D8 看记录「是否在更新」（活性），D11 看更新「是否产生了可验证的结果」（疗效）。
- **锚点细化**：9–10 = 关键指标多数有实证且抽查全部对得上；7–8 = 主流记录真实、
  个别指标注水或不可考；5–6 = 记录存在但结果稀疏（大量 open 停滞、证据缺席）；≤4 = 记录面
  基本是仪式，无可验证疗效。

### D12 存在意义（价值主张）

- **要回答**：这个项目为什么应该存在？——不用它的人具体损失什么（选 2–3 个真实场景做
  「有 agentflow vs 无 agentflow」的对照推演，例如一个跨层 feature、一个反复出现的缺陷）；
  它的核心价值主张（确定性门 + 受治理发布 + 记录即编译）是否不可替代，还是宿主本身 / 竞品
  已覆盖；**仪式成本与收益比**——数一个 material 改动从 Intake 到 Decision 要产生多少记录、
  跑多少检查、开多少会（角色），这个成本对目标用户（单人开发者？小团队？）是否划算；什么
  情况下不该用它（SKILL description 自称「trivial single-step work 跳过」的划线是否合理）；
  结论必须包含建设性判断：**砍掉什么它反而更好**。
- **方法**：场景推演 + 成本清点（对着 SKILL 十步数产物与检查）+ 与「裸用宿主 agent」的
  同题对照。允许低分，但低分必须附「改什么能翻盘」或「砍什么更健康」的具体建议。
- **锚点细化**：9–10 = 价值主张具体、不可替代、成本可接受且有实证场景；7–8 = 有价值但
  某类场景成本倒挂；5–6 = 价值集中在少数场景，普适性存疑；≤4 = 找不到不用它会痛的场景。

### D13 竞品比对

- **要回答**：与同类工作的横向对比（至少覆盖 superpowers、BMAD-METHOD、spec-kit、Claude Code
  subagents、Codex AGENTS.md 约定；形态对照可加 OpenHands / CrewAI / LangGraph）。对比矩阵
  至少含列：形态、角色 / 流程机制、确定性强制力（提示词级 vs 机器级）、自迭代 / 治理、
  记录与审计、上手成本、与 agentflow 的重叠度。结论回答三件事：agentflow 的**真实空白创新点**
  是什么；哪些部分是重复造轮子；对外叙事该押注什么。不贬竞品、不吹自身，一切用可核查的公开
  事实。
- **方法**：公开资料检索（每条结论注明来源与检索日期）；与本仓的实际能力对表（引用本仓
  实证，不引用宣传语）。
- **锚点细化**：9–10 = 对比全面、差异化结论有据、叙事建议可执行；7–8 = 覆盖主要竞品、
  个别论断缺来源；5–6 = 对比笼统或只罗列不判断；≤4 = 把重叠当差异或反之。

## 五、执行流程

1. Supervisor 完成「开工三件事」（第二节）。
2. 分发 R1–R7（并行或顺序，按宿主能力）；R8 在 R1–R7 交付后启动。
3. 每个角色交付「分维度报告」：意图卡片 + 分数 + 锚点说明 + 亮点清单（带证据）+ 硬伤清单
   （带证据）+ 无证据推测清单（单独节）+ 未读清单（含原因）。
4. R8 交付「证据链审计」。
5. Supervisor 汇总裁决。**综合分 = 十三维算术平均，其中 D2 计两遍**（门禁是本仓自我声名的
   地基；如你认为权重应改，给出理由与备选权重下的分数，两版都列）。
6. 报告末尾给「拍板项」：需要用户决策的事项（含「评测装置口径是否调整」这类），每条带推荐
   默认值与框定它的证据。

## 七、已知环境坑（先读，避免误判）

- macOS / BSD `grep` 不支持 BRE 交替（`a\|b`），用 `grep -E 'a|b'` 或宿主搜索工具。
- 时间戳一律 `date` 现取，不手算；校验器拒绝未来时间。
- `validate.py all` 的 `tests` 子项在个别宿主（注入了 Python path broker 的宿主）会环境性假红
  （README 已披露）；遇到先在干净环境复跑，再决定记「未运行」还是「真失败」。
- `__pycache__` 会出现在 `check-diff` 的变更路径里但不被阻塞；在副本上跑过门后预期看到它。
- YAML frontmatter 的列表不支持注释行（`  # ...` 会报 nested mapping）——审 schema 与
  frontmatter 时别被这个假象误导。
- 非 ASCII 路径 + git 的 C-quote 输出曾导致 `check-write-scope` 误 FAIL（ISS-2026-10-10-写范围dot-scope静默不匹配 同根因）
  ——审这类脚本时专门测一条中文路径。
- `record_store.py` 需先 `index` 再 `query`；它是词法索引，不是向量库，也不替代记录文件本身。
- 做 D4 静态统计时不得向被评测环境安装任何包；宿主没有 pyflakes / ruff 时，用标准库 `ast`
  自写只读统计即可。

## 八、完成定义（自检通过才算完成）

- 每个分数都有锚点说明与至少一条硬证据；
- 每条硬伤都可复现或可指出确切位置；
- 缺口清单每行都有解锁条件；
- 附录 A 的命令输出是逐字的、退出码齐全的；
- 没有对未运行的检查声称通过；
- 附录 C 的覆盖清单与各角色实际引用一致，未读者均有原因；
- 拍板项与推荐默认值成对出现。
