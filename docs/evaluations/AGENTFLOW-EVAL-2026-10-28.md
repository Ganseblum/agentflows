## 一、哪里好，为什么好，怎么好的

### 1.1 门是机器，且这次是「被抓过之后补的网」

10-26 审计用 25 个变异实证 19 个让门变红；审计后一周，被抓出的缺口全部以**带审计编号的代码注释**
补上，形成可复核闭环：

- `tools/lab/docchain/checks.py:1314` fail-closed 修复注释逐字：「2026-10-26 audit G02: chmod 000 turned 8 C16 findings into PASS」；
- `tools/lab/gate/checks.py:183-194` 逐案行数交叉验证，注释引用 G12：「a mutated selftest printing 200/200 passed this gate」；
- `tools/lab/gate/checks.py:106-119` 逐文件下限，注释引用 G14：「MIN_UNIT_TEST_COUNT alone let 4 of the 5 declared files be gutted」。

**为什么好**：验证缺席是本仓自定的最高优先级故障类，四点修复说明「审计→变异→修门→注释留痕」
循环真实走通。**怎么好的**：每处都有变异实验的红绿证据（如 ISS-2026-10-27-计划模板验证标题不匹配 附带
`fix-target-red.txt`/`fix-target-green.txt`），不是改完就声称好了。

### 1.2 记录即编译——本轮评测本身是它的受益者

核对 35 项审计发现时，每一条都能在一分钟内定位到修复证据。ISS-2026-10-27-计划模板验证标题不匹配 是教科书案例：
模板标题与检查器字面量不匹配 → 只改模板不放宽检查器 → 新增
`test_shipped_plan_template_can_be_used_as_hybrid`（照抄真实模板必须过真实校验）→ 独立评审批准
→ `verified`。记录不是给人看的文档，是能被下一个会话机器复核的产物。

### 1.3 L3 证据工具是全仓工艺最高档的新增量

`workflow_lib/` 五模块 1731 行。`workflow-tool.md:3` 逐字声明「不提供模型运行时、沙箱、批准或
任务状态系统」，`execution.md:57` 说「不是第二套进度系统」——它守住了架构声明，不是第二套编排器。
实现要点：`seal/verify/run` 指纹绑定计划/请求/HEAD/写范围，执行前中后三次快照比对，漂移即拒绝
（`execution.py:233-258`）；red 阶段要求「用例真实失败且命令非零」（`:146-150`）；`managed.py`
做到预览指纹 + 备份 + 原子替换 + 读回校验 + `os.link` 防覆盖竞态（`:226-250`）；全 typed 异常、
argv 列表传参、8MiB 输出上限、0o600。58 个用例且被 `protected-paths.txt:54` 保护。

### 1.4 处理问题的方式已收敛为可执行判据

`execution.md`（86 行）把四件最容易走样的事写成判据：有效失败 vs 损坏夹具/依赖缺失（:23）、
选测与证据复用过期条件（:33）、共享失败 vs 独立失败分流（:45-51）、三种结论分开（:80-86）。
`roles.md` 用六条工作链做默认入口（:30-46）。九本再犯台账**无一处于 escalated 档**。

### 1.5 诚实是成体系的

improve skill 三处标注 canary/automatic 不可达；L3 批次声明「实际宿主未安装、跨平台未运行、
疗效未测量」；EP-2026-10-27-002 把「裸 python3 是 CLT 3.9、未运行不算通过」记成 signal。不把环境
问题、未验证事项伪装成绿色。

## 二、哪里不好，为什么，成因

### B1（最实）整改追踪没有载体

**现象**：10-26 审计 §十三 给出六批整改路径，但发现总表没有状态列。一周后要回答「35 项谁修了」
只能读提交信息、grep 代码、对 PENDING 编号体系。`4bb29dc` 的提交信息只列了自己做了哪些项。
G14 曾在两个不同编号体系里被混淆（PENDING 第 12/13 条登记的是另一套编号的 G19/G20）。
**成因**：审计报告是「一次性快照文档」，其整改表没有状态机。本仓给 feature 做了目标承接表
（C22），却没给审计做同样的事。

### B2 改进环空转，且评审能力无分级——本轮实测撞上死因

**现象**：四治理角色自装置裁撤后零真实候选。本轮更直接的证据：转发四个并行调查角色、
再单独派一个，**全部返回 `model concurrency limit exceeded`**。方法里所有「独立评审门」条款
都建立在「角色可用」的假设上；降级条款只覆盖「宿主没有委派机制」，不覆盖「有机制但当下额度耗尽」，
更没有定义「委派不可用时独立评审的最低替代形态」。
**成因**：方法按宿主能力**上限**设计，没有按**可用性**分级。额度被其它会话占满是常态。

### B3 本机门基线长期 10/11

`validate.py all` 本机永远 `FAIL lint`（ruff/mypy 装不上，PEP 668 拒绝 pip；`--break-system-packages`
是明知有害不该推荐的动作）。G01 勘误后两个口径各自诚实了，但代价是**本机 11 项门有一项常红**，
报警价值被磨掉：哪天 lint 真回归，本地不会有人注意。
**成因**：缺一条「一行起带 dev 依赖的解释器」的约定路径（venv）。

### B4 表达面膨胀，同一规则维护 2–3 份

分支/证据/检索/重试纪律同时出现在用户级全局块、`SKILL.md`、`contracts.md`、
`templates/host/global-rules.md`，且「改一处就改另一处」（`SKILL.md:102`）是显式义务——用纪律
对冲重复而非消除重复。`document-chain.md` 481 行（references 第二名 382，多数不到 100），轻量档
六条判据埋在中间。`SKILL.md:52` 与 `:126` 两处重复声明「execution-coordinator 不存在」。
10-26 审计「砍掉对已裁撤能力的反复解释」这条至今未做。
**成因**：多宿主承载（插件 + 全局块双轨）必要，但 references 内部沉淀没跟上瘦身批节奏——
瘦身批砍的是记录面与装置，没砍过表达面。

### B5 角色深度与产出重要性倒挂

reviewer 175 行最深；backend-engineer 32 行、frontend 40 行、technical-director 22 行。实现角色
是产出主体承载者却着墨最少，深度被转嫁到 Supervisor 的简报纪律。improve 侧四治理角色仅 20–24 行
——与 B2 互为因果：薄所以没案例长厚，没案例所以一直薄。FE/BE 是否合并自 2026-10-19 拍板起挂
「由 28 例边界测试决定」，从未写出裁决规则（通过率多少算该合并？）。

### B6 发布税偏高

0.16.0–0.19.3 全部落在 10-26/27 两天；0.19.3 整个提交是纯版本号提升。安装快照机制决定「改一个
标点也要 bump + 重建生成树 + 重装 + 双端校验」，CHANGELOG/manifest/回写提交的噪声随发布频率线性增长。
**成因**：版本号被用作宿主缓存失效的机械手段，语义版本与安装版本没有分离。

### B7 次要在场缺口

`docs/issues/归档/` 仍不存在（G28）；G34 成本对照无载体；G19/G20 待拍板。

## 四、改后对比（举例）

**例 1 整改追踪**。改前：核对 35 项需四个回合（本轮实际发生，且初判 G14 出错）。改后：
`grep "G14" docs/evaluations/AGENTFLOW-AUDIT-2026-10-26.md` 一条命令出状态，状态列可直接由门检查。

**例 2 委派瘫痪**。改前（本轮实际发生）：5 次派发全失败，报告独立性只能靠开头一段声明补救，
方法文本对此无话可说。改后：决策记录写
`review_tier: L0（宿主并发不可用，5 次派发失败）→ supervisor 自审 + 全套确定性门 + 用户可见
行为改动在能力恢复后补开门`——损失从隐性变显式、有恢复条件、可审计。

**例 3 本地门**。改前：本机 10/11 常红。改后：`.venv` 一行就绪后本机 11/11，红线重新有信息量。

**例 4 必读面**。改前：查「轻量档能不能用」要从 `SKILL.md:87` 跳进 481 行文件找六条判据。改后：
`SKILL.md` 该节一行直达判据表 + 一句「判据由 C26 机器核验」。

**例 5 改进环**。改前：0 候选，两份 schema 是「无消费者的活契约」，对外不能押「受治理自迭代」。
改后：本批改动成为第一份真实候选 + 发布记录，两份 schema 的 `allOf` 首次在真实记录上编译。
