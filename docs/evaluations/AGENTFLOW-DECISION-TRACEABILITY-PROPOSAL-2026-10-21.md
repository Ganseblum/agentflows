## 一、先复述坏在哪（五个可观测症状）

| 症状               | 现场证据（都是这一轮真实发生的）                                                    | 如果有门，会在哪一步红                        |
| ---------------- | ------------------------------------------------------------------- | ---------------------------------- |
| **S1 来源缺失**      | 用户连问两次「这是哪个需求、文档还是 todo 弄的」；第一版说明里只有一个 `#96`，读者无法回溯到第三期/第五期原文       | 决策条目缺可解析的「来源」列 → 登记当天红             |
| **S2 状态四处不一致**   | 同一条 #96：差异清单写「仍存在」、社区收口批写「已修+回归项」、PENDING 写「已拍板」、待拍板清单写「已关闭」。四份都自称对 | 状态词只允许出现在记录里，台账只能给链接 → 第一份台账写状态时就红 |
| **S3 清单滞后代码**    | #86 第八轮就修了、#119 前后端都通了，清单仍记「仍存在」，多讨论一轮；我自己也把 R6 误判成「前端写死」（实际已动态渲染）  | 引用对象在核验之后被改过 → 条目过期红               |
| **S4 孤儿条目**      | R5/R6/R7/R8 四条**从未进过任何批次**：没有任务行、没有验收项、没人负责，只能在「待拍板」里循环             | open 条目必须有承接批次或显式「不做」→ 无归属即红       |
| **S5 一句话推荐无法拍板** | 用户原话：「写清楚不要一句话描述」；根因是契约把决策的最小形态定义成「一行问题 + 最多三个选项 + 推荐」              | 无法机器判定，只能靠模板与角色纪律（见 M5）            |

**一句话概括**：agentflow 现在很擅长拦「文档链长得不够」（C1–C11）和「声称与现实不符」（C12），  
但**不擅长拦「待办本身没有出处、没有归属、过期了也没人知道」**。

## 二、归因：三个设计缺口（不是 Youc 用错了）

### D1 台账可以替代记录

`docs/issues/` 里有完整的状态机（`open → fixed-pending-review → verified`）、必填的  
`closure_criteria`、`## 变更记录`、再犯台账（`class_id`/`occurrence`）。但**没有任何规则禁止**  
一个仓库用一张几百行的表格代替它——Youc 就是这么做的：`planning/规划与实现差异清单.md`  
一千多行，每行自带状态、自带结论、多轮回填。于是：

- 状态不在记录里，而在表格单元格里 → 没有任何机器能校验它；
- 一条问题可以永远停在表格里，不需要归属、不需要验收、不需要关闭条件；
- 「已修」是表格里的一句话，不是一条带前后对比的证据。

### D2 决策的最小形态被定义得太小

`skills/agentflow/references/contracts.md`「先问再假设」节规定：决策「以一行问题交给 owner，  
最多三个选项并标出推荐项」。这条规则在**技术取舍**场景是对的（快、省），但在**产品决策**场景  
必然返工，因为 owner 缺四个字段就拍不了：这件事在哪发生、影响谁、每条路要付什么、现在的事实  
是什么。这一轮 9 条全部踩中。

### D3 只检查「路径是否存在」，不检查「路径是否变过」

C12 能抓「文档说某文件待产出、但该文件其实已存在」。它抓不到反向：**文档说某问题仍存在，  
但那条代码路径在文档写下之后已经改过三轮**。这就是 S3 的机制缺口——判断依据是「存在性」，  
而漂移的本质是「时间序」。

## 三、四个机制

### M1 · 台账降级为索引（治 S2 的根、S4 的一半）

**规则**：问题台账（差异清单、缺陷索引、`docs/issues/README.md`）只能写四列——  
`编号 | 一句话 | 记录链接 | 归属`。**台账行里不允许出现状态判断词**（仍存在 / 已修复 / 已关闭 /  
已失效），状态只写在记录 frontmatter 里。

**改哪**：`skills/agentflow/references/document-chain.md` 增「台账与记录的分工」一节；  
`tools/lab/doc_chain.py` 增检查 `C15 ledger-index`。

**判据**（确定性，无自然语言理解）：

1. 按**列名**定位表格（不按列序——本仓 C9 已因按位置读列踩过坑）；
2. 任一行出现 `STATUS_WORDS = 仍存在|已修复|已关闭|已失效|已修|待修` 且该行没有 `ISS-\d{4}-\d{3}`  
   → finding；
3. 行内每个 `ISS-YYYY-NNN` 必须在 `docs/issues/` 下存在同名文件（slug 后缀放宽匹配）；
4. 反向：每个 `status: open` 的记录必须在**至少一个**台账里出现且只出现一次（重复登记也是 finding）。

**红的样子**：

```
FAIL C15 ledger-index docs/issues/README.md:41
  台账行自带状态词「仍存在」；状态只能写在记录 frontmatter（ISS-2026-096-...）
FAIL C15 ledger-index docs/issues/README.md:57
  ISS-2026-101 未在任何台账登记（孤儿记录）
```

**授权级别**：门变更（`doc_chain.py` + `tests/` + `protected-paths.txt` 条目）。

---

### M2 · 决策条目八列（治 S1、S5 的机械部分，并新增评级/影响范围/自动决策）

**规则**：`docs/PENDING-DECISIONS.md`（以及任何被 AGENTS.md 声明为拍板口的文件）每行固定**八列**：

| 列    | 内容要求                                    | 为什么             |
| ---- | --------------------------------------- | --------------- |
| 来源   | 需求文档 `path:line` 或 `ISS-YYYY-NNN`，多个用顿号 | 回答「这是哪个需求/文档弄的」 |
| 待决问题 | **至少 3 个选项** A/B/C，每个带「要动什么 + 代价」           | 回答「有几种走法、各什么影响」 |
| 现状核验 | ISO 日期 + 反引号命令                          | 回答「现在还是这样吗」     |
| 推荐   | 一句 + 理由                                 | 回答「你建议哪个」       |
| 关闭条件 | 命令 / 日期 / 批次三者之一                        | 防止「拍完还是悬着」      |
| 优先级   | 枚举 `P0\|P1\|P2\|P3`                       | 回答「这事多急、要不要立即拦」 |
| 影响范围 | `级别(具体模块/项目，逗号分隔)`，如 `多模块(youc-admin 订单筛选页 + youc-canvas 支付组件)`、`跨项目(agentflows 质量门 + Youc/server 后端)` | 回答「动哪、波及多大、跨不跨项目」 |
| 自动决策 | 枚举 `Y\|N`；`Y` 仅允许 `P3`                     | 回答「谁来拍板、能否交预设规则」 |

> **评级与自动决策政策**（完整版在模板 `decision-record.md`）：
> - `P0` 阻塞发布/资损/合规红线/安全事故 → 人工，立即；`P1` 高影响、多模块或核心链路（支付/审核/登录）→ 人工，本迭代内；
>   `P2` 中影响、单模块可排期 → 人工；`P3` 低影响、局部 → **可自动决策**。
> - **仅 P3 可标 `Y`**；`Y` 时「推荐」列必须附「自动规则 + 触发条件 + 本次判定结论」。自动决策 ≠ 不记录，只把"谁拍板"从人换成预设规则，全量字段 + 理由仍须写。
> - `P0–P2` 误标 `Y` → C16 红。

**改哪**：`skills/agentflow/templates/decision/decision-record.md`（新增模板，不属门）；  
`tools/lab/doc_chain.py` 增检查 `C16 decision-record`。

**判据**：

1. 表头八列按名匹配，缺列或改名 → finding；
2. 「来源」列至少有一个反引号路径或 `ISS-` 编号，且路径必须存在于盘上（同 C12 的解析器）；
3. 「待决问题」列必须出现至少两个选项标记（`A`/`B`/`C`…），且每个选项含代价描述；
4. 「现状核验」列必须匹配 `\d{4}-\d{2}-\d{2}` 且含反引号包裹的命令；
5. 「关闭条件」列不得为空、不得为 `—`/`无`；未决项若依赖外部（法务、服务器资源），必须点名依赖物；
6. 「优先级」必须是 `P0`–`P3` 之一；「影响范围」必须是 `级别(具体模块/项目)` 形态，级别∈`单功能/单模块/多模块/跨项目`，且括号内必须列出至少一个具体模块或项目名（只写级别词、不列具体名称 → finding）；
7. 「自动决策」=`Y` 时优先级必须为 `P3`，且「推荐」列含「自动规则/触发条件/判定结论」子串；=`N` 时可为任意优先级；非 `P3` 却 `Y` → finding；
8. 拍板后不移出也可以，但状态列只允许 `未决 | 已拍板（日期） | 阻塞（外部）` 三值。

**红的样子**：

```
FAIL C16 decision-record docs/PENDING-DECISIONS.md:31
  第 8 条缺「现状核验」列：没有核验日期与命令，无法判断是否过期
FAIL C16 decision-record docs/PENDING-DECISIONS.md:31
  「来源」列的 planning/第五期-...md:30 在盘上不存在（路径已改名）
FAIL C16 decision-record docs/PENDING-DECISIONS.md:31
  优先级 P2 却标 自动决策=Y（仅 P3 可自动）→ 高优先级不得自动决策
FAIL C16 decision-record docs/PENDING-DECISIONS.md:31
  影响范围 列只写「单模块」没列具体模块名（须 `级别(具体模块/项目)`，如 `多模块(youc-admin 订单筛选页 + youc-canvas 支付组件)`）→ 级别词不能代替具体模块
```

**授权级别**：门变更。

### M3 · 过期检测（治 S3，这是最值钱的一条）

**规则**：条目声明的「核验日期」之后，若它引用的任何仓库路径被改过，该条目视为过期，必须重核。

**改哪**：`tools/lab/` 新增 `staleness.py`（或并入 `doc_chain.py` 作 C17），  
`validate.py all` 增一个子项。

**判据**：

1. 从条目取 `verified_at`（M2 的「现状核验」列）；
2. 取该行引用的仓库路径集合；
3. 对每个路径执行 `git log -1 --format=%ct -- <path>`，取最后修改时间；
4. `max(mtime) > verified_at` → finding，并打印那条 commit 的短 SHA 与日期；
5. 外部链接（URL）跳过并在输出里显式声明「N 个外部引用未检测」——空集也要声明。

**红的样子**：

```
FAIL C17 staleness docs/PENDING-DECISIONS.md:29
  #86 的引用对象 server/internal/platform/billing/orders.go 在核验（2026-10-20）之后
  被修改过：a1b2c3d 2026-10-21 09:14 —— 必须重跑核验命令并刷新日期
```

**诚实边界**：它防的是「忘了重核」，防不了「故意填一个未来日期」。后者只能靠评审看到  
命令输出——所以 M2 要求核验列**带命令**，评审可以要求贴输出。

**授权级别**：门变更。

---

### M4 · 归属检查（治 S4：让孤儿条目无法隐形）

**规则**：每条 `status: open` 的问题必须有归属，三选一：

- 挂进某个 feature 批次的「承接表」（表头含 `记录编号 | 任务号`）；
- 或 `disposition: deferred`（含复核日期）；
- 或 `disposition: not-doing`（含理由）。

**改哪**（两个版本，成本差一个数量级）：

- **M4a 零 schema 版（建议先做）**：`doc_chain.py` 增 C18，检查每个批次 README 的承接表，  
  以及「open 记录是否至少被一个承接表覆盖」。不动 `schemas/`。
- **M4b schema 版（更强）**：`schemas/bug-record.schema.json` 增 `target_feature`、  
  `disposition`、`disposition_reason` 三个可选字段，`validate.py artifacts` 直接判。  
  代价是改 schema + 补 `examples/invalid/` 反例 + 过一遍 `EXPECTED_TEST_FILES`。  
  **这是门变更，且动的是记录契约本身，建议单独一批做。**

**红的样子**：

```
FAIL C18 ownership
  ISS-2026-087 状态 open，但未出现在任何批次承接表，也没有 deferred/not-doing 声明
  → R5/R6/R7/R8 这类「从来没派进去」的条目会在登记当天就红，而不是躺三个月
```

**授权级别**：M4a 门变更；M4b 门变更 + schema 变更。

### M5 · 决策简报模板（治 S5 的人话侧，非门）

**规则**：给 owner 的决策简报固定七段——`来源 / 出现在哪 / 发生了什么 / 影响 / 选项与代价 /
建议 / 拍板后动作`。禁止只给「推荐 A」。

**改哪**：`skills/agentflow/templates/decision/decision-brief.md`（新增，不属受保护路径）；  
`skills/agentflow/SKILL.md` 的路由里加一句「用户要做产品决策时用决策简报，不用一行问题」。  
注意 `references/contracts.md` 属受保护面，改它需要授权——所以 M5 先只落模板与 SKILL，  
契约文字等授权后一起改。

**为什么不做成门**：判断「这段散文有没有把影响说清楚」是语义问题，机器判会误伤。  
本仓的既有判断是对的——C 系列只守结构底线，内容质量交给评审门。M5 同理，只给形状，不给判决。

## 四、用真实失败做语料（这是本仓一贯做法）

新检查要有回归语料，否则第一个假阳性就会让人把门关掉。**建议直接用 R1–R9 做语料**，  
放在 `examples/decisions/`（新增目录，需用户确认，见第五节）：

| 语料                      | 故意埋的缺陷                             | 必须红的机制         |
| ----------------------- | ---------------------------------- | -------------- |
| `bad-missing-source.md` | 决策行只有「#96 建议 A」                    | C16（来源列无可解析路径） |
| `bad-stale-path.md`     | 来源写 `planning/第五期-...md:30`，该路径已改名 | C16（路径不存在）     |
| `bad-no-verify.md`      | 有来源、有推荐，没有核验日期与命令                  | C16            |
| `bad-stale-verify.md`   | 核验日期 2026-09-22，引用文件 10-21 才改过     | C17            |
| `bad-ledger-status.md`  | 台账行写「已修复」但没有 ISS 链接                | C15            |
| `bad-orphan.md`         | `status: open` 的 ISS 不在任何承接表       | C18            |
| `good-r1-r9.md`         | 9 条全部按七段式写全                        | 全绿             |
| `good-r6-channel-knowledge.md`（**已落地**） | R6 单条按五列 + 七段双形态写全，内容基于 2026-10-21 代码核验 | 全绿（实例见 `examples/decisions/good-r6-channel-knowledge.md`） |

**这套语料本身就是交付物**：下次有人问「这个门到底抓什么」，跑一遍正反例即可，  
不用读实现。

## 六、不做什么（明确边界，避免过度工程）

- **不做「清单必须最新」的人治规则**。靠自觉的规则等于没有规则；只做「过期了必须红」。
- **不做状态词的同义词 NLP**。`已修复`/`搞定了`/`OK` 永远列不完，会制造假阳性；  
  状态词只认枚举，散文里怎么写不管。
- **不给每个待办建全量文档链**（proposal→spec→design→plan）。待办不是特性，  
  给它套四阶段只会让人绕过门。
- **不把决策塞进 issue 状态机**。决策不是缺陷：没有「根因」、没有「修复」，  
  硬套会逼人编造字段。决策有自己的五列，够用。
- **不追求「门能判断决策对不对」**。门只能判「字段齐不齐、对象变没变、有没有归属」，  
  结论对错永远归评审。把这条写进契约，免得以后有人加语义检查。
