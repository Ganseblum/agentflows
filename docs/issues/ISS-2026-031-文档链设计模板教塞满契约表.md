## 现象

模板（document-chain-templates.md §design/be）的契约表头即杂糅形态，照抄产出即缺陷：

> `#### 1.4.2 契约字段汇总表 <填：| 接口 | 请求字段(类型/必填) | 响应字段 | 错误 |>`

按此生成的实际产物被用户连续三轮纠偏：`name(string/Y)` 一格挤类型与必填；错误列裸枚举码无解释无 HTTP 码（"都是枚举也好，但是没解释根本看不懂"）；响应字段纯英文名无含义说明。

## 已验证的更优形态（语料证据）

ts-workflow-ai 仓 feature-v4.2-01 Bundle 组合销售接口文档（1439 行，v0.5.9）的形态：

- 统一响应包裹先行（`errno/errmsg/data/trace_id` 带注释）；
- 每接口一个 jsonc 代码块：请求行 + 每字段行尾注释（类型/必填/限制）+ 响应示例 + 失败行（HTTP/errno + 中文含义）；
- 公共对象用 Go/protobuf 结构体 + 行尾中文注释（枚举全在注释里）；
- 错误带 HTTP 码（如 `409/60104`）。

aiwork 本轮实测：改造为该形态后用户确认可读（错误如「400/60501 上限 20 已达」）。

## 根因

模板只定了表头存在（linter C4 也只查「请求字段+响应字段」表头存在），未定形态标准；没有吸收语料中已验证的 jsonc+注释形态。
