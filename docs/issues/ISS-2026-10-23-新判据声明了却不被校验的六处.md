## 现象

独立评审第一轮在 C22/C23 上跑出六处「文档声明了、代码不校验」或「换个写法就绕开」，逐条实测：

| 编号 | 实测 | 后果 |
| --- | --- | --- |
| F1 | 证据列写**裸路径**（不带反引号）→ 判「无载体」 | 与 `spec/be/backend.md` §6.2「反引号内或裸写的相对路径」直接冲突：按契约写反而被判红 |
| F2 | `proposal 出处` 列写不存在的路径 → 无 finding | §6.1 声明「出处路径须可解析」，实现只扫 `spec 承接` 列 |
| F3 | 同形表格放在任意标题下即被当成承接表；真表标题不含「目标承接」时无人读 | 造一张 decoy 表就能让真表逃检 |
| F4 | 表头写 `**目标**` → 判「打了标记却没有承接表」 | 纯样式改动即改变判据结论；且 `_cells` 取不到值时是静默空串 |
| F5 | 承接表写 `◐`/`⚠` 而看板全 ☑ → 不报 | §6.1 声明「出现进行中/未开始/阻塞即要求降级」，实现只判两个方向 |
| F6 | `agentflow@0000000:zzz.md` 直接算可复核载体；仓扫只遍历**有 README 的**批次目录 | 本仓名的引用可达却被无条件放行（同格子的提交号却要求 `git cat-file` 可解）；两模式共用实现却不共用批次集合 |

## 根因

写实现时以「代码写到什么程度」为准，写契约时以「我希望它管什么」为准，两件事没有互相对照的步骤：

1. 契约文本先写（立项当天），实现后写，实现按当时最省事的解析落地，没人回头逐列核对；
2. 夹具只覆盖了实现支持的形态（反引号路径、无装饰表头、只判过报方向），因此**实现缺什么、
   夹具就正好不测什么**——这与本仓自列反模式「存在性 ≠ 形态」是同一形状；
3. 仓扫的批次入口用 `docs/features/*/README.md` glob 起手，把「README 是否存在」误当成
   「批次是否存在」，属于顺手写法固化成口径。

## 修复

- F1 复用既有 `path_candidates()`（与 C9 同一套路径候选口径，不另立正则）。
- F2 出处列走同一 `_resolves()` 校验（批次目录与仓根各试一次）。
- F3 新增 `trace_tables()`：只取「目标承接」标题作用域下的表，标题下无表即报「补表，不许摘标记」。
- F4 新增 `_norm_col()` 列名归一化，表头匹配与取值同一口径；`plan_task_rows` 一并复用。
- F5 状态聚合改为双向：表字形与「全 ☑」不一致即报（过报与漏报同罪）。
- F6 仓名属本仓时要求 rev 可解析且路径在盘；仓扫批次集合改遍历 `docs/features/*/` 全部目录，
  与目录模式一致。

## 怎么避免

新判据落地的自检顺序：**先按契约列一张「声明 → 校验实现 → 覆盖夹具」三列的表**，
任何一行缺第三列（夹具）即视为未实现。本批 C22/C23 的最终夹具与判据条目一比一对应
（86–106），并在 `plan/PLAN-TRACE-001.md` 的偏差节留下这一课的现场记录（DEV-05）。
