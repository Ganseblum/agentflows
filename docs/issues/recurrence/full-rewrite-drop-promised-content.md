## 类模式

整文件覆盖式重写时，文件里**当时已经存在但不属于本次作者**的内容被静默丢弃。两种载体：

1. 已对外承诺的内容——图目录列出的图、既有章节、自测判别夹具（首现三例：design/fe 丢图
   1/5/6，由 linter C8 真实链复跑抓出；design/be 丢执行通道节，评审发现；doc_chain.py
   自测丢 C6 夹具，独立评审 round-2 点名）。
2. 同工作树里他人未提交的改动（`ISS-2026-10-28-整文件重写还原他人未提交改动`：用
   `git show HEAD:index.md` 作底重写 `index.md`，把另一批次未提交的 5 处索引改动还原掉）。

形态一当时无任何机器检查覆盖「承诺 vs 兑现」；形态二的检查缺口是条款按命令枚举
（只点名 `git checkout` / `git restore`）而非按机制定义，于是「以已提交版本为底整份写回」
这类等价写法不受约束。

## 升级记录（2026-10-28，ISS-2026-10-28-整文件重写还原他人未提交改动）

形态二暴露出「按命令枚举」的条款写法的通病：只约束被点名的两条 git 命令，同机制的其它
写法（`git show HEAD:<path> > <path>`、脚本读 HEAD 版本再整份写回）全部漏网。新增两层：

- `AGENTS.md`「实验与恢复」把条款改为**按机制定义**——判据是「写入底稿是否取自已提交
  版本」，并写明正确做法是增量替换、只动自己负责的行。
- `tools/dirty-guard.py`：写前 `snapshot`、写后 `verify`，逐行比对快照时的新增行是否仍在
  当前文件中，消失即红。实测七组（覆盖式重写、删他人行、追加保留、无写入、中文路径真阳性
  与真阴性、本仓 300 个 dirty 文件实跑）判别正确。首版因 `git diff --name-only` 对中文路径
  做八进制转义而产生 131 行假红，改用 `-z` 后修正——这是本仓「首轮误报须修正判据复跑」的
  又一次实例。

残余风险：守卫靠作者自觉在写前调用，没有自动触发点（pre-push / pre-commit 都只在写完之后，
接入会成为「机器门制造假红」）。**这类「按命令枚举」的条款应作为一般教训对待：凡是把危害
写成「这几条命令会出错」的条款，都要检查同类机制是否漏网。**
