## 现象

整门变异测试报告里两项长期被判「无效」，原因都是锚点在源码里已不存在：

```text
M48 无效   doc_chain.C6                   doc_chain_selftest anchor 'for table in re.findall(...fe_text, re.M):' matches 0 lines, need exactly 1
M25 无效   schema.contains                tests              anchor 'if matches < minimum:' matches 0 lines, need exactly 1
```

「无效」不是「门没问题」，而是**这条变异根本没被执行**：判据的破坏从未被尝试，所以这一项的判别力
是未知的。2026-10-20 的评测复核已经记过「M25/M48 锚点漂移」，但只写在计划文本里，没有修，
到本批仍然存在——一条已知缺陷在只被登记的情况下活了三天。

## 根因

`tools/lab/mutate.py` 的 `SPECS` 用**逐字源码行**当锚点。源码改写时（C6 的循环把 `re.M` 写成
`re.MULTILINE`；`schema.contains` 的计数变量从 `matches` 改成 `matched_count`），没有任何检查
要求同步 `SPECS`：

- 变异清单的生成阶段只做「锚点是否命中唯一一行」的运行时校验，跑到该项才发现；
- `validate.py` 的 `tests` 子项跑变异覆盖表只判「每个 ITEMS 条目至少有一个变异或 EXEMPT 理由」，
  条目还在、锚点已失效，照样绿。

即：**清单的完整性有门，清单的有效性没有门**。这与本批 C23 要解决的「已完成却没有可复核证据」
是同一类问题——声明存在，但没人能复现它的效果。

## 修复

两条锚点改为**从源码取原文**再写回 `SPECS`（不是手工猜字符串）：

- `doc_chain.C6` → `for table in re.findall(r"((?:^\|[^\n]*\|[ \t]*\n){2,})", fe_text, re.MULTILINE):`
- `schema.contains` → `if matched_count < minimum:`

## 回归检查

- `python3.12 -B tools/lab/mutate.py --check doc_chain_selftest --report /tmp/…` → `总变异数 15 已杀死 15 存活 0 无效 0`，
  其中 M48 由「无效」转「已杀死」。
- 最终整门实跑（报告落盘）：58 项 = 51 杀死 / 7 存活 / 0 无效（评审第一轮补入 M57/M58 后），逐字记录见
  `docs/features/feature-2026-10-22-追溯闭环与证据在场/testing/agentflows-gate-evidence/evidence/mutation-run-2026-10-23.txt`，
  机器可读版见同目录 `mutation-results-2026-10-23.json`。
- 副作用要如实记账：`schema.contains` 锚点修好后，该项从「无效」变成「存活」，存活总数由 6 升到 7。
  判别力空白因此**多暴露了一条**，不是门退化了。后续处置登记在 ISS-2026-059。

## 备注

后续批次应把「锚点漂移」变成机器判据：`validate.py` 增一项或在 `mutate.py --list` 阶段就校验所有
`SPECS` 锚点命中唯一行，命中失败即门红——现在只有真正跑那一项变异时才会暴露。本批不做（属门项集合变更，
且要与 `--list` 的只读语义一并设计）。
