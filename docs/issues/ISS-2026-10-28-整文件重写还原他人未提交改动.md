## 现象

对一个工作树里已有他人未提交改动的文件做整文件覆盖式重写，那些改动被静默还原。

2026-10-28 实例：`index.md` 同时带着另一批次（工程基线吸收批）的未提交改动。为把本轮的
一行改动「隔离」出来，用 `git show HEAD:index.md` 取出已提交版本、替换目标行、整份写回。
结果该文件里 5 处他人未提交改动（批次索引行、`ISS-<YYYY-MM-DD>-<slug>` 编号更新、
`EP-2026-10-27-002.json` 路径修正等）全部消失，靠事后按 diff 逐条重打才恢复。

预期行为：本次只增删自己负责的行，其余行一字不动。
实际行为：文件被重置为「已提交版本 + 自己那一行」，他人未提交内容整体丢失。
影响对象：同一工作树里并行工作的其它批次；丢失内容若未被察觉，将随下一次提交一起消失。

## 根因

`AGENTS.md`「实验与恢复」原有条款只点名了 `git checkout` / `git restore` 两条命令，
把危害描述成「这两条命令会重置文件」。实际危害属于**整文件覆盖式写入这一整类**：
只要写入的底稿取自已提交版本（`git show HEAD:<path> > <path>`、`git cat-file`、
或用脚本「读 HEAD 版本 → 替换一行 → 写回」），效果与 `git checkout` 完全相同。

条款按命令枚举而非按机制定义，于是同类操作的其它形态不受约束；作者在
「我要隔离自己那一行」这个看似合理的动机下，正好走进了没被点名的那一条。

归因 `missing-constraint`：不是明知故犯，是规则只覆盖了该类的两个实例。

## 修复方案

三条候选，状态：已采纳 1+2，第 3 条暂缓。

1. **把条款从「命令枚举」改成「机制定义」**（已采纳）：覆盖式写入的判据是「底稿是否
   取自已提交版本」，不是「用了哪条 git 命令」。并在条款里写明正确做法——改新版本文件用
   增量替换，只动自己负责的行。
2. **提供可执行的保全校验**（已采纳）：`tools/dirty-guard.py`，写前 `snapshot`、写后
   `verify`；verify 逐行比对「快照时的新增行是否仍在当前文件里」，消失即红。
3. **接入自动门**（暂缓）：没有合适的触发点——它需要「写操作前后」两个时刻的配对，
   而 pre-push / pre-commit 都只在写完之后。若接入会成为又一次「机器门制造假红」，
   留作人工步骤。

**已知局限（照实记）**：守卫按「快照时的新增行是否仍在文件里」判定，因此**你自己改写同一行**
也会报红。这不影响它发现「他人改动被覆盖」，但意味着 verify 报红时要先看消失的那行是不是
你自己刚写的——是，就是正常改写；不是，才是真丢。正确用法是**在覆盖式写入之前立刻 snapshot**，
不是整个会话开头拍一张，快照越贴近写入时刻，误报越少。

## 修复

- `AGENTS.md`「实验与恢复」新增一条：工作树里有他人未提交改动时，任何整文件覆盖式写入
  先做保全快照；列出该类的四种形态；给出 `tools/dirty-guard.py` 的 snapshot/verify 用法；
  附 2026-10-28 实例。
- 新增 `tools/dirty-guard.py`（只读 git，不改任何文件）。

## 回归检查

未运行自动化回归——`tools/` 下脚本未被 `tests/` 覆盖，且 `validate.py` 的 `lint` 子项
只做静态检查。已做的最小实验（`/tmp/dg2`、`/tmp/dg3` 一次性副本）：

| 场景 | 期望 | 实测 |
| --- | --- | --- |
| 用 `git show HEAD:f.md > f.md` 覆盖含他人改动的文件 | 报红并列出消失行 | `FAIL f.md：1 行未提交改动消失 / - 别人的新行`，退出码 1 |
| 删除他人新增行 | 报红 | `FAIL f.md：1 行未提交改动消失`，退出码 1 |
| 追加自己的行、保留他人行 | 通过 | `PASS：1 个 dirty 文件的新增内容全部保全`，退出码 0 |
| 快照后不做任何写入 | 通过 | `PASS：1 个 dirty 文件的新增内容全部保全`，退出码 0 |
| 中文文件名（`索引.md`）+ 覆盖式重写 | 报红 | `FAIL 索引.md：1 行未提交改动消失 / - 别人的改动`，退出码 1 |
| 中文文件名 + 追加式写入 | 通过 | `PASS`，退出码 0 |
| 本仓真实工作树（300 个 dirty 文件）快照后立即 verify | 通过 | `PASS：300 个 dirty 文件的新增内容全部保全`，退出码 0 |

**首版有 bug 并已修**：`git diff --name-only` 默认对非 ASCII 路径做八进制转义，本仓文件名
多为中文，首版因此把 131 行判成「快照后被删除」（假红）。改用 `-z`（NUL 分隔、不转义）后
上表七项全部符合预期。这条记在这里，是因为「首轮误报要修正判据复跑，不得把误报当发现」
本身就是本仓纪律。

## 前后对比

改前：无条款覆盖该类，无任何检查；错误发生后只能靠人记得 diff 长什么样才可能恢复。
改后：条款按机制定义该类，`dirty-guard.py` 可在写入后立即判定「是否有人内容被覆盖」。
实测证明它能精确命中本次这一种写法，同时对追加式写入不误报。

## 怎么避免

已落地：`AGENTS.md` 机制化条款 + `tools/dirty-guard.py` 保全校验。

**这一层不够的位置**：`dirty-guard.py` 靠作者自觉在写前调用；没有自动触发点能够强制它
（见「修复方案」第 3 条）。所以它降低的是「覆盖后不自知」的概率，不是「不覆盖」的概率。
真正的第一道防线仍是条款里那句「改新版本文件用增量替换」。
