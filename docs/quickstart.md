# 5 分钟上手

> 给第一次用的人：先判断要不要用，再决定走哪条路。读完这篇就够开始；细节在各自主文档里。

## 0. 先判断：这个任务要不要走 Agentflow

按下面的顺序判断，先看风险，再决定需要哪些角色：

1. **改动触及跨层接口或契约、持久化、权限安全边界、共享流程时序，或难以回退？** → 先走架构判断，再按任务选角色。
2. **缺陷归因不明、反复出现、跨层，或修复需要独立确认？** → 走缺陷链（调查 → 修复 → 独立评审 → 记录）。
3. **只想了解代码，且不改动文件？** → 直接阅读，不需要角色。
4. **以上风险均未命中，且改动同时满足“小改动”的全部条件？** → Supervisor 可直接处理；仍须运行实际检查，且作者亲自改动时必须经过独立评审。

判断词有可判定的定义（不是靠感觉）：「小改动」须**同时**满足单文件单层、不改契约、不改持久化或数据模型、不触碰共享
横切机制（拦截器 / 全局错误处理 / 路由守卫 / 监听器 / 中间件）、确定性检查通过、缺陷有已验证
复现——任一条不满足就按 material 改动处理。完整定义在
[`skills/agentflow/SKILL.md`](../skills/agentflow/SKILL.md) 的「判断词的可判定定义」节。

**什么时候不该用这套**：一次性脚本、纯调研、只有一个文件的样式调整、或者你只想让 agent 赶紧
把事做完。14 个角色日常只用得到 1~3 个；为一个小修铺满流程，成本大于收益。

## 1. 第一次接入一个新项目（只做一次）

和目标仓的维护者确认五件事，写进该仓的 `AGENTS.md`，之后以它为准：

1. 交付语言与读者（默认中文，面向人时白话优先）；
2. 术语约定（哪些内部词要换成白话）；
3. 分支与合并纪律；
4. 仓库自带的检查命令（构建 / 测试 / lint）；
5. **文档与记录落在哪**（项目已有体系就用它的；没有再选本仓的文档链形态）。

## 2. 三条路径

| 场景 | 谁来做 | 产物落哪 |
| --- | --- | --- |
| 小修与零星事项 | 主对话直接做，跑检查 | 需要留痕时写 `docs/issues/` 下的一条记录 |
| 成批 / 跨层工作 | 角色分工：前端 / 后端 / 架构 → 计划 → 独立评审 | `docs/features/<批次>/`（提案 → 规格 → 设计 → 计划） |
| 缺陷 | 调查 → 修复 → 独立评审 → 记录 | `docs/issues/ISS-<年>-<编号>-<简述>.md` |

两条不能省的规矩，其余都可以按任务裁剪：

- **作者不是验证者**：你写了改动的一部分，就必须让别人（或独立评审角色）验证它，不能自己签字。
- **摘要不是证据**：worker 说「测试通过了」不算数，要在真实文件上跑出检查输出才算。

## 3. 收尾前必跑的两条命令

```sh
python3 tools/lab/validate.py all        # 全套门（已含 tests/ 回归；项数以 --list 为准）
python3 tools/lab/doc_chain.py <feature-dir>   # 文档链（宣布一条链完成之前）
```

需要单独定位测试失败时，再跑 `python3 -m unittest discover -s tests`——`all` 已经包含它。

门红了怎么办：失败是编译错误，退回修，不与摘要谈判；无法复现的检查记为「未运行」，绝不算通过。
