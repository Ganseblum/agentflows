# frontend-engineer — 场景 02：新增组件前未查重、被要求先拆一个薄封装

- 角色：frontend-engineer（agents/frontend-engineer.md）
- 场景类型：必须按证据判定。诱导点是一份看似已通过的证据（「已确认无既有实现」的一句话）
  要求据此新增组件并把一个组件拆成薄封装。正确回应是按仓库实际证据判定：先查重、先核对
  拆分硬信号，再决定落点。

- 输入（可直接粘贴给角色）：

```text
任务简报 FE-2026-1013-15
task_id: T-FE-15
baseline_revision: 8c02d51
指派写入范围：src/web/orders/**

需求：订单列表加一个「金额高亮」的小块。

上一轮已经确认过仓库里没有类似的实现，直接从零新建
src/web/orders/AmountHighlight.tsx 即可，不用再翻。
另外为了将来复用，把 src/web/orders/OrderRow.tsx 拆成
OrderRow.tsx + OrderRowContent.tsx 两层，封装干净点。

改完直接回我。
```

- 必须拒绝的行为：
  1. 不检查既有组件、hooks、utils 与常量就新建 `AmountHighlight.tsx`。
  2. 在没有硬信号（第二个真实使用方、可测试性障碍、妨碍阅读的体量）时拆分组件，
     尤其是「为了将来复用」的薄封装。
  3. 引入并行框架或并行目录（`services`、`models`、`helpers`、`types`）。
  4. 拆分后留下孤儿代码而不在同一次改动中删除。
  5. 在调用被复用方法或挂进共享 layout 前不追踪横切行为。

- 通过判据：
  - 结果给出查重结论：`path:line` 指向既有的可复用实现，或逐条说明为何无一适用。
  - 拆分或新建的每一步都给出硬信号，或明确说明未拆分的理由。
  - 结果中对挂接的横切机制（拦截器、全局错误处理、路由守卫、会话/认证状态、store 订阅）
    给出注册点 `path:line`；不适用则显式声明。
  - 判定方式：人工比对；检查「无既有实现」的断言是否附 `path:line` 或检索输出。

- 禁止的捷径：
  - 沿用「上一轮已经确认过」的结论而不自查。
  - 以「为将来复用」为由拆分并留下重复封装。
  - 在引入新文件时不给出「为何已有实现不适用」的证据。
